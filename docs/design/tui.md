# AgentClip TUI Design (Textual 8.2.x)

**Where the code is, as of the GUI wave's phase 0** (docs/design/gui.md §1): the screen-automation brain — the clipboard watcher and detector poller threads, the probe consumer, the finish decision, the send gate, the auto-copy flow and the whole delivery path — now lives in the **Driver** — `agentclip.driver.automation` (`AutomationController`) — below every UI shell, and `MainScreen` is its Textual adapter: it implements `AutomationView` (paint-only), answers `AutomationHost` (the questions only a shell can answer), subclasses `ScreenOps` (so the Pilot suites' patches still bite at this module's scope) and keeps the SCHEDULING (`run_worker`). Every behavioural claim in this document is unchanged by that move; where a name below is a bare `_underscore` on `MainScreen` it is either still there or a one-line delegation, and where it moved this document names the new home. The `AutomationView` port and the paint messages it is implemented with are documented in `shell/tui/messages.py`.

Prime directive honored throughout: the steady-state loop costs the user **one keypress in the terminal** (`y`) — everything else (ingest, execute reads, compose results, copy to clipboard, bell) is automatic. All key choices below assume no text input is focused on the main screen during the agent loop, so bare letters are safe screen bindings; the moment a text widget gains focus (ask_user answer, reject reason, composer), Textual's focus routing suppresses them automatically.

## 1. Screen map

The harness decision log (§3.3b) used to be a ninth entry here — a `LogScreen` modal holding a *snapshot* of the entries. It is now a **pane** on MainScreen (`HarnessLogPane`, §1.2), for the reason in §3.3b: the moment a user asks *why did it do that?* is the moment it is still doing it, and a modal you have to close, re-open and re-scroll to see the next entry is the wrong instrument for watching a loop.

`HelpScreen` is a cheatsheet, and a cheatsheet about a moving UI rots silently — the version that shipped through three waves still advertised *"F2 settings (lands in M3)"* after F2 had become the whole service-profile editor, still described a tab per delegation after tabs became browser windows, and carried a **fifth** hand-written copy of the chat-command list. So its command section is not prose at all: `screens/help.py` renders one row per `app.commands.COMMANDS` entry (§3.3a) and a test pins the two together, exactly as one pins the controller's dispatch table. The rest is prose and stays prose — but it is prose about the *shipped* model: two rows of window tabs, one persistent sub-agent transcript with dividers, `▶`/`✓`/`✗`, F2 profiles, F3 sidebar, F4 themes, F7 the ELEMENTS crops, F8 the harness log pane, and what the slash popup does to Enter.

Layout reasoning: the chat column is transcript on top with the ActionPanel as a bottom drawer — a side-by-side split for the *diff* was rejected because diffs and command output need horizontal room, and the drawer keeps the last few transcript events visible above the diff, which is enough context to approve. The two right-hand columns are the exception: the sidebar is narrow, static settings chrome (not content) and `F3` collapses it whenever a diff wants the full width back; ELEMENTS is narrower still (20 cells — an icon is a couple of dozen pixels wide) and `F7` collapses it the same way. Two columns rather than one because they are owned by different things and read at different moments, and because the sidebar already scrolls: the pictures went *beside* the verdicts rather than under them, where they would have pushed the lines the user reads mid-run below the fold. Both toggles are `priority` bindings, or the composer's `TextArea` would eat the key. At 110 columns the three columns leave the chat ~58 cells, which is comfortably above the ~54 the ActionPanel's button row needs; anything narrower is what the two toggles are for. The harness log pane is the one thing that is **not** a column: it is a sibling of `#body` in the screen's vertical layout, so it spans the whole terminal and the three columns give up height rather than width while it is open. That is forced by its content — an entry is a timestamp, a kind and a whole sentence of reason, ~120 cells — and it is why the third toggle (`F8`, §3.3b) trades the opposite dimension from `F3`/`F7`.

Transcript auto-scroll is fit-or-park (`TranscriptPanel._autoscroll`, decided per event after its layout settles — Markdown events are awaited via `Markdown.update` so their real height is known): an event that **fits** the visible area pins the panel to the bottom with the container-level `anchor()` (which releases when the user scrolls up and re-engages when they return to the bottom — NB: anchoring the event widgets themselves, the original approach here, is a silent no-op in Textual 8); an event **taller** than the visible area is parked with its top at the top of the view so the user reads the response from its first line. While parked, follow-up noise (tool calls, notes, outbound) mounts below without moving the view; a new conversational beat (user or assistant message) always re-applies the fit rule, and pinning also resumes once the scroll returns to the bottom. One thing that rule cannot see is that an **ingested reply is several events** — the prose, then a widget per tool call — so a reply whose every widget fits used to end pinned at its last line with the model's opening sentence already off the top. The controller brackets it instead (`ChatView.begin_reply` / `reveal_reply`, called only from the ingest path in `_run_turn_body`): the panel remembers the reply's first widget and, once the last one has landed, parks the view there — the same park a tall event gets, applied to the reply as a whole, so the user reads it from its first line with as much of the rest as fits below. Transcript children are pruned beyond 500 events (oldest unmounted) to bound layout cost.

### 1.3 Session start flow (inline — no modal) and the Sidebar

There is **no launch dialog**. At startup the user sees the finished app: an empty transcript, the docked `ChatComposer` enabled and focused, and the settings sidebar on the right. Typing a task and pressing `Enter` starts the session.

Mechanics: `ChatView.prompt_new_session()` (the port the controller awaits, unchanged) is implemented on MainScreen *inline* — it flips `awaiting_new_session`, switches the composer's border title to `Describe the task · Enter starts the session · Ctrl+J newline`, unlocks the sidebar's service `Select`, focuses the composer and parks on an `asyncio.Future`. The first non-empty send resolves it with `SessionSpec(task, service=<sidebar selection>)`; an empty send just warns. **Slash lines are commands here too** (§3.3a): `_submit_text` dispatches them instead of resolving the future, so `/identify` — the one command with no session gate, most needed when nothing is armed — runs at the prompt rather than becoming the opening message to the model, and a session-gated or unknown command toasts its usual refusal with the prompt still waiting. A task that must begin with a slash is typed `//…`, the follow-up path's escape (one slash stripped, the rest is the task).

Every "new session" moment reuses that one path: the launch, the budget-exceeded retry, `/new`, and the summary screen's *new session* choice all call `prompt_new_session()` again, which re-arms the same inline surface. There is no second way to start a session — and one more way to *ask* for one: the sidebar's `#newchat-btn`.

**"New browser chat" ends the session it emptied.** The button's job used to stop at the browser (find the new-chat control in the *selected* tab's window, click it, hand focus back — §3.4a). But on the **master** tab a landed click destroys the very conversation the running session is having, and leaving that session armed would paste its next turn into a chat holding none of its history. So a successful click there also runs the tool side of `/new` (`SessionController.request_new_session()`). And it is the *same flow* `/new` itself runs: the command reaches `MainScreen._new_browser_chat(slot)` through `ChatView.open_new_chat_now()` with the slot pinned to the master (§3.3a), so the button and the command are one implementation with two doors rather than two behaviours that drift.

The five cases, all decided before anything is clicked:

- **Master tab, session active, idle** — click, refocus, then the reset; and the reset even when the click never happened (§3.3a). This is also `/new`'s whole path.
- **Master tab, session active, mid-turn** — the same thing, plus an abort first. The press used to be refused here, on the reasoning that a turn in flight holds results that were never sent to the model; that put the *only* way out of a conversation behind the very turn the user wanted out of. So `request_new_session()` now ends the turn instead (§3.3a): whichever park it is sitting on is poisoned (`_TurnAborted` into the gate or the ask_user future, `_SubagentAborted` into a delegated run's reply future), an executing step is cancelled through `Engine.request_cancel()`, and the reset waits for the flow to finish unwinding before it starts. One toast says so — *"aborting the current step — starting a fresh session"* — and the turn's outbound is never copied, because a payload for a chat that no longer exists is worse than none.
- **Sub-agent tab, mid-turn** — the one refusal left, and it is a different refusal: that window's chat belongs to a delegated run (a delegation keeps the master busy for its whole length), and emptying it would destroy the run's conversation without ending the run. *"the sub-agent window's chat belongs to the run in flight — /abort ends it, or start the new chat from the master tab"*. "Mid-turn" is `busy | pending_approval | awaiting_answer` **minus `awaiting_new_session`**: the inline start flow parks the session worker as busy with no turn in it, the same distinction `action_quit` draws before it warns about quitting.
- **Master tab, no session** (start screen, or already re-prompting after a `/new`) — click and refocus only; there is nothing to reset, and the start screen has just been handed a clean chat to start in.
- **Sub-agent tab, idle** — click and refocus only, ever. That window hosts delegated runs, which the controller starts and ends (§3.4c); emptying it says nothing about the master's conversation. `/new` never lands here: it pins the slot to the master (§3.3a).

The button is also the **escape hatch from an ask_user park** that costs no keystrokes at all. While the composer is in answer mode its text *is* the answer, verbatim — the standing invariant of `SessionController.submit_message` (§3.3a) — so typing `/new` there delivers the string `/new` to the model, as it must. The press comes in through `request_new_session()` instead, which is not competing for those keystrokes, and the abort above poisons the answer future like any other park. (`Esc` is the *other* way out, and a much smaller one: it dismisses the question without ending anything, and slash commands — `/new` typed included — work again the moment it lands. See §3.3e.)

Which slot the press meant is decided **once, before the click**, and carried through as an argument (`_new_browser_chat(slot)` → `_reset_after_new_browser_chat(slot)`) — the same rule the region picker follows (§3.4a) and for the same reason: there are awaits either side of the click, the user can select another tab across them, and re-reading `_calibrating` afterwards would credit the *master* with a chat opened in the sub-agent's window and end the master's session for it. A failed click (any non-`CLICKED` outcome) still runs the reset; what it skips is the refocus, because the browser is where the user has to finish the job. Its toast carries the reason and then hands that job over — see §3.3a's fourth rule.

The controller then composes the bootstrap prompt (protocol layer), copies it, mounts the task as `.ev-user`, arms the watcher, and toasts `bootstrap copied (5.2k chars) — paste into ChatGPT`. If the bootstrap exceeds the preset budget the flow loops back to the inline prompt with an error toast (chunk-walk, §6, lands in M3).

The column is **live status plus the two things you steer with**, and holds nothing that has to be *configured*. Capturing what a service looks like, and ticking which finish signals it may run, both live in the service editor (§1.4): they are per-service settings and belong next to the service's other settings — and six capture buttons with six status lines had grown into two thirds of a 32-cell column that is meant to be glanced at, not filled in. What is left is:

- **STATE**, an eight-line rail, `Sidebar.show_loop(state)`, one row per `driver.automation.loop_state.LoopState` — the **browser-automation loop**, not `engine.states.Phase`. The engine's machine says where the *task* is (awaiting reply, review, done — the status bar's territory); this rail says where the *round trip through the browser* is, which is the loop the user actually watches the tool run: `idle → auto insert → (manual insert) → wait send → wait generate → auto copy → (manual copy) → interpreting → idle/auto insert`. The active state gets a `▶` marker and bold/reverse; `LOOP_TRANSITIONS[active]`'s rows read at normal brightness; everything else is dim. `AutomationController.set_loop_state` is the sole writer and drives it from the loop's own events rather than from status pushes or tab clicks: `copy_outbound` enters **auto insert** and resolves it to **wait send** (the synthetic Ctrl+V landed) or **manual insert** (it did not — the user pastes); the send gate seeing its button promotes a manual insert to **wait send**, and its release (§3.4b), or `evaluate_finish` arming on generation evidence, enters **wait generate**; the finish verdict either fires the auto-copy flow (**auto copy**) or — no captured copy button, or any flow failure — hands the harvest to the user (**manual copy**); `ClipboardCaptured` (and the `i` force-ingest) enters **interpreting**; and a status push whose turn has settled back to waiting on the user, or whose session is gone, returns the rail to **idle** (`clear_transcript` resets it there too). Because it follows the live automation's events, the rail is the **LIVE** window's loop — the same scope as DETECTION — and the states are display only: nothing reads the enum back to make a decision, so evidence that skips a state (a manual paste-and-send the gate never saw) simply never shows it. Painted once on mount so it is never blank.
- **SERVICE**, which is per *window tab* (§1.6): the picker, its caption and the appearance summary all describe whichever tab is selected, and `Sidebar.show_service(key)` writes that tab's key in when the selection moves — deliberately *without* posting `ServiceChanged`, because the picker is catching up with a choice already made rather than announcing a new one. There is no AGENT SLOT picker any more; the tab bar replaced it.
- **CHAT WINDOW**, the selected tab's window: `#set-region-btn` writes into it, and `Sidebar.show_slot(cal, note)` repaints the block — the drawn rectangle and the readiness note — in one go. Nothing else: the detection lines below are **not** the selected tab's (see §3.4e).
- **DETECTION**, five read-only lines the running automation writes into: `Sidebar.update_template(kind, text)` for the send gate (§3.4b), the busy/idle probes and the auto-copy flow's last click attempt, `Sidebar.update_stale(text)` for the staleness verdict. Only four `TemplateKind` values ever produce a *decision* (`DETECTOR_LABEL`); the two chat boxes and the new-chat button are searched on every tick like everything else (§3.4f) but nothing here is decided from them, so they have no verdict line and `update_template` ignores them — their pictures are next door, where every kind has a row (§1.7). Each line is *named as it is painted* (`send · …`, `busy · …`, `idle · …`, `copy · …`) — five unlabelled verdicts stacked on each other are not readable — and pinned to `height: 2` (class `side-probe`) so a long verdict cannot walk the button below it up and down the column. **The block is the LIVE window's, not the selected tab's**, its heading says which (`Sidebar.show_detection_window` → *DETECTION · SUB-AGENT*), and only the detector machinery writes into it — the ownership rule is §3.4e.
- ...and the **pictures** those lines are words about are the column next door: `ElementsPanel` (§1.7), one crop of each appearance the detectors actually recognised — all seven kinds, not just the four with verdict lines here. Written by the same machinery under the same rule (§3.4e), and deliberately *not* in this column — the sidebar already scrolls, and seven pictures at the bottom of it would push the verdict lines below the fold exactly when they are being read.
- One read-only **appearance summary** under the service picker, `#side-profile-note` — *"appearance: 4/7 captured · F2 for captures + detection"* — so *is this service usable at all?* is answerable at a glance without opening the editor. It names F2 for both halves because both live there: the captures and the checklist that decides which of them the poller may use.
- **MCP** (docs/design/mcp.md §6), one `side-status` line per configured server, sitting with PROJECT because it shares its scope: one `McpManager` per process, an app-run fact rather than a tab's. The block — heading included — is composed **only when the app was built with a manager**, so the default install's column is untouched; the row count is then fixed for the process (permissions.json is read once) and rows are addressed by config-order *index* (`side-mcp-0…`), never by server name — names are the user's and can collide once sanitized into an id. `Sidebar.show_mcp(statuses)` is the display-only painter (`show_profile`'s pattern); each line is `name · human state`, plus the tool count when connected and the detail on `failed`/`needs_auth` — one ellipsized row each (`/mcp` prints the uncut lines). Live updates arrive over the manager's status hook: `MainScreen._mcp_status_hook` runs on the **manager's loop thread** and only posts `McpStatusChanged` (`post_message`, the same thread-bridge idiom as the detector probes and the run-panel hooks — not `call_from_thread`, which refuses the same-thread case `ensure_started` can produce); the handler repaints this block **and** `#seg-mcp` from a fresh `statuses()`, and lands `failed`/`needs_auth` in the **master window's transcript once per server per state** (`_mcp_announced`; toast too), while `connected` only toasts quietly, once. The hook is wired — and the block painted — at `MainScreen.on_mount`, which is app mount in practice (the screen is pushed once and never popped), so the lazy-connect resting states (`pending`/`disabled`) show before any transition fires.

`Sidebar.show_profile(profile)` repaints that summary and nothing else. It is called when the service picker moves (`Sidebar.ServiceChanged` — a domain message, because a different service is a different set of appearances, not a display change: MainScreen files the key against the selected window, relabels its tab, reloads the profile, repaints and recomputes the readiness note), when the window tab bar moves, and when `MainScreen.update_config` adopts an editor visit. It deliberately does **not** reset the probe lines any more: those belong to the service the poller is *running*, which is the live window's, so wiping them on a tab click threw away the readout of a sub-agent run the user had switched over to read. Resetting them is the poller's own job (§3.4e). The detector poller is the one thing `ServiceChanged` restarts **conditionally** — only when the tab that changed is the one the automation is driving (`_calibrating is _live`), because re-pointing the sub-agent window mid-session is the normal way to set delegation up and rebuilding the master's poller there would throw away its in-flight streaks for a window nothing is watching. Same rule as a mid-session region redraw (§3.4a).

**The finish detectors are presence questions, not fixed rectangles.** "Is the model still generating?" is answered by asking *is the stop button on screen anywhere in the chat?*, not *does this rectangle still look like it did?* — so the user captures what the busy indicator **looks like** once per service (the busy-indicator row's "Capture" in the editor, `TemplateKind.BUSY`) and `agentclip.driver.screen.presence.PresenceTracker` searches for it inside the drawn chat region on every poll. It searches for *every* image the service has of that kind (§3.4d) and ORs them, stopping at the first hit: the question is presence, this runs on a poll timer, and the diff it reports is only ever the sidebar's readout. The prompt warns against boxing an animated spinner, and that warning lives on the enum rather than in the TUI: an animation is a different picture every frame, so it can never be matched back, and that is a fact about the appearance, not about the caller.

The de-bounce is deliberately **asymmetric**. The two mistakes are not equally bad: believing the model is still generating when it has finished costs one poll interval, while believing it has finished when it hasn't harvests a truncated answer and feeds it to the engine as the whole response. So "still generating" is adopted the instant one frame supports it, and "finished" must survive `required_ticks` consecutive frames. The idle indicator's capture (`TemplateKind.IDLE`) is the mirror — something on screen only while the chat is **idle**, usually the send button — with `found_is_busy=False`, so `#side-tpl-idle` reads the inverse polarity. Both repaint via `Sidebar.update_template(kind, …)` with an unmistakable state string (`● GENERATING · match (diff 1.2%)` / `○ response ready · changed (diff 34.0%)` / `✗ capture failed`).

The third detector has **no button and no capture at all**: the drawn chat region reading unchanged frame to frame *is* a finished response, whatever a particular service's pixel cues do (`agentclip.driver.screen.stale.StaleTracker`, comparing each poll to the previous one rather than to a fixed anchor). Once it has read unchanged (`STALE_MAX_DIFF = 0.002` over up to `STALE_MAX_SAMPLES = 16384` samples) for `required_ticks` consecutive polls it reports STALE. `#side-stale` (`Sidebar.update_stale`) is a readout only: `○ response ready · stale (still ×4)` / `● GENERATING · changing (diff 0.08% · still ×2)` / `✗ capture failed`. Because it rides on the box every window draws anyway, **every window has a working finish detector from its first drag** — busy and idle only reinforce it.

**Which of the three run is the service's decision** (`ServicePreset.finish_signals`, edited in the service editor's DETECTION checklist, §1.4): a checklist over `config.FINISH_SIGNALS = ("busy", "idle", "stale")` — the same canonical order the poller builds and posts in — defaulting to `("stale",)`, the one every drawn window can already do. A ticked busy/idle entry *additionally* needs its appearance captured; a ticked `stale` needs nothing. Staleness is therefore opt-**out**, not unconditional: a chat whose region never settles (an animated avatar, a ticking clock) can untick it and lean on its icons instead — and `#side-stale` then reads `stillness not watched for this service - F2` (`Sidebar.STALE_UNTICKED`) rather than sitting blank while the icons do the work. An empty checklist is legal and means no finish detection at all — nothing can fold into a verdict, `_active_detectors` is empty and `#side-stale` reads `finish detection off - F2 to configure` (`Sidebar.STALE_OFF`), because "the auto-copy will never fire" must be visible somewhere other than in a copy that never arrives, and the door to turning it back on is the only useful thing to say next to it. That is deliberately **not** the same question as whether a poll loop runs: any captured appearance is worth watching and showing (§3.4f) — a send or copy button, and equally a stop icon whose signal nobody ticked — so the worker starts whenever `ScreenDetector.watching` — anything at all is calibrated — and only `_active_detectors` decides what can ever *finish* a response. A ticked busy/idle entry *without* its appearance runs nothing either, so its own line says `ticked but not captured - F2` (`Sidebar.PROBE_UNCAPTURED`) instead of resting forever at "no verdict yet", which is indistinguishable from a detector that simply never finds anything. Unknown entries are dropped (with a warning) when the config loads, so the poller can never be asked for a detector that does not exist.

All of them share one knob and one tick. `required_ticks` comes from the **live window's** service preset's `stable_seconds` (§1.4) via `max(1, round(stable_seconds / _BUSY_POLL_S))` for *every* tracker, because "how long is long enough" is a property of the streaming cadence of the service in the chat being driven — mid-delegation that is the sub-agent tab's, not the master's and not whichever tab is on screen. And each tick takes **one** capture of the chat region and hands it to all of them: cheaper, but mainly it makes them judge the same instant instead of three moments of a moving screen, and it makes a failed capture reach all of them as the same ERROR (`PresenceTracker.observe(None)` / `StaleTracker.observe(None)` — streaks intact, so one dropped frame cannot restart the stillness clock on an in-flight finish). Their verdicts drive the auto-copy-click trigger described in §3.4b and nothing else. The drawn region survives `/new` (only the pointers reset to MASTER, and the poller restarts against the surviving window); the captured appearances survive the process itself.

**A fourth appearance rides the same tick and is not a finish detector at all.** `TemplateKind.SEND_READY` — the *ready-to-send button*, the control a service shows only while there is something in the composer to send — answers a question that comes *before* all three of them: has the user actually pressed Enter yet? Between AgentClip's paste and that keystroke the chat is still, and a still chat is what the stale detector calls finished. It is **searched for on every tick the live service has a capture of it** (§3.4f) — the search is not the gate's to switch on — and while such a capture exists `AutomationController.open_send_gate` reads those answers and holds finish detection back until the button has been *seen* and then seen to *go* — or until the model is seen to *generate*, which proves the same send by better evidence and overrides the gate (§3.4b). It has no checklist entry and no checkbox, because there is nothing to decide: a service either shows such a button or it does not, and the capture is the whole switch. It is also the appearance stacks exist for: a service that **greys the send button out while a file uploads** draws a second picture of the same control, and a profile holding only the first would read the greyed one as "the button is gone" and release the gate on a message nobody has sent. Capturing the greyed variant too keeps the gate armed — the probe reports found if *any* image matches. `#side-tpl-send-ready` is its line (`send · watching for the send button` / `on screen - press Enter to send`, then whichever of the four ways it let go applies: `gone - sent, finish detection running`, `generating - sent, finish detection running`, `never appeared - finish detection running`, `never went away - finish detection running` — resting at `no gate - not captured`).

The `Select` is the only place a service is chosen, and it chooses one **per window tab**: the master tab's value flows into `SessionSpec.service` and from there into the engine and the status bar's service segment, the sub-agent tab's into `SessionSpec.subagent_service` and from there into every delegated run's engine (§1.6). It is **disabled while a session is active** — on *both* tabs, because both were baked in at bootstrap (the master's paste budget into its engine, the sub-agent tab's into the `can_delegate` answer that decided the catalog) — and re-enabled whenever `prompt_new_session` is waiting. After the services table itself changes (service editor), the sidebar rebuilds its options via `Sidebar.refresh_services(config)`, preserving the current selection when that preset survived; `MainScreen.update_config` does the same repair for the tab that is *not* selected, which has no widget to catch a deleted preset.

Rejected alternatives: a one-line `Input` for the task — coding tasks are multi-line (pasted tracebacks), so `ChatComposer` (Enter sends, `ctrl+j` newline, paste keeps newlines) is the right widget. And the original launch modal — it forced a decision (which service?) before the user had seen anything, and duplicated a text box the main screen already owns.

### 1.4 ServiceEditorScreen (shipped M3; scope narrowed from the original ConfigScreen sketch)

The original ConfigScreen sketch covered the whole config surface (permissions, poll interval, bell/toast switches, backup retention); what actually shipped is narrower and sharper, and is now the **whole per-service profile editor**: a `ModalScreen["ServiceEdits | None"]` (`src/agentclip/shell/tui/screens/service_editor.py`) holding everything that is a property of *one chat service* — its name, the two size numbers (`max_paste_chars`, `total_context_chars`), the stale-detector's stillness window (`stable_seconds`, §3.4b), what it **looks like** (the seven captured appearances, §3.4d), which **finish signals** its poller may run (`finish_signals` + `hover_scan`, §1.3/§3.4b), how an outbound payload is **delivered** into its chat box (`delivery` + `auto_submit`, §3.4a), how the auto-copy flow **scrolls** to the newest reply (`scroll_action`, §3.4b), one short line of **extra instructions** for the model about this host's quirks (`extra_instructions`, protocol.md §2 / §3.4h), whether the foreground **comes back here** after an auto-sent delivery (`snap_back`, §3.4a), and whether a loop that has stalled on the user **says so out loud** (`alert_sound` + `alert_repeat_seconds`, §3.4a). The rest of the config surface is still hand-edited TOML; nothing else needed a form badly enough to justify one yet.

Opened via `F2` (`AgentClipApp.action_settings`) or the sidebar's "Edit services..." button. Both routes are synchronous entry points into an async flow (`push_screen_wait` needs a worker), so `action_settings` is a plain `def` that hands off to `self.run_worker(self._open_service_editor(), group="settings", exclusive=True)` — the same shape as `AgentClipApp._confirm_quit`. Two guards on the way in: if the editor is already the active screen, F2/the button are no-ops — and if `MainScreen.picker_open` says the chat-region overlay is up, F2 is **refused with a toast**, because the editor has capture overlays of its own behind a separate flag and two fullscreen child processes cannot share a desktop (cancelling a worker cannot kill either of them). The visit also suspends the finish detectors for its whole duration (§3.4e).

The editor opens preselected on the **currently selected window tab's** service — `MainScreen.selected_service` (master tab selected → the master's service key; sub tab selected → the sub-agent's, already resolved to the master's when the sub key is blank, same resolution `_active_preset`/`_service_for` use everywhere else) — passed into `ServiceEditorScreen` as `initial_key`. This is what you were just looking at, not a fixed default: `_open_service_editor` reads `main.selected_service` fresh on every open. Falls back to `config.general.service`, then alphabetically first, when `initial_key` is `None` or names a service that no longer exists (`main` is `None`, or the key was deleted since). Every other service is still one click away in `#svc-select` — only the *initial* selection changed.

**The layout has exactly one flexible column, and it is the form.** The other two hold *prose* — checkbox sentences, kind names, status readouts — and truncated prose reads as a different text: the first shipped layout squeezed each status into whatever a 34-cell column had left beside a preview and a button, which on a real terminal rendered *"captured"* as *"captu"*. So the texts got lanes sized to render whole (the appearance column's 50 = 12 preview + gutter + 21 for the longest kind name and status + 5 for the stacked click-point boxes + 9 for the stacked buttons), the columns holding them are fixed, and `#svc-form-col` absorbs a narrow terminal instead — deliberately, because it holds *values*: a squeezed `Input` scrolls its content and stays fully editable, and its labels end in an ellipsis rather than a chop. The Add/Reset/Delete action moved out of the form column to `#svc-footer` for the same reason — exactly one of the three is displayed at a time (`_update_buttons`), and the footer, shared with the escape hint, is the one strip whose width no column can squeeze. Everything that can ever be truncated anyway carries `text-overflow: ellipsis`, so degradation below ~100 cells is an honest "…" and never a mid-word cut. Both geometries are pinned by tests at 120×45 *and* 100×35 (`test_appearance_texts_survive_a_narrow_terminal_uncut`).

**Model:** the screen works on an in-memory *working copy* of `config.services`. Selecting an existing preset and editing its name/sizes applies **live** — every keystroke revalidates the whole candidate (key + label + both sizes together, since "max ≤ total" is a cross-field rule) and, only while the candidate is fully valid, writes it straight into the working copy; an invalid candidate is never applied, it just leaves `#svc-error` showing why. Adding a new preset is the one *discrete* action instead of a continuous one: fill in a unique lowercase-hyphen key (validated against `^[a-z0-9]+(-[a-z0-9]+)*$`, immutable once created) plus the other fields, then press "Add service" (enabled only once the candidate validates) — creation is a one-time event best gated behind an explicit action rather than silently committing a half-typed key on every keystroke. The fourth field, `stable_seconds` (`#svc-stable`, "Stale after (seconds unchanged)"), folds into the same candidate and the same live-apply/discrete-add split, but validates on its own (`0.5`–`60`, the exact bounds `config.py`'s `_take_float` enforces on load, so a value the editor accepts is never silently replaced on next start) rather than cross-checked against the two sizes; unlike the blank size fields it is pre-filled with `DEFAULT_STABLE_SECONDS` (`2.0`) when adding a new service, since it has one sensible default most users never need to touch. The fifth, `extra_instructions` (`#svc-extra-instructions`, "Extra instructions (one short line)"), rides the same live-apply path with **no validation at all** — any text is legal, including none, which is the default everywhere. It is a single-line `Input` and that is the whole design of the field: the text is shipped verbatim inside the bootstrap, which has ~67 chars of slack on the smallest presets (protocol.md §2), so the box itself is the budget warning. `r` (§3.4h) is what makes one short line enough.

**Escape** (`action_close`, same worker hand-off shape as `action_settings` since it awaits a modal): if the currently displayed fields are valid, the screen dismisses with the working `services` dict if it differs from what it opened with, or `None` if nothing changed (so the caller has nothing to persist). If the currently displayed fields are invalid, nothing was ever written to the working copy (invalid values are never committed) — so there's no real edit to lose — but the visible text would still vanish, which is surprising, so escape instead asks via the shared `ConfirmScreen`: *"The current field values are invalid (\<reason\>) and were never applied. Close the service editor anyway?"* Denying returns focus to the editor; confirming closes as if the field had never been touched.

**APPEARANCE** (`#svc-appearance-col`): one fixed-height row per `TemplateKind` in declaration order — the picture, then the kind's name over its status line, then "Capture" and "Clear" stacked at the right edge — plus the `#svc-templates` count and the "Forget appearance" escape hatch. The kind's *name* carries the row, which is what lets the button be the one word "Capture" instead of seven "Capture \<thing\>..." labels that each filled a column on their own; it also turns the block into a scannable table, names aligned above names, statuses above statuses. The block is *generated* from the enum with the kind encoded in each button's id (`svc-capture-<kind>-btn`, class `svc-capture-btn`), so **one** `@on(Button.Pressed, ".svc-capture-btn")` handler serves all seven — an eighth appearance is an enum member and nothing else. A press runs the same full-screen draw-a-box overlay the chat region uses (`driver.screen.picker.pick_region` with `TemplateKind.prompt`, then `driver.screen.capture.capture_region`, both imported *into* this module so tests monkeypatch them at `agentclip.shell.tui.screens.service_editor`); the modal stays open and `_show_appearance` re-derives every readout from `profile_store.load_profile(profile_root, key)` when the worker returns.

**A capture ADDS an image; "Clear" is what takes them away.** A kind holds a *stack* (§3.4d), all of it ORed at match time, so pressing "Capture busy indicator..." a second time teaches the service a second way that control is drawn rather than correcting the first — and the status line therefore counts them (*"24×24 · 3 images"*, the first image's size), because a line that kept saying "captured" would leave the user believing the second press replaced the first. Each kind's own **Clear** (`svc-clear-<kind>-btn`, class `svc-clear-btn`, parsed back out by the same convention through a second `@on(Button.Pressed, ".svc-clear-btn")` handler) empties that one stack, **instantly and with no `ConfirmScreen`**: a cleared kind is one capture press away from being back, so a dialog would cost more attention than the mistake it guards. It is `disabled` while the kind is empty, which is also the only readout of whether pressing it would do anything — there is no dialog on the way to find that out from. "Forget appearance" keeps its confirm and stays what it always was: the whole service's calibration, gone. The `#svc-templates` line under the rows counts and does nothing else (*"appearance: 3/7 captured"*): every kind's row already carries its own name and status, and the captured-names list the summary used to append made it wrap by a different number of rows per service, walking "Forget appearance" up and down on every selection change.

**And the row shows the capture, not only its size.** `#svc-tpl-preview-<kind>` draws the kind's *first* image at the head of its row, twelve cells wide. *"40×40 · captured"* says a drag happened; it cannot say **what** was caught, and a box that missed the stop button and got the blank page beside it reads identically — which is the one calibration mistake with no other symptom than an automation that quietly never matches. The first image only: a kind's variants are pictures of the *same* control (§3.4d) and the count is already on the line beside it. It is repainted by `_show_appearance` with every other readout — same folder, same re-read — so a Clear or a "Forget appearance" takes the picture with it; a thumbnail of a PNG no longer on disk would be the most convincing wrong answer in the column.

**Both renderers, chosen exactly as the ELEMENTS column chooses them** (§1.7): `ServiceEditorScreen` reads the startup verdict once in `__init__` and composes `textual_image.widget.sixel.Image` or a half-block `Static` per kind, never revisiting it. That the two surfaces answer the *same* question is the reason they must not answer it at different qualities — this block is where a capture is judged, and judging it from twelve by four averaged pixels ("is that orange thing an icon or a slab of page?") was strictly less than the terminal could show. On the sixel path the picture is the captured `RegionImage` at full resolution put through `crop_picture`, and its height is `preview_rows` — `graphics.crop_rows(cell_height)`, the ELEMENTS column's pixel budget, **capped at `SIXEL_PREVIEW_MAX_ROWS` (3)** — pinned inline on the widget **and on the `.svc-appearance-row` around it**, because a bitmap taller than its container is simply cropped, and cropped sixel is not cropped at all (next paragraph). Half-blocks keep the two-row budget unchanged in every respect: they are what every terminal without sixel gets, headless test runs included.

**Nothing in the appearance column ever scrolls, and that is a sixel-safety rule, not a styling preference.** The column used to take the body's height and scroll (`overflow-y: auto`), which read as the obvious way to absorb the taller sixel rows. It was the source of the smeared pixel bands the editor left across the terminal: textual-image's sixel widget injects its escape sequence at `render_lines` time and moves the cursor itself, **bypassing Textual's compositor and its clipping entirely** (`shell.tui.graphics`), so a preview half scrolled out of its viewport — or half clipped by any container — keeps painting its full bitmap over whatever Textual believes is there, and what it painted last frame is not erased by a scrim or a repaint of ordinary cells. The only design that *guarantees* no residue is one where every sixel row is always entirely on screen: the column is content-sized, all seven rows are always visible, and the row cap is what makes that arithmetic hold — `crop_rows` can answer four-plus on a small font, which ELEMENTS (four crops in a full-height column) can absorb and seven always-visible rows cannot. Seven rows of three plus the readouts fit the modal's 95% share of a 45-row terminal with room to spare, and the whole modal — footer included — still fits a 35-row one. `test_sixel_previews_sit_whole_inside_the_modal_at_a_narrow_terminal` pins exactly that structure: full `preview_rows` height for every kind, every preview region inside the box, `max_scroll_y == 0`.

Captures are the one thing here that does **not** wait for escape: `save_template` writes the PNG immediately, exactly as Clear and "Forget appearance" delete immediately, because the editor holds no `ServiceProfile` of its own to hand back — the store *is* the working copy, and `ServiceEdits.profiles_changed` is what tells the caller its cache is stale. Consequently a save failure files nothing at all (unlike the old main-screen path, there is no in-memory template left to be useful) and is reported as an error toast. The box is still anchored first (`ServiceProfile.put` on a throwaway profile) so an unsearchable sliver is refused before anything reaches disk.

**One overlay at a time, and escape belongs to it.** Cancelling an exclusive worker cannot kill the blocking child overlay process it spawned, so `_capturing` is held for the whole method (pick → capture → anchor → save → repaint), and while it is held a second capture press *and* `action_close` are both refused with a toast — closing the editor out from under an in-flight capture would strand the worker that still has to write the PNG. Same shape as MainScreen's `_picker_open` guard on the chat region.

**DETECTION** (`#svc-signal-*`, `#svc-hover-scan`): the finish-signal checklist and the hover-scan opt-in, labelled in *user* terms — "reasoning icon disappears" / "send icon appears" / "screen stops changing" — because the TOML names (`busy`/`idle`/`stale`) describe how a detector works and these describe what the user will see, which is the only thing they can check against their own chat window. `Checkbox.Changed` folds **all four** boxes back into the preset at once (`normalize_finish_signals` over `config.FINISH_SIGNALS`, then `replace`) rather than toggling one entry: the checklist has one canonical order anyway, and reading the set makes the handler immune to the echo Textual fires when `_load_service` writes the values in — that echo writes the freshly loaded service's own values straight back, which is a no-op. A ticked `busy`/`idle` whose appearance is not captured runs *nothing* (§3.4d: the checklist and the profile are ANDed), which is otherwise invisible until an auto-copy never fires, so `#svc-signal-warning` says so inline — *"busy indicator: ticked but not captured — it will be skipped"* — and clears the moment the capture lands.

**DELIVERY** (`#svc-stream-delivery`): one tick, because there are exactly two modes and one of them is the default — off is `delivery = "paste"` (one clipboard write, one Ctrl+V) and on is `"stream"` (the payload walked in a chunk at a time, §3.4a). It rides the same `Checkbox.Changed` handler as the detection ticks for the same echo-proofing reason, and the same working-copy-then-persist path on close; it is written to the TOML as the mode *name*, not a boolean, so a third mode would not have to break the file.

**MATCHING** (`#svc-matcher-set`, `#svc-tolerance`): the two settings that between them decide whether a captured appearance is *found* — a different question from what the service looks like (APPEARANCE) or from what counts as finished (DETECTION), which is why it is its own block rather than more ticks under either. The backend picker is a `RadioSet` of two, labelled by the trade rather than by the library ("Anchors (built-in)" / "OpenCV (exhaustive)", §3.4g); `RadioSet.Changed` reads the pressed button's id back and `replace`s the preset, which is the same echo-proofing route the detection ticks take — `_load_service` sets `_selected_key` before it presses anything, so the echo can only ever write a service's own value onto itself. Choosing OpenCV on a machine where `cv2` will not import still *saves* the choice (the user may be configuring a machine they are about to install it on) but shows `#svc-matcher-warning` inline, because the fallback is otherwise completely silent: the setting persists, a search runs, and it is simply not the search that was asked for. **The line depends on how AgentClip was installed** (`opencv_missing_note`, keyed on `sys.frozen`), because the two audiences can do two different things about it: from source it is *"OpenCV is not installed — anchors will be used. Install it with `pip install agentclip[cv]`"*, and in a frozen build it is *"This build does not include OpenCV — anchors will be used. Nothing to install: it has to be built in."* Showing the pip line inside the exe was a real bug report — there is no environment to install into, so it sends somebody to a command that cannot help them and reads as if they had got something wrong. The shipped exe bundles OpenCV (§3.4g), so the frozen branch describes a build made without the `cv` extra; it still has to tell the truth. The probe (`driver.screen.matchers.opencv_available`) is read **once** in `__init__`, like the graphics verdict, since asking costs a real import of a 60MB wheel.

The tolerance control is a **slider**, and it is the only one in the app (`shell/tui/widgets/slider.py` — Textual 8.2 ships none, so it is ours: a track, a handle, the number beside it, arrows to walk it, shift-arrows for ±8, home/end, and a click on the track to jump). Almost every number in this app is right to be an `Input`: a paste budget or a context size is a value the user *knows*. Pixel tolerance is the exception — nobody knows their browser's sub-pixel anti-aliasing needs 31 rather than 24; they know their button is not being found and want to push a value until it is, which is a gesture and not a typed fact. It applies live with no validation gate, because the control cannot express a value outside `0`–`64` and those are the exact bounds `config.py` enforces on load. `_load_service` fills it in via `set_value(notify=False)` so that loading a service does not read back as the user having moved it.

**Nothing to file it under yet.** While the `+ Add new service...` sentinel is selected and "Add service" has not been pressed, there is no key, so every capture button, every checkbox, the backend `RadioSet` and the tolerance `Slider` are all `disabled` (disabled rather than hidden: the column must not reflow while the user fills the form in). They come alive on the `_refresh_select_options` that follows the add. Disabled, but **not blank**: the controls show the `ServicePreset` dataclass defaults (`_NEW_PRESET_DEFAULTS` — *screen stops changing* ticked, hover off, anchors at tolerance 24), which is exactly what "Add service" is about to create. An all-unticked form that silently produced a stale-ticked preset misrepresented the one setting this form is the only place to see.

Because the editor writes *and* deletes profiles out from under MainScreen's per-run cache, `MainScreen.update_config` clears that cache, repaints the sidebar summary and restarts the detector poller — which is what makes a busy/idle capture take effect without a restart.

**Delete vs. reset:** the twelve built-in keys (`config.BUILTIN_SERVICE_KEYS`) can be edited and reset but never deleted — `#svc-delete-btn` only appears for a non-built-in key. `#svc-reset-btn` only appears for a built-in key and restores its shipped values (`config.default_services()[key]`) regardless of whether it currently differs (idempotent no-op if it's already default).

**Wiring on close** (`AgentClipApp._open_service_editor`): a non-`None` result is persisted via `config.save_services(result, self._global_config_path)`, which writes a preset's whole `[services.<key>]` table only when it differs at all from its built-in default (an untouched or reset-to-default built-in is omitted entirely) — and, within a written table, adds `stable_seconds`, `matcher` and `tolerance` only when *that field itself* still differs from the built-in's, so editing just the size fields on a preset left at the default `2.0` doesn't pin today's value into the file; a service that never customizes it keeps tracking future changes to the shipped default. That result is folded into a fresh `Config` via `dataclasses.replace(self.app_config, services=result)`, and propagated to `self.app_config`, `MainScreen.update_config` (which also updates the `SessionController`'s config so the *next* session and any `/new` see it), and `Sidebar.refresh_services`. Engine construction reads `Config` fresh per session start (`cli.make_engine_factory` takes a `get_config: Callable[[], Config]`, called on every `build()`, not once) — so a saved edit takes effect for the next session in this process without restarting the app, while a session already in flight keeps the `Config` snapshot its `Engine` was built from. Opening/using the editor mid-session never touches `awaiting_new_session`, so the sidebar's service `Select` stays exactly as locked/unlocked as it was before.

### 1.5 End-of-session summary (SummaryScreen)

Pushed on demand via `e` (end session); it is **not** auto-pushed on `task_done` — the user stays in the chat and may follow up (protocol.md §8). Contents: a `Static` rendering a Rich `Table` — turns, calls per tool, files created/modified (paths), commands run, total chars pasted both ways, and `sub-agent runs` when the session delegated at least once — plus the `task_done` summary text from the LLM as `Markdown`. Bindings on the modal: `u` undo the **most recent turn** (ConfirmScreen; the modal then closes back to the chat — walk further back with the main screen's own `u`, or reopen with `e`; only `l` export re-shows the summary), `t` new session, `escape` back to main (transcript stays for review), `ctrl+q` quit.

### 1.6 Window tabs, agent slots and delegation

Delegation (protocol.md §3's `delegate` tool) gives the model a second chat window to run a bounded sub-task in. **A tab is one of those browser windows.** Not a transcript, not a session view: a window is open before any session exists, keeps its own service, its own drawn rectangle and its own accumulating transcript, and is still there after `/new`. Everything else in this section follows from taking that literally.

**The bar.** `WindowTabs` (`shell/tui/widgets/window_tabs.py`) is two rows: row 1 the master windows, row 2 the sub-agent windows of whichever master is selected. Today that is exactly one of each — `m1` and `m1-s1`, tab ids `win-m1` / `win-m1-s1` — so it reads as two short title lines, and there are no add/remove controls. The ids, the `WindowSpec` tree, the `WindowSelected` message and the sub-row rebuild are shaped for N × N anyway, because they are the entire difference between one-of-each and many, and retrofitting them would mean re-teaching every caller what a tab is.

Each tab's label is *what the window is · what it runs on*, plus live state: `MASTER · chatgpt-attach`, `SUB-AGENT · claude` before anything has run there, `▶ SUB-AGENT · claude` while a delegated run is in flight, and otherwise the **last** run's outcome: `✓ …` when it handed a result back, `✗ …` when it ended without one (a refused chat, a bootstrap over budget, an abort, a crash). The last run, because the tab is a status light for the window and what a user wants at a glance is how the most recent attempt went; the earlier runs are still readable in the transcript below it. The service is on the tab because it is per window and the sidebar only ever shows the selected one's — otherwise *"which chat is the sub-agent going to open?"* would be a question you answer by clicking around.

Textual's `Tabs` is deliberately not used. Two rows would be two independent `Tabs.active` values fighting over one selection, and a row whose only tab is already active swallows a click without posting anything (`_activate_tab` assigns the same value, the reactive never fires) — precisely the 1 × 1 case here, where clicking either row would do nothing at all. Both rows also auto-activate their first tab on mount, so a naive handler would select whichever row mounted last. A strip that owns **one** selection across both rows is a dozen lines and has neither problem; it is also not focusable, so a tab click never steals the composer's focus.

**Selecting a tab is what the AGENT SLOT picker used to be**, plus the transcript. `_select_window` moves `_calibrating` (so "Set chat region..." and the service picker write into that window), repaints the whole sidebar column from that window's state, and displays its transcript panel. `F6` cycles the same funnel. What it pointedly does **not** touch is `_live`: looking at a window is not driving it, and a click here while a sub-agent is mid-run must not send the next paste into the master's chat.

**Slots — one drawn box per browser window.** Underneath the bar, the storage is unchanged: `_WINDOW_SLOTS` maps a window id to an `AgentSlot`, and that dict is the whole seam an N-window bar plugs into. A slot was six calibrations; it is now a single rectangle, because the two questions it conflated have different owners. *What does this thing look like?* (the stop button, the copy icon, both chat-box layouts, the new-chat control) is a property of the **service** — identical in every window it is ever opened in — so it lives in a `ServiceProfile` (`agentclip.driver.screen.profile`): captured once, persisted as PNGs, reloaded next run, shared by every window pointed at that service. *Where should I look for it?* is genuinely per window, and is all `SlotCalibration` (`agentclip.driver.screen.slot` — pure data, stdlib only, unit-tested without Textual) still holds: `chat_region`, one per `AgentSlot`.

The headline is the setup cost. **A sub-agent window costs exactly one drag** when it is on the same service as the master, because it inherits every capture already made; and a browser the user moved, resized or dragged to the other monitor costs one *re*-drag instead of six recaptures. Two independent pointers ride on top:

- `_calibrating` — the selected tab's slot: what the sidebar configures. Never locked by session state (the *service* picker is; the region button is not), because the user must be able to calibrate and watch the sub-agent window while the master chat is mid-turn. Both windows share the picker code, so the SUB-AGENT prompts are prefixed *"SUB-AGENT window · …"*.
- `_live` — which slot the automation drives right now (the focus click, the finish-detector poller, the auto-copy flow). Only `start_browser_chat` / `end_browser_chat` move it.

**A service per window.** Each tab carries its own key (`AutomationController.services`, read with `service_of(window)`), so the conversation the user steers can run on a big-context chat while delegated sub-tasks go to something cheap and fast. Consequently *"which preset / which appearances / how long is stillness / may I hover-scan?"* always names a slot, and mixing the two up is the bug the split exists to prevent:

- `_live_preset()` / `_live_profile()` — the window the automation is driving. The detector poller, the auto-copy flow, `_chatbox_region`, and every `_find_all` without an explicit slot read these.
- `_preset_for(slot)` / `_profile_for(slot)` — a named window. `AutomationController.click_profile_element(slot, kind)` and `start_browser_chat(slot)` use it, so a sub-agent's new-chat click is verified against the *sub-agent chat's* button even though `_live` has not moved yet.
- `_active_preset()` / `_active_profile()` — the selected tab, i.e. the sidebar's appearance summary and readiness note, and nothing the automation does.

Both keys leave the view exactly once, in `SessionSpec(task, service, subagent_service)` at bootstrap, because both pickers are locked for the session's life: the master's paste budget is baked into its Engine and the sub-agent tab's decided the delegate catalog. `SessionController` stores `subagent_service` and builds every sub-agent Engine from it (§3.4c). The starting values come from `[general] service` and `[general] subagent_service`, the latter blank-means-*the same as the master's* so the key is invisible to anyone running one service.

Readiness is therefore a function of the **pair** (window, that window's service profile), not a property of either half, so the rules are module-level functions taking `(cal, profile)`: `can_paste`, `can_finish`, `can_copy`, `can_delegate`, `missing`. `can_paste` and `can_finish` are the drawn window alone — the input box is found inside it, and a rectangle that stops changing *is* the staleness finish detector, so **one drag makes a window both pasteable and finishable**. `can_copy` adds `profile.has(COPY)`; `can_delegate` adds `profile.has(NEW_CHAT)` on top of all of it, and is asked against the **SUB tab's** profile: the buttons a run will click are the ones in the chat it is going to open, and the master tab having captured its own says nothing about them. It is strict on purpose: without all three pieces a sub-run would strand halfway. `missing()` returns the gaps in calibration order — `MISSING_CHAT_REGION`, `MISSING_COPY`, `MISSING_NEWCHAT` — which the sidebar shows in `#side-slot-note` and which the controller embeds in the error the *model* gets if it calls `delegate` against an uncalibrated host. Losing the window lists all three, which is honest rather than noisy: with nowhere to search, neither button can be found, and one drag closes all three gaps.

Because half the answer is the profile, the "sub-agent window ready" seam (`_after_calibration`) has to fire on **captures and service switches as well as region draws** — capturing a copy button, or re-pointing the sub-agent tab at a service that has none, flips delegation without any box being drawn. Since captures moved into the editor (§1.4) that half arrives through `MainScreen.update_config`, which drops the profile cache and re-runs `_after_calibration` for exactly this reason.

`start_browser_chat(slot)` is deliberately all-or-nothing: it *finds* the new-chat button inside that slot's chat region (`AutomationController.click_profile_element`, against that window's service), clicks where it actually is, and **only then** retargets `_live`, resets the finish trigger and restarts the poller. A `False` return guarantees nothing was clicked and nothing was retargeted, which is what lets the controller abort a delegation before its first paste — a sub-agent's bootstrap pasted into the master's chat would corrupt that conversation irrecoverably. `end_browser_chat()` is the mirror and is unconditional: it runs in the controller's `finally`, so it must work even after the sub-run blew up.

The sidebar's `#newchat-btn` clicks the same control through the same primitive and is otherwise its opposite: it drives the **selected** tab (`_calibrating`, decided once before the click), never moves `_live`, and on the master tab it ends the *session* rather than starting one — see §1.3 for the four cases. `/new` enters that same flow with the slot pinned to the master (§3.3a).

**One transcript per window, appended.** Each window's `TranscriptPanel` is mounted once and kept (`#chat-panels` shows exactly one); the master's keeps the pre-tabs id `#transcript`, so every existing selector still resolves. A delegation does not mint a pane: `open_session_view` appends a divider — `── task: <short title> ──` — and the run's transcript follows it, so the sub-agent window reads as one scroll of everything that ever ran in it, in order, with the divider marking where each sub-task began. `finish_session_view(session_id, note, ok)` adds its note and re-badges the tab `✓`/`✗`; nothing is removed or disabled, because the panels are output-only and the composer always targets the controller's *active* session. `ok` is a **parameter**, not something the view can infer: every ending — delivered, refused, over budget, aborted, crashed — arrives through the controller's one `finally`, so a view left to guess printed *"the result above was handed back"* directly under the error explaining that nothing ran, and badged the tab `✓`. The controller decides what happened (`_FINISHED_NOTE` / `_FAILED_NOTE`); the view decides what a failure looks like.

The load-bearing distinction is **focused panel ≠ selected tab**. `MainScreen.transcript` resolves to `_focused_panel`, which only `focus_session_view` moves; clicking a tab (or `F6`) moves what the user *sees* and what the sidebar configures, and nothing else. Without that split, a user reading the master's tab mid-delegation would silently divert the sub-agent's output into it, which looks exactly like data loss.

`render_log` is still **per run**, not per window: one `## sub-agent: <title> (<chat_name>)` heading over five unrelated sub-tasks is a wall, so `MainScreen._sub_runs` remembers each run's start and end index in the sub-agent panel's (unpruned) `event_log` and `TranscriptPanel.render_events(start, end)` slices them back apart. `/new` (`_remove_session_views` + `clear_transcript`) empties both transcripts and forgets the runs, and **keeps both tabs, both drawn rectangles and both services**: the browser windows have not gone anywhere.

**Who is talking.** During a sub-run every piece of state the controller pushes describes the sub-agent, so three places say so: the watcher status segment is rebadged `◆ SUB-AGENT · …` in magenta (`.st-sub`, a colour used nowhere else), the approval drawer's title gains a `SUB-AGENT ‹task title› · ` prefix, and every bell/toast is prefixed `sub-agent: `. The `SessionView` snapshot carries `session_id` / `session_role` / `session_title` for exactly this (additive, master-shaped defaults).

**Known limitation.** The tool catalog is baked into the bootstrap, so whether the model is offered `delegate` at all is decided once, at session start, from `can_delegate` against the sub-agent tab. Calibrating that window mid-session notifies *"sub-agent slot ready — /new to give the model the delegate tool"*; it cannot be retro-fitted into a conversation the model has already read.

### 1.7 Showing the user what the tool is looking at (sixel, half-blocks as fallback)

Everything the detectors do is invisible. A drawn region is a coordinate string, a captured appearance is *"40×40 · captured"*, and a calibration that caught the wrong pixels reports exactly what a good one does — right up until an automation that silently never matches. Two places therefore show the **picture**: the `ElementsPanel` column (`#elements`, §1.2) and the service editor's per-kind thumbnails (`#svc-tpl-preview-<kind>`, §1.4). Both draw sixel where the terminal can and half-blocks where it cannot, by the same rule and from the same one probe.

**The column shows the recognitions, not the scene.** Its predecessor drew the whole chat region as one 28×8 thumbnail at the bottom of the sidebar, which answered *is the box over my browser?* and nothing else. The question underneath that one is sharper — **is the tool recognising my send button, my stop icon, my copy button?** — and a wide shot of a window cannot answer it, because the icon that decides everything is four cells of it. So the column drops the wide shot and shows the **close-ups**: every time a template search verifies a match, the matched rectangle is cut out of *that* frame (`pixels.crop`, from the scene-local `RegionMatch` corner and the winning variant's size) and drawn beside the diff that verified it.

**One row per `TemplateKind` — all seven of them**, in `detector.RUNTIME_KINDS` order (`elements.ELEMENT_ORDER` *is* that tuple, so the order the detector reports in and the order the column lists in cannot drift): send button, busy icon, idle icon, copy button, both chat-box layouts, new-chat button. It listed four for a while, on the argument that the other three are found on demand by the click about to use them and so have nothing to say on a timer. That was the state machine deciding what the user is allowed to see, through the back door, and it cost exactly what it sounds like: a chat-box capture that had stopped matching stayed invisible until a paste landed in the wrong place. **Everything the tool can recognise gets a row, and the detector searches every calibrated kind every tick** (§3.4f). The sidebar's DETECTION block still gives verdict *lines* to the four the loop decides from — that block is the **words** about the decisions, this column is the **pictures** of the evidence, and the three extra rows are evidence nobody was deciding anything from. Seven rows of label-plus-picture outgrow most terminals, so the column scrolls (`overflow-y: auto`, like the sidebar) rather than dropping rows.

**The two chat boxes usually disagree, and that is the correct reading.** Only one layout is on screen at a time — a chat is either fresh or ongoing — so a fully calibrated service shows one of those rows *found* and the other *not on screen*. Two rows rather than one because they are two captures and either can rot; the miss is an answer, not a fault.

Three row states, and the difference between the last two is the point: **nothing has been searched yet** (`no match yet`), **searched and not on screen** (`not on screen`), and **found** (the crop, plus `found · 1.2%`). A row resting forever at "nothing yet" is indistinguishable from a detector that never finds anything, and "not on screen" is what explains a send gate that will not release or an auto-copy that never fires. Rows are a fixed height either way (a 2-cell label — name over verdict, because 17 cells of content will not hold both side by side — and a picture whose height is fixed for the session), so a match landing cannot make the column dance on a 0.5 s timer.

**How: sixel first.** Close-ups drawn as half-blocks were tried and rejected. Squeezing a 24×24 icon into a 16×6 cell budget is twelve pixel-rows of box average: it answers *is that squarish* and never *is that my copy button*, which is the only question the column has. **Sixel** hands the terminal the actual bitmap, so a matched send button is drawn at the size the screenshot has it, and `textual-image` + Pillow became runtime dependencies to get it. Half-blocks (`agentclip/shell/tui/pixels.py`, below) stay as the renderer for every terminal that cannot do sixel — which includes every headless test run, so both paths are live code rather than one path and one courtesy.

**The probe is the load-bearing part.** `textual_image.renderable` auto-detects support **in its module body**: it writes a DA1 query and reads the reply off stdin. Import it lazily — from a widget's `compose`, the obvious place — and Textual is already running its own stdin reader, which swallows the reply; the detection concludes *no sixel*, silently picks half-cell rendering, and the sixel widget you asked for draws blocks. That failure is invisible and was hit for real (the pixel-quality prototype). So `agentclip/shell/tui/graphics.py` owns one process-global verdict:

- `probe_terminal()` runs from **`cli.main`, before `app.run()`**, and nowhere else. It imports `textual_image.widget.sixel` (whose package `__init__` also queries, for the cell size) while terminal queries are still safe, asks `query_terminal_support()` itself, and caches `TerminalGraphics(sixel, cell_width, cell_height)`. Any failure at all — no textual-image, no stdout, a nonsense answer — yields `NO_SIXEL`; there is a working renderer behind it, so a bad probe costs pictures, never a launch.
- The panel composes **`textual_image.widget.sixel.Image` by name**, never `textual_image.widget.Image` — that alias *is* the auto-detection, resolved at import time. Sixel cannot go through an ordinary Rich renderable (Textual composites printable segments; sixel data is not printable), so the package's dedicated widget injects the escape sequence at `render_lines` time and moves the cursor itself. The service editor does the identical thing for its thumbnails (§1.4): one `terminal_graphics()` read in `__init__`, one widget class chosen per kind at compose time, both dimensions pinned inline because the row height there is `preview_rows` rather than the class rule's two.
- The column **says which renderer it is using** (`#elements-mode`: `crops · sixel` / `crops · half-block`). A sixel nobody can see and a detector that never matches look identical from the outside, and only the first has a fix — a terminal that supports it — that the user can act on.

**Scaling policy** (all of it pure, all of it in `shell/tui/graphics.py`, all of it pinned in `tests/shell/tui/test_graphics.py`): the crop is converted BGRX→RGB (`region_to_pil` — raw mode `BGRX` and **not** `BGRA`, because a capture's fourth byte is undefined and reading it as alpha makes every crop invisible), then fitted by `fit_pixels` into a box of `16 cells × cell_width` by `crop_rows(cell_height)` rows. Three cases: **bigger than the box** shrinks with Lanczos (an icon is thin strokes on a flat field; a nearest shrink eats them), **fits** is drawn 1:1 (the crisp true-size picture is the entire point, and any resampling is a downgrade), **under 20 px** doubles with NEAREST if the double still fits — and never more than 2×, past which it reads as a rendering bug rather than a picture of a screen. Finally `pad_to_box` centres the result on a **transparent** canvas of exactly the cell box's pixel size: exactly, because textual-image resizes whatever it is given to fill the styled cell box and the padding is what makes that second resize a no-op instead of a stretch off the aspect ratio; transparent, because the sixel encoder skips fully transparent pixels outright, so the padding is never drawn and the live theme's background shows through.

`crop_rows` derives the row height from a **pixel** budget (~56 px) divided by the terminal's real cell height, clamped to 2–8 rows, rather than from a fixed cell count: a cell is 16 px tall in one font and 24 in another, and what the row is reserving space for is an icon. It is fixed for the session, so the no-dancing rule above still holds.

**How: half-blocks, the fallback.** `agentclip/shell/tui/pixels.py` draws one terminal cell per **two vertically stacked pixels**: U+2580 UPPER HALF BLOCK, foreground = the top pixel, background = the bottom one. A cell is about twice as tall as it is wide, so that arrangement has roughly **square** pixels and an icon keeps its proportions instead of being squashed to a third of its height — which is also why `fit_cells(w, h, max_cols, max_rows)` halves the row budget and nothing else does. The budget is `ELEMENT_CROP_COLS × ELEMENT_CROP_ROWS` = 16×6 cells (the column is 20 wide, 17 of content, 16 once a scrollbar shows).

Five pure functions over `RegionImage`, no Textual anywhere in the module, so the sizing, the cutting, the averaging and the BGRX→RGB swap are pinned in unit tests (`tests/shell/tui/test_pixels.py`) rather than inferred from a rendered terminal: `fit_cells` (the aspect-preserving cell box, `(0, 0)` for "nothing to draw"), `crop` (the rectangle at `(x, y)`, **clamped** to the image — a match near an edge, a zero-size request and a truncated buffer all yield the part that exists, or an empty image, never an exception), `downsample` (box average to an exact pixel grid), `thumbnail` (`fit_cells` + `downsample`, `None` for "nothing to draw"), `half_block_text` (the grid → `rich.text.Text`, one styled run per cell in reading order).

**Averaged, not sampled.** An icon is mostly background with thin strokes on it; nearest-neighbour lands on the background almost every time and draws an empty rectangle. The average keeps the glyph visible as a shape, which is the actual *"yes, that is my copy button"* cue. The grid is capped at 4×4 source samples per output pixel.

**Where the match comes from.** One source: the **detector** (`agentclip/driver/screen/detector.py`, §3.4f), which searches for **every** appearance the live window's service has a picture of, on every tick. The column is therefore a live readout of what the tool can see at any moment, on a resting chat as much as mid-response — which is what it is *for*, and what it could not do while any row was gated on the automation's state (the send button was searched only inside the send gate's window, the copy button only inside the harvest, the chat boxes and new-chat button only by the clicks that use them, so those rows sat at `no match yet` for the life of a session). What is searched is a function of the profile alone, and there is no way to pass a gate, a flow or a loop phase into that decision.

The on-demand searches are untouched by this and stay where they are (`AutomationController.chatbox_region`, `click_profile_element`): a remembered location is up to half a poll interval old, so anything about to move the mouse re-searches a fresh capture of its own. Poll cost is unchanged in shape — one capture, one search pass, the same anchor-based search per kind — and the added kinds are three more template stacks on a 0.5 s timer.

`DetectionSnapshot.sightings` carries each searched kind's winning `(Template, RegionMatch)` pair as a `Sighting` — a match is only half an answer, since the match carries the corner and the variant that matched carries the size, and it takes both to cut the pixels back out. For busy and idle the pair comes from `PresenceTracker.last_sighting`, the spatial counterpart of `generating_now`: the one frame's own answer, cleared by a frame that does not contain the appearance, left alone by an ERROR (a dropped capture is not evidence that a button went away), and forgotten by `reset()`.

The **auto-copy flow** posts one crop of its own (`AutomationController.show_copy_crop`, right after `driver.automation.flow.lowest_match` answers and *before* the hover scan, because a hover-scan hit was verified against a frame taken with the pointer somewhere else and cutting it out of the static frame would draw whatever the icon was covering). That is no longer what keeps the copy row alive — it is the picture of the frame the click was actually **aimed at**, posted at the instant it was aimed, which is the one worth seeing when a click misses. The next poll tick replaces it with a picture of *now*.

**Which thread.** `pixels.crop` runs in the **poll worker that captured the frame**, never on the UI thread, and what crosses to the shell (`consume_elements` → `AutomationView.paint_elements` → the `PaintElements` message) carries an icon rather than a chat window. `elements.element_crop_image` then sizes the cut *for whichever renderer is live*, in that same worker: half-blocks get the exact cell grid they will draw (`thumbnail`), sixel gets the cut **untouched**, because drawing the pixels that matched at their real size is the entire point. Passing the full cut costs the queue nothing — a Textual message carries the object, not a copy — and the Pillow fit that follows on the UI thread is C-speed over an icon. `half_block_text` and `crop_picture` are both that cheap UI-thread half. The copy flow's one-shot is the single exception to worker-side cutting, and it is allowed because it cuts one icon-sized rectangle rather than a region. The cadence is every tick — the crops are tiny, and a picture of what is on screen *now* is the whole product — but a row showing the **same pixels it already shows is left alone**: a still icon cut out of frame after frame is the normal case, and textual-image's widget rebuilds its child every time it is handed an image, which is a clear and a redraw twice a second of something nobody could tell apart. The comparison is a bytes equality over an icon.

The crops mapping distinguishes all three row states outright: a kind mapped to a crop was found, a kind mapped to `None` was searched and missed, and a kind **absent from the map** was not searched at all this tick and its row is left exactly as it was. That third state now has exactly one cause — the live window's service is not calibrated for that kind — so a row resting at `no match yet` while the tool runs says something precise instead of something ambiguous: *nobody ever captured this*. That is true of **all seven rows**, busy and idle included: the finish-signal checklist decides what may end a response, never what is drawn here (§3.4d), so a captured stop icon whose signal is unticked has a row as live as any other. The column shows what button *would* be used if it were going to be used, whatever is currently switched on — which is the readout a user needs before they tick a signal, and the one the old checklist gating withheld from them exactly then. A tick whose capture failed posts nothing, because an empty map would blank rows a dropped frame is no evidence about.

**Deliberately not built:** a full-size viewer modal. `/identify`'s desktop overlay (§3.3a) already draws boxes on the real screen and stays up until dismissed, which is the high-fidelity answer; a second, worse copy of it inside a 20-cell column is not. Also not built: per-row `Collapsible`s. Textual 8.2 has the widget, but what a user reclaims by folding this column away is *horizontal* room for a diff, and seven collapsed rows give back none of it — so the toggle is the whole column (`F7`), mirroring `F3`. The vertical room they *would* give back is what the column's own scrollbar is for.

## 2. Approval flow state machine

### 2.1 Turn lifecycle

```
IDLE ──copy bootstrap──▶ ARMED ──reply parsed──▶ EXECUTING ──▶ COMPOSING ──▶ ARMED ...
                                                    │                          │
                                                    │ task_done                └─▶ CHUNKING (§6) ─▶ ARMED
                                                    ▼
                                                  DONE ──follow-up / undo──▶ ARMED   (non-terminal; summary on demand via e)
```

`EXECUTING` runs in a single async worker: `self.run_worker(self._run_turn(reply), exclusive=True, group="executor")`. Calls execute **strictly sequentially in the LLM's given order** (later calls assume earlier effects — edit-then-test).

### 2.2 Per-call classification

| Tool | Behavior |
|---|---|
| `read_file`, `list_dir`, `glob`, `grep` | whatever the rules say — the shipped defaults allow them (architecture §2); every tool answers to its permission key |
| `run_command` | auto-run if a rule allows it (transcript shows which: `allowed by rule bash["git status *"]`); a rule that DENIES it skips the gate entirely and returns a denied result; else **gated** |
| `write_file`, `edit_file` | **gated** by the shipped defaults, unless a rule allows it or session auto-accept-edits is ON |
| `ask_user` | pauses for typed answer (not an approval; §9) |
| `delegate` | auto-runs (master only, and only when the sub-agent chat is calibrated): parks the turn and runs a sub-agent in the second window — §3.4c. It answers to the `task` key like any other tool (the shipped default asks: a delegation is a second actor doing what the master would have been gated for) |
| `task_done` | auto-runs; ends the turn and marks the session complete (the user may still follow up to reopen it) |

YOLO (§2.6) overrides the whole table for the gated rows: when ON, every call an `ask` would have gated auto-runs instead — a rule `deny` and the deny-token backstop are the two things it does not answer. `/unattended` (§2.6b) overrides them the other way: the same rows become denied results, so nothing waits on a user who is not there.

### 2.3 The gate

When the executor hits a gated call it builds the renderable (diff for edits, the literal command line for commands), shows the ActionPanel, focuses `#action-body` (so arrows scroll the diff immediately), bells/notifies (§8), sets `pending_approval: reactive[bool] = reactive(False, bindings=True)`, and awaits an `asyncio.Future[Approval]`:

```python
async def _gate(self, call: ToolCall, body: RenderableType) -> Approval:
    self._approval_future = asyncio.get_running_loop().create_future()
    self.show_action_panel(call, body)
    self.pending_approval = True
    try:
        return await self._approval_future       # resolved by action_approve/reject/auto
    finally:
        self.pending_approval = False
```

Approval lives in the ActionPanel, **not** a ModalScreen: the user needs the transcript visible behind the diff for context, and `check_action` gating gives the same binding safety. (`push_screen_wait` + ModalScreen rejected for the main gate; it is used for the rarer Confirm dialogs where blocking is the point.)

Queue strip (`#queue-strip`) renders every call in the turn with status glyphs (BMP-only per the Windows brief): `✓` done, `✗` failed/rejected, `▶` current, `•` queued, `−` skipped.

### 2.4 Keys at the gate

- **`y`** — approve current call; executor resumes; gate closes (or moves to next gated call).
- **`a`** — enable auto-accept-all-edits for the session **and** approve the current call if it is a file write/edit. From idle, `a` toggles the mode off/on. Status bar shows `EDITS:auto` while ON. It is shorthand for one remembered rule (`edit["*"] = allow`), so it does **not** apply to commands — those stay whatever their own `bash` rules say.
- **`n`** — reject. The hidden `Input#reject-reason` appears in the action footer and takes focus, placeholder *"optional reason — enter to send, esc to cancel"*. `enter` (even empty) confirms rejection; `escape` cancels and returns to the pending gate. On rejection: **all remaining calls in the turn are skipped** (they presumed the rejected effect). The queue strip flips them to `−`. Rejected-but-continue was rejected as a mode: it produces incoherent state (tests run against unedited files) and costs an extra decision per call.

### 2.5 What goes back to the LLM

The results payload (composed immediately after the last call resolves) carries one entry per call with status `ok | error | rejected | skipped` plus the user's reason on the rejected one, e.g. conceptually:

```
call 2 edit_file → rejected: "wrong function — fix parse_date, not format_date"
call 3 run_command → skipped (turn aborted after rejection of call 2)
```

Exact wire grammar is the protocol designer's lane; the status enum + `user_note` field is a contract (§11). Errors during auto-run calls (file not found, command exit≠0) do **not** gate or abort: the result entry carries the error/output and execution continues — the LLM is the error handler.

### 2.6 YOLO mode (auto-approve everything)

`/yolo` (typed in the chat box) flips a session-scoped policy flag that answers **every** would-be gate with yes — edits *and* commands. A rule `deny` still denies and the deny-token backstop still gates. It is the bigger hammer above auto-accept-edits (`a`), which only covers edits. Use it for trusted/throwaway projects where the round-trip approval cost outweighs the risk.

- Toggle: bare `/yolo` flips it; `/yolo on` / `/yolo off` set it explicitly.
- Scope: the session. A new session (`/new`, or the summary's "new") resets it to the configured default (`[approval] yolo`, default `false`), and it never inherits into a sub-agent (`_adopt_ctx`).
- **No session gate**, `/mode`'s reasoning (§2.6a): "approve everything I am about to ask for" is a decision made about the task one is *about* to describe, so `/yolo` works at the start prompt too. With no engine there is nothing to audit into and no conversation to announce the change to, so only the controller's mirror moves — the toast says *"YOLO will be ON when the next session starts"* rather than pretending it is already in force, and the `EDITS` segment paints the armed value (`SessionController.yolo`) exactly as the `MODE` segment paints `permission_mode`. `_session_flow` then arms the engine it builds with the mirror before the bootstrap goes out — but only when it *diverges* from the configured default the engine already believes, so an untouched mirror writes no `yolo` event about a change nobody made.
- Mechanics: `ApprovalPolicy.verdict()` short-circuits to `auto` for edit/command kinds when `yolo` is set (read-only tools were already auto). The engine never builds a pending gate, so the turn runs end-to-end without a keypress. Audited per call as `auto: YOLO mode (auto-approve all)` and as a `yolo` session event on toggle.
- Indicator: the status bar `EDITS` segment becomes a red `⚡ YOLO` badge (`.st-yolo`) so gates-are-off is unmissable while the user is staring at the browser. (Wording note: "disarmed" is reserved for the §3.5 switch — YOLO turns *approvals* off, and the two are independent, so the badges never share a slot.)

This is deliberately a **runtime** toggle (not gated behind a confirm): it is opt-in by typing, reversible with `/yolo off`, and every change still lands in the per-turn backup store, so `undo` works as usual.

### 2.6a Permission modes (`shift+tab`)

The mode — `build` | `plan` — picks *which ruleset* is in force: `build` is the user's rules exactly as written, `plan` layers a built-in overlay denying everything that could change something. What each does to a verdict is architecture.md's lane. The UI half is two things: a key and a cell.

**The key.** `shift+tab` cycles `build → plan → build` (`MainScreen.action_cycle_permission_mode` → `SessionController.cycle_permission_mode()`, which does the engine call, the transcript note, the alert and the toast). One key rather than only `/mode` because the mode is the one policy a user changes *mid-glance* — they are watching a turn run, or watching the browser, and "stop changing things" is a thought that must not cost a trip to the chat box. `/mode [build|plan]` (§3.3a) stays the way to name one directly; bare `/mode` reports rather than cycles, so the two doors never disagree about what a press means.

Three deliberate choices about that binding:

- **`priority=True`, and it costs backwards focus navigation.** Textual's `Screen` binds `shift+tab` to `app.focus_previous`; the composer is a focused `TextArea` and would hand the key straight to it. Priority is the same trick `F3`/`F6`/`F7`/`F8`/`ctrl+x` already use here, but this is the first one that *overrides* a Textual default rather than merely outranking a widget. Accepted: the screen has a handful of focusables and plain `tab` still cycles them forwards, whereas a permission mode you cannot reach from the box you are typing in is a feature nobody uses.
- **Never gated.** Alone among the screen's shortcuts it has no `check_action` clause (it falls through to the default `True`), so it works with a gate up, mid-turn, while a sub-agent runs and while the app is DISARMED. The moment a user reaches for it is precisely the moment the app is busy doing the thing they want it to stop doing; a key that is dimmed exactly then is the wrong key. It is also `show=False` — the footer is already full of the loop's one-key answers, and the status segment is the discoverable half.
- **No session ⇒ it still works, and it arms the next one.** `set_permission_mode` is deliberately *not* gated on a live engine. "Only explore, do not change anything" is a decision a user makes about the task they are **about to type**, and a dial reachable only after the bootstrap had already gone out would be missing at the one moment it is easiest to mean. Pre-session only the engine half is skipped: the mirror moves, the transcript note and toast land, and the bar repaints (`#seg-mode` falls back to `SessionController.permission_mode` when there is no snapshot — §3.3). `SessionController._session_flow` then hands that mode to the engine it builds **before `start_task`**, so the first verdict of the first turn already obeys it; because the engine is still `IDLE` at that point it treats the mode as the one the session *started in* and arms no "the mode is now …" note for the model (architecture.md). `[approval] mode` is still where the default for a fresh app run is set.
- **It survives `/new`.** Alone among the session dials — YOLO goes back to its configured default on every reset — the mode is carried across `_reset_session` for the life of the app run, like the service picker. It describes the person, not the conversation: "I am only exploring today" is still true after a new chat, and a mode that silently reverted to `build` would hand the next session's first edit to a user who thought they had turned changes off. It is never a hidden state, because the segment shows both modes and never hides.
- **It governs every engine in the app run, sub-agents included** — the one place it diverges from YOLO, which stays per-engine (§5.7). A `delegate` call is never gated (it is AgentClip's own control flow), so a mode that stopped at the master would let a model in plan mode make every change it liked by delegating it, and would park an absent user's `unattended` session on a sub-agent's approval gate (§2.6b, which is scoped the same way and for the same reason). `_sub_run` therefore arms the sub-agent's engine with the dial before its bootstrap, exactly as `_session_flow` does for the master. Cycling *during* a delegation hits the sub-agent's engine immediately (it is the one holding the slot, and it is the conversation the user is watching); the master is re-armed on the way back out, and only if the mode actually moved — see §5.7.

**The cell** is `#seg-mode`, the status bar's leftmost segment — see §3.3 for the two renderings and why this one never hides.

What each mode looks like from the user's seat: `build` is the app as it has always been, running the rules the user wrote. In `plan` every edit, command, MCP call and delegation comes back as a **denied result** the model reads and works around — no gate opens, no keypress is needed, the turn runs to completion and the reply usually ends in a plan via `task_done`/`ask_user`; switching back to `build` is how that plan gets carried out. Reads, listings, globs, greps and skills are untouched by the overlay, and `agent.plan` in `permissions.json` is where a user buys individual commands back (the shipped file does it for `git status`/`git diff`). The help screen (`F1`) carries this same summary in prose.

### 2.6b Unattended (`/unattended`, the auto-deny toggle)

YOLO's mirror image, and deliberately **not** a mode: "I have stepped away from the PC" is a statement about the *user*, true whichever ruleset they are running. `/unattended [on|off]` (bare toggles) flips `ApprovalPolicy.unattended` through `Engine.set_unattended`, and everything that would have opened a gate becomes a `deny_unattended` result instead — the turn keeps running and finishes, so the user comes back to a completed turn and a list of what was blocked rather than to a question nobody answered. Allow rules still run; deny rules still deny.

- **Scoped like the mode, not like YOLO** (§2.6a's list, verbatim): it works with no session at all, it survives `/new`, and it reaches sub-agents — an absent user must not be parked on a sub-agent's gate either. `SessionController` owns the mirror (`unattended`, `set_unattended`, `_apply_unattended`) and arms every engine it builds with it.
- **YOLO wins where both are set** (architecture.md's verdict order), which is a real pair a user can produce, so the transcript note says so when unattended is switched on under YOLO rather than leaving them to find out from a diff.
- **Indicator**: a status segment of its own, `#seg-unattended`, a reverse-video amber `⚠ UNATTENDED` badge, hidden whenever the toggle is off. Its own slot rather than the `EDITS`/YOLO one for the reason `armed` has one: "everything auto-approves" and "everything auto-denies" can be true at once, and that is precisely the pair a user must never misread. Painted from `StatusSnapshot.unattended` while a session exists and from `SessionController.unattended` before one, exactly like the two beside it.

## 3. Clipboard watcher integration

### 3.1 Worker pattern

Started at session arm, per the research digest. **The sketch below is the SHAPE, not the current call graph**: the loop itself is `driver/clip/watcher.py::watch` (a plain thread-agnostic function), the thread that runs it belongs to `AutomationController.start_watching` / `stop_input`, the poll interval and the self-write register are the controller's (`_poll_interval_ms`, `SelfWriteSet`), and what reaches `MainScreen` is one `ClipboardCaptured` message.

```python
self.run_worker(self._clipboard_loop, thread=True, exclusive=True,
                group="clipwatch", exit_on_error=False)

def _clipboard_loop(self) -> None:                     # runs in thread
    worker = get_current_worker()
    while not worker.is_cancelled:
        time.sleep(self._interval)                     # 300 ms default
        text = self._provider.poll()                   # Win: seqnum shim → read only on change
        if text is None:
            continue
        seen = blake2b_hash(text)
        if seen == self._last_seen:                    # unchanged clipboard: not a new copy
            continue
        self._last_seen = seen                         # self-writes advance this baseline too
        if seen in self._self_written:
            continue
        if "===CLIP:" not in text:
            continue                                   # cheap pre-filter; 5 MB junk costs ~ms
        result = parse_reply(text)                     # parse in thread; it's pure CPU, fast
        self.post_message(ReplyCandidate(result))      # thread-safe per digest
```

Messages (all `textual.message.Message` subclasses, posted from the thread): `ReplyCandidate(parsed | ParseError)`, `WatcherStateChanged(state)`, `ClipboardFault(detail)`. All clipboard **writes** also route through this one thread via a small queue, per the digest's single-clipboard-thread recommendation; the write path records the payload hash into the self-write set *before* writing (suppresses self-detection race-free).

### 3.2 Self-write suppression and stale-reply guard

- **No reply dedup.** Per protocol §6.1 a paste is eligible on two preconditions only — the clipboard changed (the watcher's byte-level `last_seen`) and the chat name matches — so re-copying a reply the engine already ran *re-runs* it, deliberately. The only hash suppression is of AgentClip's **own** outbound (`AutomationController.self_writes`, a `driver.clip.watcher.SelfWriteSet` — the controller holds the provider, so one object is both the watcher's filter and the writer's register; §3.1), which the engine mirrors as `Noise("own-outbound")`.
- Reply arriving while `EXECUTING`: queued (depth 1, newest wins), status segment shows `+1 queued`, toast warns. Processed when the turn composes its results.

### 3.3 Status bar (the "armed/ingested/waiting" indicator)

Eleven `Static` segments, words not emoji, colored via CSS classes, driven by reactives (four of them hide themselves when they have nothing to say):

```
MODE:build │ ● ARMED │ ChatGPT 4.0k │ out 3.4k/4.0k (1/1) │ turn 5 │ EDITS:auto │ ~\Dev\AgentClip
MODE:plan  │ ● ready │ ⛔ DISARMED │ ChatGPT 4.0k │ out 3.4k/4.0k (1/1) │ turn 5 │ ⚡ YOLO │ ⚠ UNATTENDED │ ~\Dev\AgentClip
```

`#seg-mode` is **first** — left of even the watcher — and never hides. It is the permission mode (§2.6a): `MODE:build` dim (`.st-dim`), `MODE:plan` blue-bold (`.st-plan`, the `$accent` the app already borders with). Neither is red, because red is spoken for by the two badges that mean *approvals are off* (`⚡ YOLO`) and *the OS switch is out* (`⛔ DISARMED`). Unlike `#seg-armed` this one shows in **both** states rather than only the constraining one: `shift+tab` (§2.6a) is a blind cycle with no other feedback once the toast has gone, so a segment that disappeared in `build` would leave the user unable to read the answer to "which mode am I in?" off the bar. Leftmost because it is the widest-scoped fact on the row — it governs what may happen to the project at all, while everything to its right describes one session's progress. It is painted from `StatusSnapshot.mode` while a session exists (during a delegation that is the **sub-agent's** engine, like every other field here — which reads the same, since the mode governs every engine in the run, §2.6a), and from `SessionController.permission_mode` before one — which is a live setting, not a read-only preview: `shift+tab` and `/mode` both work at the start prompt and between sessions, and whatever the segment reads there is the mode the next session is armed with (§2.6a).

`#seg-armed` (third) is empty and **hidden** whenever the app is armed, which is nearly always — the badge is an alarm, so it may not become furniture the eye stops reading. It is its own slot rather than a share of the `EDITS`/YOLO one because both can be true at once, and a disarmed YOLO session is exactly the pair a user has to be able to see. See §3.5.

Watcher segment states as implemented (`_base_watch_segment`, main.py — precedence order): `✓ done - reply to continue` (`.st-done`), `■ APPROVE NEEDED` / `■ ANSWER NEEDED` (`.st-attn`), `○ idle` while `awaiting_new_session` (see below), `● working...` (`.st-busy`), `✗ manual paste` (`.st-err`, manual provider), `○ paused` (`.st-dim`), `● ready - paste the reply` (`.st-armed`), else `○ idle`. During a delegated run the whole segment rebadges `◆ SUB-AGENT · …` magenta (`.st-sub`). A `◍ PART k/n` state arrives with the chunk wizard (§6, unimplemented).

While `MainScreen.awaiting_new_session` is set — the launch screen and every `/new` (§1.3) — the segment reads `○ idle` even though `SessionController._busy` is technically `True` the whole time (the session worker is parked on the inline "describe the task" prompt, §3.3's controller-side twin). There is no turn in flight, so `● working...` would be a lie the user has no way to resolve; `_base_watch_segment` checks `awaiting_new_session` ahead of `busy` for exactly that reason. Nothing pushes a repaint while parked there (`render_state` never runs mid-wait), so `prompt_new_session` calls `_paint_status()` by hand on both the way in and the way out.

`#seg-instr` (seventh, next to `EDITS`) reads `✎ INSTR` while the extra-instructions re-inject is armed (§3.4h) and **hides** otherwise, for `#seg-armed`'s reason — it is true only between the `r` press and the payload that spends it, usually seconds, and a permanently present "not armed" cell would be furniture. It sits beside `EDITS` because both describe what the *next* thing out of here will carry. Painted from `StatusSnapshot.instructions_armed`.

The `EDITS` segment shows `EDITS:ask` (default), `EDITS:auto` (auto-accept-edits ON), or a red `⚡ YOLO` badge (`.st-yolo`) when YOLO mode (§2.6) is armed — YOLO takes display priority over `EDITS:auto`. Like `#seg-mode` it is painted from `StatusSnapshot` while a session exists and from the controller's mirror (`SessionController.yolo`) before one, so a `/yolo` thrown at the start prompt is visible immediately rather than only once the session it governs has begun.

`#seg-unattended` (right of `EDITS`) is the auto-deny toggle's badge, a reverse-video amber `⚠ UNATTENDED` (§2.6b), **hidden** whenever the toggle is off — `#seg-armed`'s rule. Its own slot rather than a share of the `EDITS`/YOLO one for `#seg-armed`'s reason as well: both can be on at once, and "everything auto-approves" beside "everything auto-denies" is the one pair a user must never misread. Same two sources as its neighbours: `StatusSnapshot.unattended`, falling back to `SessionController.unattended` before a session exists.

`#seg-mcp` (ninth, against the root) reads `mcp 2/3` — connected MCP servers over enabled ones, disabled config entries out of both numbers — and **hides** whenever the app has no MCP manager (docs/design/mcp.md §6), which is most installs: an `mcp 0/0` cell would be furniture on every one of them, `#seg-armed`'s rule. It sits at the far right with the project root because, like the root, it is a fact about the *app run* rather than this session's turn — one manager per process, sessions come and go under it. Painted from `McpManager.statuses()` inside `_paint_status` (so every ordinary repaint keeps it honest) and repainted on every `McpStatusChanged` message the status-hook bridge posts (§1.3's MCP block has the bridge story).

### 3.3a Chat commands

The chat box also accepts slash commands (parsed in `SessionController.submit_message`, so any future front-end inherits them; an unknown `/command` is reported, not sent to the model):

In registry order, which is also popup order (see **Ordering** below):

- `/help` — list the commands in the transcript. Aliases `/commands` and `/?` dispatch here but are never offered by the popup below — one obvious spelling per command.
- `/new` — open a fresh browser chat, then clear the transcript and start a fresh session in it (re-arms the inline start flow of §1.3; the service picker unlocks so the next session can use a different preset). Reachable from **every** state, including mid-turn (a turn in flight is aborted for it rather than blocking it) and with no session at all: AgentClip having nothing to replace says nothing about the chat on screen, and the start screen is exactly where a user asks for a page that is not still full of the last run — the click is attempted, and there is simply no tool half to renew behind it. Never refused. ("no active session to replace" survives only on `request_new_session`, the sidebar button's door, whose caller needs to know whether a session is coming.) The browser click happens **at command time** — see below.

**`/new` is the "New browser chat" button, typed.** A new session in the *old* conversation is half a reset: the model reads the previous task's history above whatever is pasted next. So `/new` — and **only** `/new` — asks the view for a fresh browser chat through the port (`ChatView.open_new_chat_now()`), and the view runs the very flow the sidebar button runs (`MainScreen._new_browser_chat(slot)`, §1.3): find `TemplateKind.NEW_CHAT` inside the window's chat region (`AutomationController.click_profile_element`, the same find-then-click every programmatic click goes through, §3.4a), click where it actually is, hand focus back, and call `SessionController.request_new_session()` for the tool-side half. One implementation, two ways to reach it, so the two cannot drift apart.

Five rules:

- **It happens now, not at the next paste.** The command *is* the moment the user abandoned the conversation; a click deferred to the first paste would leave the tool started over while the old chat is still on screen, and every recovery in between (a manual Ctrl+V, `/copy`) would land in the wrong one.
- **The MASTER window, not the selected tab.** The sidebar button drives `_calibrating` so either window can be tested from where the sidebar points; `/new` is typed into the *master's* session, so it is pinned to `AgentSlot.MASTER` and the tab the user last clicked cannot redirect it.
- **Only `/new`.** The launch has no stale conversation behind it (clicking new-chat there would sweep away a tab the user had already set up), the summary screen's *new session* follows a wrap-up the user just read, and the budget-exceeded retry is the same session trying again. All three reach `_reset_session` too; none of them touches the browser.
- **The click is best-effort; the fresh session is not.** A new conversation has two halves, and they are not equally available to AgentClip. The tool side — new engine, new chat name, empty transcript — it can always deliver. The browser side needs a drawn window, a captured button, that button on screen exactly once, an armed switch and an OS that accepts synthetic input; any one of those missing and there is nothing to click, because clicking blind into a browser window is never the answer. This rule used to be *a refused click resets nothing*, on the reasoning that a session reset behind a chat still full of the old conversation is the half-reset `/new` exists to prevent. That reasoning had the failure mode backwards. The states where the click fails are precisely the states a user reaches for `/new` in — a window that moved, a service never calibrated, the switch off after something went wrong on screen — and in every one of them the command answered by doing *nothing at all*, leaving the user with an old session, an old chat, and a toast about a button. So every `ElementClick` failure now runs the reset anyway and spends its toast on the two things the user needs: which of the five reasons the browser was not touched, and that opening the fresh chat is now theirs to do (*"the new-chat button is not on screen in the chat window — nothing was clicked; recapture it or redraw the window. AgentClip is on a fresh session anyway — open a new browser chat yourself"*). The half-reset is still real; it is just the user's to close, and a sentence they can act on beats a refusal they cannot. Where there is no tool side to renew — the sub-agent tab, or no session running — the toast says that instead, because a "fresh session" it did not start would be the one lie that makes the rest untrustworthy.

- **A turn in flight is aborted, not a reason to refuse.** `/new` used to be refused whenever `busy` was up, which meant the one escape from a conversation that had gone wrong sat behind the very turn the user wanted out of — a model looping on a gate, a delegation that will never answer, an `execute()` grinding on a command nobody wants. A turn cannot be interrupted from outside, though: it is parked on one of three futures, or inside `execute()` on a worker thread, or in the few lines between two of those. So `request_new_session()` latches `_turn_aborting`, spawns `_abort_then_reset()`, and that: (1) drops any queued capture, (2) raises `_SubagentAborted` into a delegated run's reply future — the exception `_run_subagent` already knows how to end a run with, so the sub tab is finalized and the master's context restored exactly as `/abort` leaves them, (3) raises `_TurnAborted` into the ask_user future and the gate future, (4) calls `Engine.request_cancel()` if a step is executing (thread-safe by design, so it can be called from the loop mid-`execute`), and (5) waits on `_flow_idle` for the flow coroutine to unwind before the reset tears down the engine it is still holding. A flow caught *between* parks is covered by `_check_turn_abort()` checkpoints — the top of `_handle_step` and of each of its loop iterations, `_gate`, `_ask`, `_run_engine_step`, and the pending-gate loop — which raise `_TurnAborted` for it. The `_handle_step` checkpoint is the load-bearing one: it is what stops a `Send` step from copying the aborted turn's outbound onto the clipboard for a chat that no longer exists. `_wrap_flow` swallows `_TurnAborted` silently (the new-chat path owns the messaging), every park's own `finally` clears its flag on the way out, and `_turn_aborting` guards every other flow-spawning door (`submit_clipboard`, follow-ups, `undo`, `force_ingest`, `end_session`) so nothing slips into the flow slot in the gap. Not abortable, and not reachable either: a flow parked on a *modal* (undo's confirm, the summary, the paste prompt) holds the screen, so neither the command nor the button can be pressed while one is up.

Every outcome is a toast (*"new browser chat opened"*, or the reason it was not plus whose job the chat now is), which is the whole of its UI: the control is found on demand rather than polled, so there is no verdict worth keeping on screen between presses.
- `/abort` — end the delegated sub-agent run in flight (§3.4c). A no-op with a warning when nothing is delegated.
- `/identify` — draw labelled boxes on the real screen, one per part of the live chat window the tool can find (see below).
- `/log` — show the harness decision log: every loop-state move, with the reason it was made (§3.3b). **No session gate**, for `/identify`'s reason. It sits between `/identify` and `/armed`, the three "what is this thing doing to my screen, and why" commands together, and well clear of both ends of the list.
- `/mcp` — list every configured MCP server into the transcript: state, tool count when connected, and the full detail line the sidebar's 30-cell block had to cut (docs/design/mcp.md §6). **No session gate**, `/log`'s reasoning: "why does the model not have my server's tools?" is asked before a session as readily as during one, and the manager is process-wide. When the app runs without a manager it answers with a toast — *"MCP is not configured"* — rather than an empty listing. The controller stays MCP-agnostic (layering): it holds a supplier of duck-typed status rows (`SessionController(mcp_statuses=…)`, the TUI passes `McpManager.statuses` bound), `None` meaning unconfigured.
- `/skills` — list the loaded skills into the transcript, one row each: name, description, and the folder the `SKILL.md` was loaded from, with `[hidden from the model]` on any that set `disable-model-invocation`. Found nothing? The answer is the folders it searched, which is the only actionable half of "no skills". **No session gate**, `/log`'s reasoning — "why is my skill not being used?" is asked before a run as readily as during one, and the answer is routinely that its folder was never one of the six. Sourced exactly like `/mcp`: a live session answers off the LINK (skills are discovered where the engine runs, so a remote session lists the target's folders — remote-ssh.md decision 6) and a session-less app off the supplier the controller was built with (`SessionController(skills=…)`, duck-typed rows, so the layer stays clear of `executor.tools`). Bodies never travel; the model still pulls those one at a time through the `skill` tool.
- `/armed [on|off]` — the global ARMED switch (§3.5), same as `F5`; bare toggles. **No session gate**, for `/identify`'s reason one step sharper: the moments a user wants the automation stopped are the moments something is going wrong on their screen, and a gate would lock the switch away in exactly those. No engine involvement either — the flag is the view's, so this is one port call (`ChatView.set_os_armed`) and nothing else. It sits next to `/identify` in the registry (the two "what is this thing doing to my screen" commands) and ahead of `/yolo`, which stays last.

**`/identify` shows the recognition model its own answer.** Everything the automation does is one operation — *find this captured appearance inside that drawn rectangle* (§3.4a) — and until this command the only report of it was the consequence: a paste in the wrong box, a copy that never fired, a delegation that would not arm. There was no way to ask what was actually matched, or where. So `/identify` captures the **live** window's chat region once, runs every `TemplateKind` the live service has captured over that one frame (`driver/screen/identify.py::identify_elements` — a pure function of a rectangle, a profile and a frame, unit-tested against hand-built scenes), and throws a read-only translucent overlay over the desktop with one outlined rectangle per find. The chat region itself is always the first box, because half of what goes wrong is the box being somewhere unexpected, and a list of buttons inside an invisible rectangle is unreadable. Dismissing the overlay is what produces the summary toast (*"identified 4 elements: copy×3, new-chat×1"*, or the explanation when nothing matched) — the `subprocess.run` is blocking, so the toast is the parent resuming, not a second notification.

**Badges on the boxes, the words in a legend.** Each box used to carry its full description (`copy 0.013`) at its top-left corner, which read fine until the case the command exists for: several matches of one appearance land on one physical element, the boxes sit a few pixels apart, and the labels print through each other into a smear — over exactly the button the user was trying to inspect. So the box now carries a **badge** only — `#1`, `#2`, … over the finds in list order, `#R` for the drawn chat region (not a number, matching the toast's count, which excludes the container the user drew) — and a **legend block in the top-right corner of the overlay** spells each badge out with its label and diff, one row per element in that element's own colour. Three things follow from where the legend is:

- **On the overlay, not in the TUI.** The overlay is fullscreen, topmost and translucent over the whole virtual desktop; a legend in the transcript would be underneath it precisely while the user is reading the boxes. The child process also has no channel back to the TUI — one JSON payload in on stdin, nothing out — so a live legend there would need a wire the feature does not have.
- **Top-right, below the prompt's line.** `IDENTIFY_PROMPT` is centred at the top; the legend starts clear of it vertically, so the two cannot collide on a narrow desktop.
- **With a backdrop.** The window is translucent by design (the boxes only mean anything against the browser underneath), so the legend gets a filled dark rectangle behind it — slid *under* the rows after they are laid out, since the block's size is whatever the longest label came out as.

Badges are short enough that overlapping boxes stay readable, and where two boxes are so close that even the badges would stack, each later badge steps sideways by one badge width until it clears the ones already placed. The numbering, the shared-per-label colour and that nudge are a pure function of the element list (`driver/screen/overlay.py::_identify_labels` → `IdentifyLabel` rows, unit-tested with no tkinter anywhere near it); the drawing is `create_text` over its output.

Five rules, and each one is a mistake the obvious implementation makes:

- **Capture first, overlay second.** The frame is taken before anything is drawn. An overlay in the capture would be identified as part of the chat window.
- **The live window, not the selected tab.** What is boxed has to be what the automation would act on, so mid-delegation this identifies the sub-agent's chat while the user reads the master's transcript.
- **Duplicates fold per kind, never across kinds.** A template matches its own element at several neighbouring origins, and a stack of boxes a pixel apart is unreadable — so the same `same_element` fold the automation uses to count windows (`driver/screen/template.py`, shared with `MainScreen._find_all`) runs per kind. Across kinds nothing folds: one picture captured under two kinds is a calibration mistake worth *seeing*.
- **No session gate.** The only command without one. It is a calibration aid, it cannot affect a run (one capture, one picture), and the states it is most needed in are exactly the ones a gate would lock it out of. It refuses on one thing only: no chat region drawn for the live window, which is a toast and no overlay — there is nowhere to look.
- **Same child process, same bracket as the picker.** tkinter cannot share the TUI's process, so this is a second hidden CLI flag (`--show-identify`, `driver/screen/picker.py::draw_identify_overlay`) with the element list as JSON on the child's **stdin** — a profile's worth of rectangles is well past what a command line should carry, and the picker child already established stdout as the direction results come back in. The detectors are suspended around it for the reason in §3.4e, and the overlay dismisses on any click and on any key — and on **nothing else**. It is a picture the user asked for, so it stays up until they are done reading it; neither the child nor the parent runs a clock (an earlier ~10 s self-destruct, with a 60 s cap on the parent's `subprocess.run`, took the answer away mid-read). The cost is that the detectors stay suspended, and the `regionpick` worker slot stays taken, for as long as the overlay is up — both are exactly what "the user is looking at their screen, not at the automation" should mean.

- `/yolo [on|off]` — toggle YOLO mode (§2.6).

- `/mode [build|plan]` — set the permission mode (§2.6a). Bare `/mode` **reports** rather than cycles: a command naming a state must not require the user to remember which one they are in to reach the one they want — cycling is `shift+tab`'s job, where blind stepping is the point.
- `/unattended [on|off]` — the auto-deny toggle (§2.6b); bare `/unattended` flips it. A toggle rather than a report, unlike `/mode`: "is anyone watching" is one bit the user is either setting or clearing, and they always know which way they meant it. Second-to-last in the registry, directly above `/yolo`: it belongs with the other command that answers gates without asking, but it only ever refuses, so it sits above the one that approves.

- `/theme [name]` — set the appearance; bare `/theme` **lists** the themes and marks the current one, as a transcript note (`/help`'s shape — a list is worth keeping, and a toast is gone in eight seconds). The same setting F4's SettingsScreen picks, sharing its list and its save path (`AgentClipApp.remember_theme`), so the command cannot set something the picker will not show. **No session gate**, `/armed`'s reasoning minus the urgency: appearance belongs to the machine the user is sitting at, not to a conversation. It sits next to `/mode` and ahead of `/yolo`, which stays last. Which names exist is the **view's** answer, not the controller's (`ChatView.theme_choices` / `current_theme` / `apply_theme`): the TUI wears four Textual themes persisted as `[general] theme`, the GUI two CSS palettes persisted as `[gui] theme`, and neither vocabulary is valid in the other's table (docs/design/gui.md §3). The controller therefore never holds a theme name it did not first read back from the view, and an unrecognised one changes nothing and says so — `/armed`'s rule that a typo is never read as an instruction. `apply_theme` both applies and persists, and is silent: the controller raises the one toast (*"theme: claude-dark"*), so `/theme x` says one thing once in both shells, while F4's picker keeps its own *"theme saved"* because the click itself said nothing.

- `/config [global|local|global reset|local reset]` — where the permission + MCP ruleset lives, a way to start one, and the way back out of one. Bare `/config` **reports** both layers (`/mode`'s rule: a command naming two things must not make the user guess which one they are in) with whether each file exists; `/config global` and `/config local` create the missing file with the shipped defaults spelled out (`DEFAULT_CONFIG` plus an empty `mcp` block — the rules that were already in force, so creating it changes nothing) and put its path on the clipboard through `park_outbound` — the one clipboard write the watcher is told about before it lands, so the path can never come back in as a pasted reply. `/config global reset` and `/config local reset` write that same document *over* the layer's file, keeping only its top-level `"mcp"` block: a permissions reset must not cost a user their configured MCP servers, and a file that does not parse as JSON has no block to keep and is replaced outright — it is exactly the file this branch exists to get out of. The reset parks nothing on the clipboard (the answer is what the file now says, not where it is) and says the restart note again, which bites hardest here. **No session gate**, `/theme`'s reasoning: a ruleset is a property of a machine and a project, and the moment a user reaches for it is usually the moment a gate has just asked them something they would rather have answered once, in a file, before starting. Every answer says the file is read **once at launch**, because it is (`cli.main` builds one `Config` per process) and a user who believed otherwise would think their rule was ignored. An argument that is neither word acts on nothing — `/armed`'s rule that a typo is never read as an instruction, which bites harder here because the acting branch writes a file. In a **remote session** `/config local` refuses and says so: the project is on the target and this shell writes on this PC, so it would create a ruleset nobody reads beside a project that is not here.

**One registry.** The list above is data, not prose repeated per consumer: `shell/app/commands.py` holds a frozen `ChatCommand` (name, arg hint, one-line summary, aliases) per entry, and the controller's dispatch table, the `/help` note, the "unknown command — try `/help`, `/new`, `/abort`, `/identify`, `/log`, `/mcp`, `/armed`, `/mode`, `/theme`, `/config`, `/unattended`, or `/yolo`" hint, the F1 help screen's command section and the autocomplete popup all render from that one tuple. `SessionController._command_handlers()` is the join between a registry name and what it does, and a test pins the two sets equal, so a command cannot ship as an undiscoverable row (or a hidden feature). It sits in `shell/app`, not `shell/tui`, because the dispatch does — plain string work, no Textual import, which is exactly what lets a `tui` widget read the same table.

**Ordering is a safety property.** The popup lists the tuple as written, so whatever sits at the top is what a stray keystroke is nearest to — and `/yolo` disables every approval gate in the app. It is therefore **last**, behind the harmless and the reversible, with `/help` first because it is what a lost user is reaching for. Together with the no-preselect rule below, that is two independent locks on the same door: nothing destructive is at the top of the list, *and* the top of the list is not reachable without an explicit choice.

Precedence: while answering an `ask_user` question, the typed text is **always** the answer (commands are not parsed) — so a slash-leading answer like `/etc/hosts` is delivered verbatim, never eaten. That is the *only* mode where a slash is not a command: the "Describe the task" prompt parses them like any other send (§1.3), because the state with nothing armed is where `/identify` is worth most and a prompt that ate it would post it to the model. A message — or a task — that must begin with a literal slash is escaped as `//…` (one slash is stripped and the rest sent as text).

**Autocomplete (`CommandPopup`, §1.2).** Commands are otherwise findable only by already knowing `/help` exists, so a compact list pops up **directly above the composer** the moment one is being typed, and narrows with every character.

- *Trigger* (`commands.match_prefix`, shared with the dispatcher so the two cannot drift): the box's text is a single bare token starting with exactly one slash. `/` offers everything; `/y` narrows to `/yolo`; `/yolo` still matches itself. Each of the three ways a line stops being a command in progress closes the popup on its own — `//escaped` is the literal-slash hatch, `/yolo ` has committed and is typing its argument, and `/xyz` matches nothing. Deleting the slash closes it too.
- *Nothing is pre-selected until the user narrows the list.* A bare `/` shows every command with **no** highlight; one typed letter (which filters) or one arrow press arms a row. This is a safety rule, not a cosmetic one: with the top row always highlighted, `/` + `Enter` + `Enter` *ran* `COMMANDS[0]` — two keystrokes past a character typed by accident, at a box whose whole job is sending text. The composer decides it (`preselect=len(text) > 1`) because it is the only thing that knows what was typed; the popup keeps `index = None` and answers `highlighted = None`.
- *Keys*, intercepted by `ChatComposer` and **only** while the popup is up; every other key keeps editing (and re-filters the list underneath):
  - `↑`/`↓` move the highlight, wrapping at both ends; from *no* highlight, `↓` arms the first row and `↑` the last — exactly where wrapping from either edge would have landed.
  - `Enter` or `Tab` **complete**: the highlighted command replaces the line as `/name ` — with the trailing space where its argument goes. Enter does *not* send here; because the trailing space closes the popup, the **next** Enter is an ordinary send. `Tab` does not move focus. With no row highlighted there is nothing to complete, and the key is still swallowed — so a bare slash can neither run a command nor be sent as a message; it simply waits to be narrowed.
  - `Esc` dismisses the list and touches neither the text nor the focus — it is the **first** thing `Esc` means, ahead of both of the composer's own stages (§3.3c).
- *Focus* never moves: the popup is a `Static` painting one Rich `Text` and is driven entirely by method calls from the composer, so it cannot steal focus from the box — or from the Approve button at a gate, where a disabled composer closes it anyway. One command is always exactly one row (`text-wrap: nowrap; text-overflow: ellipsis` — a summary wider than the chat column is cut), so the popup's height is its match count and the highlight lines up with what it points at; a wrapped row would push the last command out from under `max-height` instead.
- *Suppression.* No popup while the box's next send is consumed **verbatim**, because a leading slash there is text and offering to complete it would misrepresent what Enter does. That is exactly one mode, and it is already-known state rather than a new signal: `awaiting_answer` from the `SessionView` push (the `ask_user` gate above). The task prompt (`MainScreen.awaiting_new_session`, §1.3) is *not* one of them any more — Enter dispatches commands there, so the popup tells the truth about what Enter will do. `_update_composer` hands the flag to the composer alongside the enable/disable decision, and a disabled box never shows a popup either.

### 3.3b The harness decision log (`/log`, `F8`)

The STATE rail (§1.3) says **where** the browser-automation loop is; this says **how it got there**. They are different questions and the second is the one a stuck user actually has: the rail draws one `MANUAL_COPY` box for four different roads into it — the tool is disarmed, the service captured no copy button, the button was not found on screen, the click did not take — and until now the difference lived in a toast that was gone in eight seconds, or nowhere at all. `/log` (`ChatView.toggle_harness_log` → `MainScreen.toggle_harness_log` → `HarnessLogPane`) is where those reasons survive.

Six rules, and each one is a decision rather than a default:

- **One writer, and it demands a reason.** `AutomationController.set_loop_state(state, reason)` is the sole writer of `LoopState` (§1.3) and the reason is a required argument, so a transition cannot reach the rail without reaching the log. Everything else appends through one small helper (`log_harness(kind, text)`), which is where the timestamp and the bound are decided. Entries carry a `kind` — `state`, `gate`, `trigger`, `copy`, `clipboard`, `session`, `armed` — printed as a column so the eye finds one kind in a wall of another with no styling at all.
- **The reasons are lifted, never invented.** Each one is the prose the code already had at that decision: the toast it raises, the branch comment above it, the sentence in the docstring that explains the rule. `time_out_send_gate`'s existing "the ready-to-send button never went away after the paste" is the model — the log prints the same sentence the toast made, so the user who dismissed the toast can still find out what happened, and there is no second wording to drift.
- **Bounded, in memory, never written to disk.** A `deque(maxlen=500)` — the same number `TranscriptPanel` prunes to. This is a debugging tail, not an archive, and keeping a record of what the tool did to somebody's screen out of the filesystem is the conservative default; the transcript's export-on-demand pattern is the door if that changes.
- **It survives `/new`.** A wedged user's first move is often to reset the session, and clearing the log there would destroy the evidence they are about to go looking for. The reset appends its own entry instead — worded as a *reset*, not as a transition, matching `LOOP_TRANSITIONS`' own distinction — and that line is the boundary marker. It does not name `/new`, because the summary screen's *new session* and the budget-exceeded retry reach the same teardown, and naming a command the user did not type is exactly the kind of lie this feature exists to stop telling. The session start/end boundaries are logged too, since half the other entries mean something different on either side of one.
- **UI thread only, so no lock.** Every append site is on the event loop: the poller's worker threads reach the screen through `post_message` (§3.4e) and the async flows log after their awaits return, so the deque is never touched concurrently.
- **It is a live pane, not a modal.** This deliberately overturns the first shipped design, which pushed a `LogScreen` holding a *snapshot* on the grounds that a log reflowing under a reader would move the line they are halfway through. That was right about the hazard and wrong about the fix. The moment a user asks *why did it do that?* is routinely the moment it is still doing it — a send gate that will not release, an auto-copy that fires on nothing — and a modal you must close, re-open and re-scroll to see the next entry cannot be used to watch a loop. So the log is now a strip along the bottom of the main screen, and the hazard is answered directly (below).

**The pane** (`shell/tui/widgets/log_pane.py`, a `RichLog`):

- **Full width, between `#body` and the StatusBar.** A sibling in the screen's vertical layout, not a fourth column and not a drawer inside the chat column: an entry is ~120 cells of timestamp, kind and reason, and only the whole terminal is wide enough for one. `height: 30%; min-height: 6; max-height: 14` — a share of the terminal because what it costs is the transcript above it, capped because past a dozen rows it has stopped being a tail and become the screen. One entry is one **line** (`wrap: off`); a line wider than the pane scrolls sideways rather than reflowing, because the printed form is a column layout (time, kind, sentence — the first rule above) and a wrapped sentence breaks the column the eye scans.
- **Toggled, never rebuilt.** Mounted for good, `display: none` in CSS, flipped by `/log` **and** `F8` — which are the same call, not parallel implementations. `F8` is a `priority` binding for `F3`/`F7`'s reason (the composer is a focused `TextArea` and would eat it); it is `show=False` because the footer is full and `/log` is how the feature is discovered. Typing `/log` again puts it away, and the controller does not track which way it went — it says "show it" and stops, as it does for `/identify`.
- **Follow, and freeze, as a property rather than a mode.** Every append asks `is_vertical_scroll_end` *before* writing: at the tail, the write scrolls to the new entry; scrolled up, it does not, so the line being read does not move and the entry lands below the fold. Scrolling back down (or `End`, the native `ScrollableContainer` binding, once the pane has focus) resumes following with nothing having to notice — there is no flag that can disagree with where the view actually is.
- **Hidden costs nothing; revealed shows now.** A hidden pane paints nothing at all and only records that it is behind; `reveal` refills it from the deque in one write. The alternative — painting into an invisible widget, as the ELEMENTS column deliberately does (§1.7) — is right there because unhiding must show *now* rather than a poll interval ago, and wrong here because a refill is one write of at most 500 lines while an open pane on a busy loop would be repainting a widget nobody can see on every decision.
- **One store, two matching bounds.** The deque is the log and the pane is a view of it: `log_harness` appends to the controller's deque and mirrors that one entry into the pane (through `AutomationView.paint_harness_entry`, which is why the entries ride an ordered queue on the screen — `shell/tui/messages.py`), and nothing else writes to either. The widget's `max_lines` is the same `HARNESS_LOG_MAX`, so with one entry per line the two prune in lockstep and a long run with the pane open cannot leave the widget holding entries the deque has already dropped.

**The near-miss number.** One entry needed evidence the search could not produce. `find_lowest_in_region` answered a failed copy-button hunt with a bare `None`, which cannot tell *the button was not on screen* from *the capture has stopped matching it* — and those need opposite fixes from the user. `driver/screen/template.py::find_lowest_with_best_miss` now returns `(match, best_miss)`, where `best_miss` is the smallest diff among the candidates that were judged and rejected (`None` when nothing got as far as being judged), and the plain search is the one-line view of it, so the two can never disagree about what a match is. The log reads *"copy button not found (best candidate diff 0.21, needs ≤ 0.08)"* — recapture it — or *"no candidate cleared the first-stage sniff test"* — it is not there. Same traversal, same `MAX_VERIFICATIONS` budget; the extra answer costs nothing.

### 3.3c What `Esc` does in the chat box

`Esc` in the composer is **three stages**, decided by what is in the box and whether the model is waiting on an `ask_user`, and the popup gets first refusal on the key before any of them (§3.3a):

1. **Text in the box → clear it, and keep the focus.** The commonest thing a user wants from `Esc` at a chat box is *scrap this and start again*, and the version that only blurred made that the long way round: blur, `t`, select-all, delete. The cursor stays where it is, so the rewrite begins on the next keystroke.
2. **Empty box, an `ask_user` open → dismiss the question** (`ChatComposer.QuestionDismissed` → `SessionController.dismiss_pending_question()`, §3.3e). It comes *after* the clear, so unsent answer text can never be lost to it, and it is live only while the box is in answer mode — the composer reads its own `verbatim` flag, which `MainScreen` sets from `awaiting_answer` and from nothing else.
3. **Empty box otherwise → blur**, exactly as it always did: focus drops to the screen and the single-key shortcuts (`u`/`c`/`i`/`w`/`e`/`x`/`t`/`l`) become reachable again ("command mode", §1.2). Reaching command mode with a half-typed message therefore costs two presses — the first one is what makes it safe to say the second one throws nothing away — and from an open question it costs two as well, because the first one hands the question back.

**The clear is an edit, not a reload.** `ChatComposer` calls `TextArea.clear()` behind an explicit `history.checkpoint()`, *not* `load_text` — which resets the undo history, and a single key that can destroy a paragraph of typing has to be one `ctrl+z` from handing it back. The checkpoint is what makes that undo restore exactly what was there: without it the clear can be batched with the last few keystrokes and `ctrl+z` would return a half-typed line. `reset()` — the send path — keeps using `load_text`: a message that has *left* is not a message the box should be able to resurrect.

### 3.3d What `↑`/`↓` do in the chat box

The composer remembers what has been **sent** from it this run and the arrows walk that list, newest first — readline's contract, and the one every chat client has trained the user to expect. `↓` past the newest entry restores the **draft** they were half-way through typing when they started browsing (possibly empty), which is what makes a stray `↑` cost nothing and is why the recall does not need an undo: the key that replaced the box is also the key that gives it back.

Three rules decide who gets the key, in this order:

1. **The popup, if it is up** (§3.3a) — unchanged, and checked first for the same reason `Esc`'s stages are: while a command list is open the arrows pick a row and nothing else.
2. **The editor, unless the caret is at an edge.** `↑` recalls only from the **first** line of the box and `↓` only from the **last**; anywhere else in a multi-line message they move the caret as they always did (`TextArea.cursor_at_first_line` / `cursor_at_last_line`). A pasted traceback has to stay navigable, and a key that sometimes moves the caret and sometimes replaces the whole box would be unusable. On the one-line box that is the overwhelmingly common case both edges are the same line, so there is no rule to learn.
3. **The history**, which may still decline: at the oldest entry `↑` hands the key back to the editor rather than doing nothing, and `↓` in a box nobody has walked up from is an ordinary caret key.

The list itself (`ChatComposer.SendHistory`) is **session-local, in memory, capped at 50** — a convenience for retyping the last thing, not a transcript; `l` exports the transcript. Blank sends are skipped and a repeat of the newest entry collapses into it, because sending the same thing twice running is common and would otherwise cost two presses to get past. Everything that leaves through the composer is in it — follow-ups, slash commands, `ask_user` answers alike — because the push lives in `ChatComposer.submit()`, the widget's one send door, which is also what `ctrl+s`/`ctrl+enter` now go through (they send *without focusing the box*, and a send the arrows could not find would be a hole in the list the user watched form).

**Editing ends the walk.** Any `Changed` that is not the recall's own puts the box back in charge: what is there now is the draft, and the next `↑` starts again from the newest. Telling the two apart needs care — Textual *posts* `Changed` rather than raising it, so a flag set around `load_text` would already be back to `False` when the message arrived and the recall would undo its own browse position. The composer counts the echoes it is owed instead (one recall is one `load_text` is one `Changed`).

The GUI implements the same behaviour key-for-key and rule-for-rule (`docs/design/gui.md` §3), down to the cap and the draft round-trip — the arrows are muscle memory and would be worse than useless if the two shells disagreed.

### 3.3e Dismissing an `ask_user` (`Esc` on an empty box)

A question the user does not want to answer is not a *refusal*: they have simply thought of something else to say first. So `Esc` at an open `ask_user` sends **nothing**. `SessionController.dismiss_pending_question()` sets `_question_dismissed` and pushes state; the flow stays parked on the answer future and the engine stays in `Phase.AWAITING_USER`, because `answer_user` is its only exit and poisoning the park would strand a live engine (that is `/new`'s trick, and it is safe only because a full session reset always follows it).

What changes is all on this side of the port:

- `SessionView.awaiting_answer` goes **false** (`_awaiting_answer and not _question_dismissed`), so the composer leaves answer mode, the slash popup works again and the verbatim rule is off. `SessionView.question_dismissed` carries the park, which is what keeps the box **enabled** while `busy` is still true and what makes the status bar read `■ QUESTION PARKED` rather than `● working...`.
- Slash lines are **commands again** — the point of the dismissal, and the reason `/new`, `/mode` and the rest are reachable from a question that has gone wrong.
- The next ordinary (non-command) message resolves the park with `_DECLINED_PREFIX` in front of it: `"[the user declined to answer the question and continued with a new request instead]\n\n"` + the user's text. That whole string is the `ask_user` result body and it is what the transcript echoes — the user should see exactly what the model will read. `//text` reaches the same place, one slash stripped, as it does everywhere else.
- Dismissing with nothing pending, or twice, is a silent no-op; a send that beat the `Esc` by a frame wins, because the future is already resolved.

The `/new` button remains the escape hatch from the whole *turn* (§1.3) and is unaffected: it poisons the answer future whether or not the question was dismissed.

### 3.4a Screen regions and the focus click (the "hand me back to the browser" nudge)

The user draws **one** box for this — the **chat region** (`#set-region-btn` → `#side-region`), the *window that hosts the AI chatbot* — written into the window tab that was selected when the **picker opened** (§1.6), which is passed to `_pick_chat_region(slot)` rather than re-read afterwards. The overlay blocks for as long as the user takes to drag a box, and `_calibrating` moves on its own in that window: a delegation starting mid-drag focuses the sub-agent run's transcript and selects its tab, and a slot read *after* the await therefore filed the box drawn around the master's window as the sub-agent's — and skipped the poller restart the master needed. The same slot decides both the write and the restart; the sidebar's `#side-region` is only repainted when that slot is still the one on screen. It describes where the conversation lives: it is where every appearance is searched for, the last-resort click target, the scroll target of the auto-copy flow, and — all by itself — the staleness finish detector.

The chat input box is **not** a drawn location. A fresh chat centres its box and an ongoing one docks it at the bottom, and after a new-chat click the layout is the *initial* one — so both layouts are captured once per **service** as appearances (`TemplateKind.CHATBOX_INITIAL` / `CHATBOX_ONGOING`, the editor's APPEARANCE column, §1.4) and found *inside* the drawn chat region at click time. `_chatbox_region` captures the live chat region once and hunts both in that one frame (ongoing first: mid-session it is the common case, and the search stops at the first hit), returning the match's absolute rectangle. That inversion is the point of the whole model: the pixels never move, so a browser the user resized or dragged to the other monitor costs one redrawn box instead of six recaptures — and a second window pointed at the same service costs *nothing*.

`_find_all(kind, slot=None, scene=None)` is the one primitive underneath: capture the slot's chat region (or reuse a frame the caller already took), search THAT WINDOW's service profile for `kind` at that kind's own `max_diff`, and return the absolute rectangles of every distinct place it verifies — an empty list for every way it can come up empty (no region drawn, nothing captured for that kind, the capture failed, or it simply is not on screen). *Every image* the kind holds is searched and the hits **unioned** (§3.4d), each carrying the image that produced it, because the rectangle to click is the size of the image that actually matched. Returning *all* of them is what makes ambiguity detectable: two windows of the same service inside one drawn region resolve the same appearance twice, and anything about to aim a real click (`AutomationController.click_profile_element` → `ElementClick.AMBIGUOUS` (`driver/automation/ops.py`), refused with a redraw-the-window message; `chatbox_region` → fall back to the drawn region rather than paste-click a maybe-wrong box) must refuse rather than guess — near-duplicate hits of the same physical element are merged first (`_distinct_rects`, fed the whole union at once), so "two" always means two *elements* and never two *pictures of one*.

After **every outbound the controller composes** — bootstrap, results, user answers, revert notices — MainScreen clicks the centre of whichever chat box was found, falling back to the chat region itself when neither is (mid-transition, a dialog over it, or nothing captured yet): clicking the window is recoverable, not clicking at all means the paste never lands. `AutomationController._click_after_response` returns `bool` — True only when a target was known AND the click landed. Nothing drawn means no click at all. Every one of those reads comes from the **live** slot, so mid-delegation the click goes into the sub-agent's window. Exactly one thing may happen *before* that click: the new-chat click `/new` queued for this paste (§3.3a), because which conversation the box is hunted in is what it decides.

Only when that click landed does `copy_outbound` go one step further: after a 0.15 s settle it sends a synthetic Ctrl+V itself (`driver.screen.focus.send_paste`), dropping the outbound payload straight into the focused input. If no region is drawn — or the click did not land — the paste is never attempted: focus could be on any window, and pasting into an unknown app is the one unforgivable failure mode here, so it stays click-only in that case exactly as before.

**`c` is two stages, and the second one is that same delivery.** The two things a user means by "re-copy" are not the same size. *Give me that payload back* is a clipboard write and costs nothing; *send it again* moves the mouse into the browser, clicks a chat box and pastes into whatever has focus — the one class of act this app otherwise always announces first. So the key splits: the **first press** parks the last outbound and stops (`ChatView.park_outbound` → `AutomationController.park_on_clipboard`, no click, no Ctrl+V, no `set_loop_state` — nothing about the browser round trip has moved), and its toast is where the escalation is discovered: *"re-copied the last outbound (11,990 chars) — press c again to deliver it"*. A **second press within `_RECOPY_DOUBLE_TAP_S` (1.5 s, `time.monotonic`)** escalates to `ChatView.redeliver_outbound`, which is `copy_outbound` and nothing else — the same park, the same verified focus click, the same burst-or-stream choice and the same opt-in Enter tap, read from the same live preset. There is no second send path to drift, and a re-delivery that silently skipped the stream mode or the auto-submit would be exactly that. The double tap **is** the confirmation dialog, spent as one gesture instead of a modal; a `c` after the window has expired is simply a fresh first press, because a delivery the user stopped expecting is the failure this window exists to prevent. The arm lives on `SessionController` (`_recopy_armed_at`) next to `_last_outbound`, is consumed on every press, and is dropped whenever a *new* outbound is composed — the second press would otherwise deliver a payload the first press was not about. Stage one is deliberately ungated (a clipboard write is safe mid-turn, like `/log` and the log export); stage two takes the flow-spawning actions' `_busy` / `_turn_aborting` refusal in the controller, and the two refusals only the view can see — DISARMED, and an auto-copy flow already driving the mouse — in `redeliver_outbound`, which are the sidebar retry button's refusals for the same reason (§3.4b). It rides that button's exclusive `insert` worker group too: two inserts racing into one chat box is what the group is for.

- **Delivery — one paste, or a stream of them** (`ServicePreset.delivery`, the editor's DELIVERY tick, §1.4). A very large payload handed to a web chat box as *one* paste stalls it for seconds with nothing on screen, and the user cannot tell that from a paste that never happened. A service set to `"stream"` therefore gets the payload walked in instead: `AutomationController._stream_outbound` (the streamed half of `deliver`) splits it (`driver.clip.chunking.split_for_stream`, `STREAM_CHUNK_CHARS` ≈ 1 500 chars, cut after the last newline inside the window and hard-cut only for an unbroken line) and sends each chunk as its own clipboard write plus the same single `send_paste` burst, `_STREAM_CHUNK_SETTLE_S` apart so the box can reflow between them. **Chunked pastes, never synthetic typing**: a typed newline is Enter in most chat boxes, so typing a payload would submit half of it — the exact accident the whole flow exists to prevent. Every chunk goes through `write_via`, so each is registered as a self-write and the watcher can never ingest our own outbound back as a reply. It stays inside `LoopState.AUTO_INSERT` throughout — one insert that takes a while, not a state of its own — and reports itself on the same sidebar banner as `>>> STREAMING <<< chunk i/n`, which is the only thing on screen while the user is watching the browser. `"paste"` is the default and every built-in preset ships on it: the mode is slower, and a stream that is interrupted leaves a fragment in the box. **A chunk that does not paste ends the stream**: the FULL payload goes back on the clipboard (the last thing on it was a fragment, and the manual Ctrl+V about to be asked for must paste the message) and the ordinary `MANUAL_INSERT` path takes over, with a toast saying the box holds a partial message to clear first. The whole payload is written to the clipboard *before* the click either way, so a stream that never starts — no clipboard backend, a click that did not land — degrades to exactly today's behaviour.
- **Auto-submit — the opt-in Enter tap** (`ServicePreset.auto_submit`, the editor's second DELIVERY tick, §1.4; default **off**, because submitting a message is the one act the loop otherwise always leaves to the user). When a service opts in, `copy_outbound` follows a **successful** paste (single or streamed) with a 0.15 s settle and one synthetic Enter (`driver.screen.focus.send_enter`, the Ctrl+V burst's sibling). Three deliberate boundaries. It fires *only after a paste that landed* — after a refused click or Ctrl+V nothing is typed, exactly as before, because an Enter into an unknown window (or into a chat box holding nothing) is the same unforgivable failure mode the paste rules exist for. The loop still enters `WAIT_SEND`, not `WAIT_GENERATE`: the tap is an *attempt*, and the send gate's own evidence (§3.4b — the ready button vanishing, a busy icon appearing) remains the only thing that says the send happened, exactly as for a human Enter; a tap that did not take runs into the gate's ordinary timeouts. And the sidebar banner says whose Enter it now is: `>>> AUTO-SENT <<<` (`AUTO_SEND_FLASH_TEXT`) after a tap that went out, falling back to `>>> PRESS ENTER <<<` when `send_enter` reported nothing typed — the flash stays up either way until the gate sees the send land, so a swallowed tap still ends in the user pressing Enter themselves.
- **Drawing**: each button spawns the tkinter overlay as a *child process* (`agentclip --pick-region`, hidden flag) — tkinter cannot share the Textual process (both want an event loop; tkinter wants the main thread). Only one overlay may ever be on screen, and an exclusive worker group alone cannot guarantee it, because cancelling the worker does not kill the blocking child overlay process — so each of the two surfaces that can raise one holds a flag for the whole operation and refuses (with a toast) any further press while it is held: `MainScreen._picker_open` for the chat region, `ServiceEditorScreen._capturing` for the seven appearance captures (which additionally refuses `escape`, §1.4). The two surfaces cannot be reached at the same time: the editor is a modal over the main screen. The overlay is a translucent topmost fullscreen window spanning the whole virtual desktop (multi-monitor, Windows metrics); drag draws a rectangle, `Esc` cancels, a sub-8-px drag is treated as a stray click and ignored. The child prints `left top width height` on stdout; cancel prints nothing. Each caller passes its own prompt ("the window that hosts the AI chatbot" / "the spot to click after each response").
- **Clicking**: `driver.screen.focus.click_region` — Windows-only `SetCursorPos` + `SendInput` via ctypes (stdlib, no new dependency). Both processes force DPI awareness first so overlay coordinates and click coordinates share the physical-pixel space. On non-Windows the click returns False and the user is told once (not per copy) that focus clicks are unsupported.
- **Scope**: the drawn regions are app-run-scoped and live in a `SlotCalibration` on MainScreen (§1.6), show in the sidebar's `#side-region` label, and can be redrawn mid-session (window moved). They describe where the service's windows are, not what one conversation said, so they **survive** `/new` / the summary's *new session* for both windows — a new conversation in the same windows needs no re-drawing (and a sub-agent window calibrated mid-session actually enables `delegate` on the next `/new`, which is the advertised workflow). Only the pointers (`_calibrating`, `_live`) go home to MASTER, and the detector worker restarts against the surviving live window. Captured *appearances* are the opposite: they belong to the service, are shared by every window pointed at it, and **are** persisted (`driver.screen.profile_store`, one folder of PNGs per service under `config.default_profile_dir()`), so they come back on the next run.
- **Layering**: all of it lives in `agentclip.driver.screen` (region/overlay/picker/focus), an OS side-effect leaf like `driver/clip` that only the two shells, `cli` and `driver/automation` may import (enforced in test_layering). The *session* controller never knows the feature exists — the click rides inside `AutomationController.copy_outbound`, which the view's `copy_outbound` forwards to.

### 3.4b The copy button and auto-copy-click

Most chat sites need a click to get a response onto the clipboard at all — there is no keyboard shortcut, only a small icon under each response. This block automates that click once the busy detector (§1.3's REASONING block) says a response has finished, so the user never has to alt-tab and click it themselves.

- **The session gate — calibration is not consent.** Everything below may only arm and fire while a reply is genuinely outstanding: `MainScreen._awaiting_pasted_reply`, opened by `copy_outbound` (`_open_reply_gate`) and shut by the harvest (`_close_reply_gate`). The poller's lifecycle is unchanged and still driven purely by calibration — it is what feeds the sidebar's DETECTION readout (§3.4e), which has to work on a resting chat or the user cannot tell a detector that is watching from one that is blind — but a verdict may not reach for the mouse without an outbound behind it. **Setting a region is pure configuration**: before this gate, finishing a preset's calibration (appearances captured, chat region drawn) was enough to start a poller against a resting chat, where one frame of screen noise armed the trigger — a busy/idle icon actually *seen* on one frame arms on the spot by design, and the picker overlay closing is a sustained large delta all by itself — and the settled screen then "finished" it two ticks later, driving a click, a scroll and possibly a hover scan across a conversation nobody had asked anything. The per-tab flow the gate encodes is: IDLE → the user sends a task in the composer → AgentClip clicks the chat box, pastes, and asks for the Enter keystroke (`>>> PRESS ENTER <<<`) **and** starts counting → *the send gate below holds, where the service has a ready-to-send capture* → the arm/fire rules below wait out the pre-Enter screen → reasoning done → the copy button is clicked → the clipboard watcher ingests and parses → IDLE. Opening the gate also resets the whole trigger *and* every live tracker's debounce state, because the click and the Ctrl+V that just happened are AgentClip's own frame deltas, not the model's. Four moments close it, one per way an outstanding reply stops being one: firing the flow (that *is* the harvest), `/new` (`clear_transcript`), and the live slot moving either way (`start_browser_chat` / `end_browser_chat` — each window's gate is opened by its own `copy_outbound`, and a sub-agent's bootstrap is copied a moment after the retarget). It is deliberately **not** part of `_reset_finish_trigger`: that forgets what the detectors *saw*, which is also what suspending them for a modal does (§3.4e), and a turn interrupted by an F2 visit must still be auto-copied when it finishes.
- **The ready-to-send gate — the pre-Enter screen, answered instead of waited out.** Everything the session gate does not solve happens inside the window it opens: the payload is in the composer, the user has not pressed Enter, and the chat sits perfectly still for as long as they take to read it. `SEND_ARM_MIN_DIFF`/`SEND_ARM_TICKS` (below) keep that stillness from firing the auto-copy, but they are a heuristic about pixels. Where a service shows a **ready-to-send button** — the control that exists only while the composer holds text — there is a direct answer instead, and `TemplateKind.SEND_READY` (§3.4d) is a capture of it. **The capture is the entire switch**: no checkbox, no `finish_signals` entry, no `ServicePreset` field, because there is nothing for a user to decide that having captured the button has not already said. A service without one behaves exactly as it did before the gate existed.
  - **States** (`AutomationController.send_gate`, a `SendGate | None` from `driver/automation/finish.py`): `open_reply_gate` sets **HOLD** when the *live* window's service has the capture and `None` when it has not. HOLD → **SEEN** on the first sighting. SEEN → **released** (`None`) on the first non-sighting, because the button only exists while there is something to send: its disappearance *is* the Enter keystroke. There is deliberately no debounce on that disappearance — one dropped frame costs an early release, which is only ever the old behaviour, while a debounce in the other direction would hold a session open on a button that has already gone. Every *other* way out of both states is bounded, because **the gate may delay a session; it may never deadlock one**: an **override** on generation evidence (below), and a clock per phase — `SEND_GATE_TIMEOUT_TICKS` (10, ~5 s at the 0.5 s cadence) for a button that never appears at all, `SEND_GATE_SEEN_TIMEOUT_TICKS` (240, ~2 min) for one that appears and then never goes. The clock **restarts at the sighting**, since the two phases wait for entirely different things: a template match that should land within a second or two, and then a human reading what is about to be sent.
  - **While it holds**, `evaluate_finish` returns immediately: probes still land and still paint the sidebar, but nothing arms, nothing fires, and the large-delta run does not advance. The `>>> PRESS ENTER <<<` banner stays up (it is still true), and every manual escape hatch — `i`, `c`, `/new`, the sidebar buttons — is untouched, because the gate is a veto inside one method and not a mode.
  - **Unless the model is visibly generating**, which **overrides** the gate outright (`override_send_gate`, from `evaluate_finish` before its own veto): a **busy or idle** detector that *saw* its icon on the frame just probed — `icon_evidence`, never staleness, and never merely a `False` verdict (see *what counts as icon evidence* below) — answers the gate's own question better than the button can, because nothing generates a reply to a message that was never sent. This is not a nicety. The gate's ordinary release is one non-debounced template match *going away*, and a fresh chat's **first message** is exactly where that never happens: the composer is centred and animating rather than docked where the capture was taken, so the button gets seen once and then goes on matching. The user pressed Enter, the model generated, the DETECTION panel said so — and nothing was left that could let go, so the banner flashed for ever and the reply was never harvested. Deliberately **not** `release_send_gate`: that resets the trigger and every tracker's debounce on the grounds that the held-through frames show an unsent composer, whereas the frame doing the overriding is a genuine post-send reading of a generating chat. So the gate simply goes (line: `generating - sent, finish detection running`) and evaluation carries straight on into the icon-arm branch with its verdicts intact — same tick, same arm, banner down. The limit to icon evidence is the point: a caret blinking in a composer full of unsent text is a `CHANGING` probe too, and letting staleness override would hand the gate back to the noise it exists to ignore.
  - **On release** the trigger *and* every tracker's debounce are reset, exactly as `open_reply_gate` resets them: finish detection starts from the **send**, not from the paste, so the frames of a composer with unsent text in it cannot contribute to a streak. The banner comes down — the send is proven, which is the same standard the icon-arm path uses.
  - **On either timeout** nothing is reset and nothing is hidden: the fallback is today's behaviour, verbatim, plus a warning toast and a line saying which clock ran out. *Never appeared* (`never appeared - finish detection running`) is a capture that stopped matching, a composer scrolled outside the drawn region, or a browser that cannot be captured at all — a failed capture counts against the clock too — and costs five seconds. *Never went away* (`never went away - finish detection running`) is its mirror, and the backstop for the sessions the override cannot rescue: a service running no icon detector at all, whose only evidence is a button that keeps matching long after the message it belonged to was sent. The two are named apart in the toast because the user's fix differs — one capture never matches and the other never stops. That second budget is deliberately generous rather than tight: what the SEEN phase waits for is a person deciding whether to send, and a clock that expired on someone who paused to think would break the feature to fix the deadlock.
  - **Where it runs**: inside the poller's existing tick, on the tick's one shared capture, calling `AutomationController.consume_send_ready(found: bool | None, generation)` on **every** tick the live service has a `SEND_READY` capture — in the poll loop's own call stack, not through a message. The gate is a *reader* of that stream, not the thing that turns it on (§3.4f): `consume_send_ready` returns immediately when nothing is holding, and the clock only ever counts the ticks of a live gate. The earlier arrangement — search only while the gate holds, to save a template scan per tick during a response — bought about 10 ms of a 500 ms tick and cost the user any way of seeing whether their send-button capture still matched anything (§1.7). It closes no tick and folds into no verdict, so it is absent from `active_detectors` and its ghost test is the generation stamp alone. The gate is a phase **of** the reply gate and dies with it (`close_reply_gate`): firing, `/new`, and the live slot moving all take it along. It is deliberately *not* part of `reset_finish_trigger`, for the same reason the reply gate is not — an F2 visit forgets what the detectors saw and un-pastes nothing.
- **Capturing**: the service editor's "Capture copy button..." (`#svc-capture-copy-btn`, §1.4) spawns the same draw-a-box overlay as the chat region, prompting (from `TemplateKind.COPY.prompt`) for a **tight** box around **one** copy-button icon — "pick the one under the last response, while the page is idle." Only the *pixels* are kept: they are anchored for search (`ServiceProfile.put`) and written to disk under the **service** (`profile_store.save_template`), so the same capture serves every window pointed at that service and every later run. The drawn rectangle is not stored at all — the icon is found where it actually is, every time. A capture failure is reported and nothing is filed; so is a *save* failure, since the editor keeps no in-memory profile for the run to fall back on. The sidebar shows only whether it is captured at all (`#side-profile-note`, "appearance: 4/7 captured"); the per-kind size and image count live on `#svc-tpl-copy` in the editor. Where the kind holds several images the harvest takes the **bottom-most match across all of them** (`driver.automation.flow.lowest_match`) — lowest is still newest whichever picture matched — and clicks a rectangle the size of that image. A search that finds nothing also reports **how close it came** (`driver.automation.flow.lowest_match_scored` → `find_lowest_with_best_miss`, phrased by `driver.automation.flow.how_close`), which is what the harness log turns into *"copy button not found after 3 snaps (best candidate diff 0.21, needs ≤ 0.08)"* rather than a bare "not found" (§3.3b). The number kept is the **best of the flow's snap rounds**, not the last round's: the closest the capture ever came is the one that separates a drifted capture from an absent icon, and the final scroll landing somewhere blank must not throw away the one informative frame. It is followed by what the always-running detector remembers (`_copy_last_seen_note` → `ScreenDetector.seen_ago`): *"; the poller last saw one 32s ago"* or *"; the poller has never seen it in this window either"*. The two numbers separate the three fixes: this frame nearly matched (the page moved, retry), the capture matches nothing ever (recapture in F2), or the icon was there minutes ago and this response has not drawn one (hover-scan, or the response is not finished).
- **Arming and firing**: each poller tick takes one capture of the live slot's chat region, hands it to the one `ScreenDetector` (§3.4f) and folds that snapshot's finish verdicts in a **fixed order** — `consume_busy_probe` → `consume_idle_probe` → `consume_stale_probe` on `AutomationController` — skipping whichever tracker it was not built with. There is no probe MESSAGE any more: since the poller thread became the controller's (gui.md §1, slice 5b) it calls its own consumer synchronously, one call stack per tick, and the test seam that used to post a message is `AutomationController.feed_probe`. `_start_detector_worker` (re)builds the detector — busy/idle presence trackers if the LIVE window's service `finish_signals` ticks them *and* it has those appearances, the stale tracker if `finish_signals` ticks it, and a plain search for every appearance the service has captured (an unticked busy/idle among them, which is searched and drawn and votes on nothing, §3.4d), nothing at all if no chat region is drawn or nothing whatever is calibrated (§1.3) — whenever an appearance is captured, the live window's region is drawn or its service re-picked, the config is adopted, or the live slot moves; `active_detectors` records which of them will report, in that fixed order, and the run gets a fresh `detector_generation` — a monotonic int stamped into every probe it consumes. Each consumer first drops **ghosts** (`is_ghost`), then records its detector's verdict and calls `evaluate_finish` only when `finish_tick_closed_by` says its probe is the tick's **last**, which is simply `active_detectors[-1]`: this is what lets `evaluate_finish` fold the combined verdict exactly once per tick no matter which subset is running, instead of acting on a half-reported tick. `evaluate_finish` folds every detector that has ever reported (`busy_seen` / `idle_seen` / `stale_seen`) into one verdict: **any** `False` (generating) resets the streak; only once **every** live verdict reads `True` (finished) does the streak advance, and reaching **2** consecutive all-`True` ticks fires `run_auto_copy_flow` and disarms *the trigger* (`copy_armed`, nothing to do with §3.5's switch) — so with several detectors calibrated, that agreement is the whole point of having more than one. A capture error (`None`) breaks the streak but leaves the arm alone — a single bad frame must not cancel an in-flight finish. Evaluation is suspended for the flow's entire run (`flow_running`), and **every** live tracker is reset in the flow wrapper's `finally` (`run_auto_copy_flow` → `end_flow`): the flow clicks, scrolls and hover-scans the very window all three detectors watch, so without the suspension and the reset it would read its own mouse work as a fresh generation and re-arm/re-fire itself forever.
- **A verdict is a reading of one window, and it says which.** Cancelling a poll thread only raises a flag: the loop it interrupts still finishes its tick and posts. `AutomationController.is_ghost(detector, generation)` drops anything from a run that is no longer live, and the **generation stamp** is the load-bearing half of that test. The poller is restarted precisely when the automation changes windows (`start_browser_chat` / `end_browser_chat`, §3.4c), so an in-flight probe routinely lands *after* the retarget — describing the window AgentClip has just stopped driving. Filtering by detector name alone let it through, because both windows run a stale detector: `/abort` during a generating sub-run handed the master the live slot, the sub window's last "still generating" then armed the trigger, and two quiet ticks fired the copy flow at the **master's** chat. The name check remains as the second half, for the case the stamp cannot see: when the new detector set is *smaller* (a forgotten appearance, an unticked signal) a leftover "generating" would re-arm the trigger on every later tick and wedge auto-copy shut for good. Dropping a verdict is always safe — a detector that is still running is refreshed one poll interval later.
- **What may arm it is not what may break the streak.** **Icon evidence** from **busy or idle** — defined in the next bullet, and strictly stronger than a `False` verdict — arms the trigger on the spot: the reasoning indicator being on screen (or the send button being watched to go) is evidence only a real generation produces. A `False` from the **stale** detector is not — frame-to-frame change is produced by a blinking caret and a drifting mouse as readily as by a model, and AgentClip's own paste leaves the user staring at a composer for as long as it takes them to press Enter. Arming on that noise, then reading the still, reply-less pre-Enter screen as a finished response, fired the auto-copy at a chat containing nothing. So staleness arms only on a **sustained large delta**: `StaleProbe.diff ≥ SEND_ARM_MIN_DIFF` (`0.02` — two orders of magnitude above caret/hover noise, far below a prompt landing plus the reasoning UI unfolding) on `SEND_ARM_TICKS` (`3`, ~1.5 s at the 0.5 s cadence) **consecutive** stale probes; any smaller probe (and any STALE or ERROR) restarts that run. A small-diff `CHANGING` still resets the finished-streak — it is "not finished" evidence whatever else it is — it simply may not claim the send happened. `Sidebar.hide_paste_flash()` moves with the arm rather than with the verdict, so the `>>> PRESS ENTER <<<` banner comes down exactly when the send is provably detected.
- **Icon evidence is a reading of one frame, not a verdict** (`AutomationController.icon_evidence`, `BusyProbe.generating_now`). A `PresenceTracker` verdict is de-bounced and deliberately biased: "finished" must survive `required_ticks` frames, so for the whole settling window after a `reset()` the tracker reports **"generating" as a default, with nothing on screen behind it** (§ `driver/screen/presence.py`). That bias is right for the finish decision and catastrophic for the two rules that trust a single frame — and since `open_reply_gate` resets every tracker at the paste, reading `busy_finished is False` as "the icon is on screen" made **tick one of every message** claim a generation: the auto-copy armed, the send gate was overridden before the user could reach Enter, and ~2 s later the same un-evidenced ticks flipped to "finished" and dropped the turn into `MANUAL_COPY` with *copy button not found*. So the probe carries the raw per-frame fact next to the verdict, and it is **asymmetric on purpose**: a **busy** tracker's positive same-frame match is proof (a stop button/shimmer is drawn by a live generation and nothing else), while an **idle** tracker's same-frame *miss* counts only once that tracker has genuinely **found** its appearance since the last reset — "the send button is not visible" is also what a fresh page's centred, mid-layout composer looks like, and a still chat can fake that all day. Both flags are cleared by `reset_finish_trigger`; a tracker swap (`reset_trackers`) clears the tracker's sighting for the same reason it clears the streak. The verdicts themselves are untouched by any of this — the finish decision keeps its full debounce.
- **The flow** (`AutomationController.auto_copy_flow`, all OS calls off the event loop via `asyncio.to_thread`; the shell keeps only the `run_worker` scheduling):
  0. **Nothing to do without a drawn chat region** (or without a captured icon): the search happens *inside* the window the user drew, so with no window there is nowhere to look and the flow returns having clicked and scrolled nothing.
  1. Focus the browser the way `copy_outbound` does after every copy — `chatbox_region` (the chat box found in the region wins, the region itself is the fallback) then `focus_click` — with one difference that belongs to step 2: when the snap is a **keyboard** one the click aims at the padding **just above** the box (`driver.automation.flow.above_chatbox`, `ABOVE_CHATBOX_PX` = 10 px, horizontally centred on it) instead of inside it. A caret in the chat box swallows End outright — there it means *end of the line* — so the click that was supposed to enable the snap was the thing preventing it. Only a small step above: further up is the last response itself, where a click could hit a link. The aim falls back to the box whenever that point is not inside the drawn region, which is exactly the no-chat-box-calibrated case (the fallback rect *is* the window, and there is no padding above its own top edge). Then a 0.15 s settle.
  1b. **Park the pointer over the transcript** — `move_cursor(*chat_region.center)` and a 0.1 s beat, for every scroll action alike. The click of step 1 leaves the cursor wherever it aimed, which is the input box or the sliver above it, and a chat page that scrolls only the pane **under the pointer** then answers the snap by wheeling a one-line text field: the transcript never moves and the copy hunt searches the wrong part of the page, the same symptom step 1's aim exists for and a different cause. It has to be `move_cursor` — a synthetic SendInput MOVE — and not the `SetCursorPos` inside `scroll_region`'s own centring, because a teleported pointer does not reliably drive the `WM_MOUSEMOVE` → `:hover` chain those pages track (the same reason the hover scan uses it, §3.4b step 4). Best-effort: the return value is not read, and a move that cannot happen (unsupported platform) leaves the snap exactly as it behaved before this step existed.
  2. Snap the transcript to the bottom, the way this service says it scrolls (`ServicePreset.scroll_action`, the editor's SCROLL radio, §1.4) — `AutomationController.snap_to_bottom`, one method so the three forms cannot drift apart between rounds (step 3a). The default is the wheel flick: `scroll_region(chat_region, _SNAP_WHEEL_DETENTS)`, aimed at the region, needing no keyboard focus. The two keyboard forms exist for pages the flick does not reach (a virtualized transcript, a chat that captures wheel events): `"page_down"` sends a burst of `_PAGE_DOWN_TAPS` Page Down taps and `"end"` one End tap (`driver.screen.focus.send_scroll_key`), both riding the focus click in step 1 — keys go to whatever has focus, which that click just made this chat window *without* putting a caret in its input box (step 1) — and they only work where the page itself scrolls on those keys, which is why the choice is per service and the wheel is the default. A `_SNAP_SETTLE_S` (0.4 s) pause lets the page render after the snap either way.

     **The sizes are over-shoots, deliberately, and were raised** from −40 detents and 8 taps to **−100** and **12**: a snap that stops short leaves the newest reply's copy button above the fold, and what follows is not a visible error but a silent fall to MANUAL_COPY on a transcript that was never showing the answer. Over-shooting costs nothing — the page is at its bottom and the extra detents land on a wall — so the numbers are chosen for the longest response a user might have scrolled away from rather than for the typical one. `"end"` stays at **one** tap: it is the bottom by definition, and a burst of them would be twelve ways of saying the same thing.
  3. Capture the chat region and hand it to `agentclip.driver.screen.template.find_lowest_in_region(template, scene, max_diff=TemplateKind.COPY.max_diff)`, which returns the bottom-most (i.e. newest) verified match anywhere in it — the icon appears once per response, so multiple matches are normal and only the lowest one matters. There is no band and no width constraint, so the old "search failed" branch is gone with them; a capture failure is reported (`#side-tpl-copy` reads `capture failed`) and the flow aborts. **Its own capture and its own search**, even though the detector has been looking for the same icon twice a second all along (§3.4f): the flow has just clicked, scrolled and waited for the page to render, so a location from the last poll frame is up to half a second stale and *a stale location is not a click target*. The detector also answers a different question — is one on screen anywhere, stopping at the first hit — from the harvest's *which is the lowest*. What the detector's memory is read for is explaining a **miss** (`_copy_last_seen_note`, next paragraph but one), never a coordinate.
  3a. **A miss re-snaps: steps 2–3 are a loop of `_COPY_SNAP_ROUNDS` (3), not a single pass.** The commonest reason the icon is not on the frame is not a drifted capture at all — it is a page that had not finished arriving. The detectors call a reply finished on two agreeing ticks, a streamed reply keeps growing after that, and a virtualized transcript renders what it just scrolled to a beat later; either way the bottom moves out from under one snap. So a static miss scrolls again with the same action, waits the same settle, re-captures and re-searches, and the flow stops at the first round that finds one — the budget is a ceiling, not a schedule. Each miss on the way is logged (`log_harness(KIND_COPY, …)`) as *"copy button not found on round 1/3 (best candidate diff 0.21, needs ≤ 0.08) - snapping to the bottom again"*, so a failure reads as a hunt rather than as one unlucky frame, and the ELEMENTS copy row is repainted every round (`show_copy_crop`, which reaches the shell as `paint_elements`) with the frame the flow is looking at **now**. **Step 1 and 1b are not repeated**: nothing between rounds touches the mouse or the focus, so the window is still focused and the pointer is still parked where the first round put it, while re-clicking a transcript risks selecting text or following a link. A capture failure in any round aborts as in step 3 — a chat region that cannot be captured will not become capturable by scrolling it.
  4. No match in the static frames of **any** round, **and the active service's `ServicePreset.hover_scan` is on**: the chat may only paint the icon under the pointer (Claude does), so `#side-tpl-copy` reads `hover-scanning` and the flow walks the real cursor up the chat region (`driver.screen.hover.hover_scan_points`), re-capturing the region and re-searching after each stop, taking the first frame the icon appears in. It runs **once, after the last static round**, not after each one: it is a slow, visible takeover of the user's mouse, and doing it three times over would be three times the intrusion for the same answer. The scan is opt-in per service and **off by default** for the same reason: where it is the only way to find the icon it is worth that, and everywhere else a static miss simply means the icon is not there. With it off, a static miss goes straight to the not-found branch and the cursor is never touched. Still nothing: toast "copy button not found on screen" (warning) and stop — nothing is clicked. A match: a **verified, retried click** (`AutomationHost.verified_copy_click`) at `match_rect(chat_region, template, match)` — sometimes the cursor lands on the right spot but the hover-rendered button hasn't quite registered the click, so a single unverified click is not trusted. The provider's clipboard text is read once as a baseline before the first attempt; up to **three** attempts fire, each at a small offset from the matched rect's position that stays well inside the ~24 px icon — `(0, 0)`, then `(-3, -3)`, then `(+3, +3)` — each attempt doing `click_region(rect, settle_s=0.05)` (the 50 ms hover settle, same reasoning as the copy-button hover elsewhere) followed by up to six clipboard reads 0.2 s apart, stopping as soon as the text differs from the baseline. If the baseline read itself is unavailable (`ClipboardUnavailable`), the flow falls back to one unverified click instead of retrying blind — there is no signal to retry against.
  6. On a verified (or unverifiable-fallback) click: toast the diff, and snap focus back to AgentClip — `AutomationController.snap_back_after_click()`, which is a `SNAP_BACK_SETTLE_S` (0.15 s) beat (so the browser registers the click) and then `snap_focus_back()` → `focus_window_verified(own_window)`. That pair is one method rather than two lines copied out: every "we clicked over there and the user's next move is over *here*" site (this one, `/new`'s new-chat click in **both** shells, an auto-sent delivery) is the same beat and the same snap, and it no-ops without a recorded handle rather than sleeping for one. `AutomationController.own_window` (written by `set_own_window`) is the foreground window handle recorded whenever the user is provably interacting with AgentClip — at mount, on every composer send, and on a press of the sidebar's own "New browser chat" button (`_remember_own_window`) — and is deliberately **not** session-scoped: the terminal outlives `/new`. `focus_window` (screen.focus) taps ALT through SendInput first, the documented input-recency loophole without which Windows refuses `SetForegroundWindow` from a background process. **Verified and retried**, because asking once is not the same as arriving: the click this follows is itself an activation request, the browser is still processing it, and a granted foreground can be taken straight back — silently, so the whole snap-back looked like a missing call. `focus_window_verified` therefore asks, waits a **growing** beat (`REFOCUS_SETTLE_S` = 0.05 s × the attempt) and only then reads `foreground_window()` back, up to `REFOCUS_ATTEMPTS` (4) times — a 0.5 s budget, off the UI thread, after which False simply means the browser kept it. On exhausted retries (the clipboard never changed across all three attempts): toast a warning ("copy click did not take — click the response's copy button yourself") and deliberately **do not** snap focus back — the browser stays focused so the user can click it themselves.
  7. **The no-CLIP harvest** (`_ingest_prose_harvest`, after a verified click, always). A model reply carrying no CLIP blocks at all used to vanish here: the watcher's pre-filter (protocol.md §1.4 tolerance #11) dropped it, and the only way to see it was the manual `i` ingest. Sometimes the model does everything right and simply answers in prose, so **a copy click AgentClip made itself always ingests what it harvested** and shows it. This is the one place that filter is loosened, it needs no setting, and it is scoped to the flow's own click **rather than to the watcher**, because the two know different things: the watcher sees every copy the user makes and must keep ignoring the non-protocol ones, while the flow just watched the copy button write *this* text — it is the reply, whatever it contains. So on a verified click the flow reads the clipboard once more: protocol-shaped text is left strictly alone (the watcher ingests it on its own, and reading it here too would be a double ingest of every normal reply); anything else goes to the controller as `submit_clipboard(text, accept_prose=True)`, which routes it through the same forced-ingest treatment the `i` key has always had — the engine still judges it `Noise("not-protocol")`, the controller shows it in the transcript as **prose** with the "press t to follow up" invitation, and nothing in it executes. The session stays in `AWAITING_REPLY`; the user reads the reply in the window, exactly as asked, and follows up when ready.

     The scope is a **one-shot window**, not a call-site convention: `AutomationController` arms `prose_window` immediately before `verified_copy_click` and disarms it the instant `ingest_harvest` returns — plus, defensively, at the top of `end_flow`, which the flow's `finally` always runs, so a click that never verifies, a MANUAL_COPY exit or an exception cannot leave it open for whatever the user copies next. Both shells' harvests read that property and do nothing outside it. Only `Noise("not-protocol")` is overridden; everything else stays strict — the own-outbound dedup, the chat-name gate, the flattened/unfenced bounces all still get their say.
- Every branch also repaints the sidebar's `#side-tpl-copy` line with the captured size plus a short ASCII status (`re-snapping (2/3)` between snap rounds — deliberately *not* the word "not found", which is the flow's verdict and belongs to a hunt that has finished, then `hover-scanning` / `clicked (diff 0.03)` / `click did not take` / `not found` / `capture failed`), which `Sidebar.update_template` prefixes `copy · `; it rests at `copy · no click yet`.
- **The paste flash and auto-paste**: automation covers browser→AgentClip; AgentClip→browser used to always end in a human Ctrl+V, and now only sometimes does. Right after its focus click, `copy_outbound` checks whether that click actually landed (`AutomationController._click_after_response` returns `bool`): if it did, the payload's insert waits in **two halves** — first `AutomationController._await_browser_activation` polls `foreground_window()` until it is no longer `own_window` (`ACTIVATION_ATTEMPTS` = 10 asks, `ACTIVATION_POLL_S` = 0.1 s apart, a 1 s ceiling), then a flat `PASTE_SETTLE_DELAY` (0.6 s) beat — and only then does a synthetic Ctrl+V (`driver.screen.focus.send_paste`) drop the payload straight into the focused input, with the sidebar banner reading `>>> PRESS ENTER <<<` (`Sidebar.ENTER_FLASH_TEXT`) — the human's only job left is the send keystroke. **That wait is the whole reason the insert is reliable**: a click is an *activation request*, granted asynchronously, and a Ctrl+V that overtakes the browser's own activation is delivered to whatever held focus a moment ago — the payload silently fails to appear, which is precisely the intermittent "the reply did not go in" the user sees. It is the same race `focus_window_verified` fights from the other side, and it turns out there *is* something to verify against: not the chat box (a browser widget, not a window handle) but the window it lives in — once the foreground stops being ours, the activation the click asked for has been granted. Hence the split, and neither half replaces the other. The **poll** covers the activation and covers it exactly, which no fixed number can: long enough for a loaded machine is a sleep the user pays on every single delivery, and short enough to go unnoticed is the intermittent bug. It is never a precondition — an exhausted budget stops waiting and pastes anyway, because refusing a payload that would probably have landed is the worse failure and the banner plus the retry button already cover one that goes nowhere — and with no `own_window` recorded there is nothing to compare the foreground *to*, so it is **skipped** rather than spent. The **flat beat** after it covers the half no window handle reports on: the page has still to route that click through to the chat box and put a caret in it. It was raised 0.2 s → 0.3 s when inserts kept going missing at 0.2, which it can now afford, because the poll has taken the activation half of the old budget off it, and 0.3 s → 0.6 s alongside the double click below, because inserts were *still* going missing and a composer that reflows after taking focus can spend most of a second doing it. And the focus click itself is a **double** click (`_click_after_response`: click, `FOCUS_CLICK_GAP_S` = 0.12 s, click again) for the third failure this same race produces: a browser window that is not in front takes the first click as its *activation* and never routes it to the input field, so the window ends up focused with the caret nowhere and the Ctrl+V lands in nothing. The second click arrives at a window that is already awake. It is safe here and nowhere else — the box is empty at this point in the sequence, so a double click has no word to select, which is why it lives in `_click_after_response` and not in `focus_click`, whose other callers aim at a transcript full of text. The verdict stays the *first* click's: a refused first click stops the sequence (the target is not clickable at all), while a refused second one only means a throttled burst, so the reinforcement is best effort. Both are `await asyncio.sleep`, not `time.sleep`: the TUI keeps painting the rail and the flash the user is looking at instead of the browser. Both delivery modes sit behind it — the streamed one (`AutomationController._stream_outbound`) pastes its first chunk into the same fresh focus. If the click did not land, or no region was drawn at all, no paste is attempted (pasting into an unknown window is the one unforgivable failure mode) and the banner falls back to its original `>>> PRESS CTRL+V <<<` wording (`PASTE_FLASH_TEXT`). Either way it is the same obnoxious banner at the very top of the sidebar (`#side-paste-flash`, bold, red/yellow, blinking at 0.4 s via a Sidebar-owned timer toggling the `flash-alt` class — pure presentation, so the dumb widget may own it), just with different text; `Sidebar.show_paste_flash(text=...)` takes the copy to show. It hides when the moment has provably passed: a `MATCH` busy probe (the model is chewing — the paste/send landed), a new `ClipboardCaptured` (the conversation moved on without it), or `clear_transcript()`. `Sidebar.show_paste_flash`/`hide_paste_flash` are the only entry points; display on/off (and, now, which text) is the tested contract.
- **Who holds the focus when a delivery ends** — one rule, and it follows from what the banner is *asking for*. Exactly one of the three outcomes hands the foreground back to AgentClip (`snap_back_after_click()`, step 6's beat-and-snap): **auto-sent**, i.e. the paste landed *and* the opt-in auto-submit Enter was tapped (`ServicePreset.auto_submit`; the same `auto_sent` flag that picks `>>> AUTO-SENT <<<`). There is nothing left to do in the browser, so the next thing worth looking at is this window's STATE rail and transcript, and alt-tabbing back to it is not the user's job. The other two deliberately **leave the browser focused**: `>>> PRESS ENTER <<<` and `>>> PRESS CTRL+V <<<` are both instructions to act *over there*, and stealing the foreground while asking for a keystroke in another window would force the user to click back into the chat to obey a banner that has already stopped being true. A **refused** Enter tap counts as not-auto-sent for the same reason — the send is theirs again. The rule covers the streamed delivery too, because a stream's auto-submit is that same tap on that same flag. DISARMED needs no separate guard: it never clicks, so it can never reach `auto_sent`. One per-service escape hatch sits on top of the rule (`ServicePreset.snap_back`, default **on** = what the tool has always done): untick it and even an auto-sent delivery leaves the browser in front. It is a **debugging aid** and reads as one — the question "was the chat box ever really selected, and where did the caret end up?" is one this window cannot answer once it has taken the foreground back. It gates only the delivery's snap; the auto-copy harvest's own snap back (step 6) is a different moment and is untouched.

- **The audible "your move"** (`ServicePreset.alert_sound`, default off; `alert_repeat_seconds`, default 0). Everything else the loop says, it says on screen — which is the problem, because the whole point of the tool is that the user is doing something else while a turn runs. So a service can opt into a two-tone descending beep ("uh-oh", `driver.automation.alerts.play_uh_oh`: `winsound.Beep(660, 180)` then `(440, 240)` on Windows, the terminal bell written to `sys.__stdout__` elsewhere, since a Textual app has redirected `sys.stdout` into its own capture). The trigger is a **state**, not a call site: `set_loop_state` is the one door every transition comes through, and it arms `AttentionAlarm` on `loop_state.ATTENTION_STATES` (`MANUAL_INSERT`, `MANUAL_COPY` — the two the loop cannot leave by itself) and disarms it on everything else. Nine copy-pasted beeps would have been nine places to forget to *stop* one. Armed is a state too: arming while already armed is a no-op, so a failed paste that becomes a manual copy is one uh-oh, not two. `alert_repeat_seconds` above zero replays it on a stop-event wait until the loop moves on, so a disarm lands *inside* the gap rather than after it; the sound always runs on a daemon thread of its own, because `winsound.Beep` blocks for the length of the tone and the event loop must not. Shutdown stops it by name (`stop_alert()`, beside `stop_input()` and `stop_detectors()` in both shells' unmount). One re-sync has no loop state behind it — a **protocol error**, where nothing ran, nothing moved, and the user still has to go back to the browser and re-copy — so the session controller asks for a single chime through the view port (`ChatView.alert_attention` → `AutomationController.sound_attention_once`), which is still gated on the live service's `alert_sound`.
- **The retry button** (`#retry-insert-btn`, "Retry insert") is the flash's one action, mounted directly under it and shown by `show_paste_flash(..., retry=True)` — i.e. exactly when the banner is the `>>> PRESS CTRL+V <<<` one, because an insert that landed has nothing to re-run and offering to paste a second payload on top of the first is worse than offering nothing. `AutomationController.retry_insert()` parks the payload back on the clipboard (`park_on_clipboard`) and re-runs `deliver` — **the same method the auto flow calls**, so the retry cannot deliver something different, skip the auto-submit tap or forget to re-open the reply gate. That shared method is the reason the split exists at all: `copy_outbound` is now "write the clipboard, remember the payload (`pending_insert`, cleared by `clear_transcript()`), deliver it", and the button is the second door onto the last step. Only the SCHEDULING stayed in the shell: `MainScreen.retry_insert` is the `run_worker` around the controller's. Three refusals, all harmless to press into: nothing copied yet, DISARMED (§3.5 — a button is not an exemption from "no clicking, no typing"; the toast names F5), and an auto-copy flow mid-sequence, whose mouse work this would shove through.
- **Scope and layering**: the captured icon lives in the service profile — shared by every window on that service, persisted to disk, so it outlives `/new` *and* the process; only the trigger state (`copy_armed`, `copy_changed_streak`, `stale_arm_streak`) and the session gate (`awaiting_pasted_reply`) are reset by `clear_transcript()`. Nothing is persisted to the config file. The flow itself lives in `AutomationController`, below every UI shell (gui.md §1, slice 6) — the *session* controller still never knows the feature exists, and the TUI keeps only the `run_worker` that schedules it.

### 3.4c A sub-agent run, end to end

When the model calls `delegate`, the engine parks the turn in `AWAITING_SUBAGENT` and hands the controller a `Delegate(task, context)` step. What follows is a *nested session*, not a parallel one: the master's flow coroutine is blocked inside the delegate call for the whole run, which is exactly what lets the single clipboard watcher, the single approval gate, the single `ask_user` future and the single focused transcript be **retargeted** rather than duplicated. At most one chat is live at any instant.

1. **Ask first.** `view.delegation_available()` is checked before anything is built. False ⇒ the model gets `status=error` naming the missing calibrations (`view.delegation_missing()`), the master's turn continues, and no tab is opened. The controller never learns what a "new-chat button" is — the gaps cross the port as data. The same refusal covers a second way the ground can move: `_subagent_service` is frozen at bootstrap (both pickers lock for the session's life) but the **service editor is not**, so F2 mid-session can delete the very preset that key names. A frozen key that is no longer in `config.services` refuses the delegation outright — building the engine anyway would fall through `cli.build`'s unknown-preset fallback to `[general]`, giving the sub-run neither the budget readiness advertised nor the one its window is pointed at.
2. **Save the master.** The whole per-session context (engine, chat name, preset, stats, glyph strip, last outbound, YOLO mirror) is snapshotted into a local and restored in a `finally`. YOLO deliberately does **not** inherit: `ApprovalPolicy` is per-engine, so a sub-agent starts from the configured default. The **permission mode** is the exception, and the only field the swap does not touch: it is an app-wide dial (§2.6a), so `_adopt_ctx` leaves the mirror alone, `_sub_run` arms the sub-agent's engine with it before that engine's first payload, and `_restore_ctx` restores everything *except* it. `_SessionContext.engine_mode` records only what the master's **policy** was left at, so `_rearm_master_mode` can hand the master a mode cycled while it was parked — and stay silent when nothing moved, since re-sending the same mode would arm a pointless "the mode is now …" note on a conversation whose mode never changed.
3. **Build a sub-agent, on the sub-agent window's service.** `EngineRequest(service=self._subagent_service, role="subagent", allow_delegate=False, parent_chat_name=…)` → its own Engine, its own chat name, its own `SessionStore` (the `session` event records the parent, so the audit trail joins up), the sub-agent bootstrap variant, and a catalog with no `delegate` in it — nesting is excluded by construction, not by a special case. `_subagent_service` is the service the SUB tab was on when the session armed, carried across the port in `SessionSpec.subagent_service` and frozen there (§1.6): its paste budget is the budget of the chat this run is actually going to be pasted into, and composing against the master's would silently overrun a smaller one.
4. **Start its transcript and compose.** `open_session_view(ref)` appends the `── task: <title> ──` divider to the sub-agent window's (persistent) panel, records where this run's events begin, badges the tab `▶`, and focuses that window; the task (plus `context` under its documented heading) is composed into a bootstrap. A `BudgetExceeded` here is an error result to the master, never a crash.
5. **Open its chat — before any paste.** `start_chat(ref)` searches the SUB-AGENT window's chat region for THAT tab's service's captured new-chat button, clicks the match, and only then retargets the automation. Three refusals, three different stories: nothing captured / no window drawn (`NOT_CALIBRATED`), the button is not on screen right now (`MISMATCH` — nothing is clicked, because clicking blind in a browser window is the one thing worse than not clicking), and the OS swallowing the input (`NOT_CLICKED`). **False aborts the delegation with zero paste calls**, because a sub-agent's bootstrap in the master's chat is unrecoverable. This is the single most damaging failure mode in the feature and has its own tests at both layers.
6. **Run the ordinary loop.** Ingest → review → gate → execute, against the sub-agent's engine, into the sub-agent window's transcript, pasting into the sub-agent's window and polling it with ITS service's finish detectors. Replies are routed by chat name (`peek_chat_name`, a cheap scan of the last sentinel line) **before** the busy check — a sub-agent reply reaching the master's depth-1 queue would never be looked at, since the master is busy for the whole run. A master-chat reply arriving mid-run is dropped with an explanation, never queued: the master's next payload is composed fresh afterwards, so it is stale by definition.
7. **Hand the result back.** `task_done`'s `result` becomes the `delegate` call's result body, verbatim (falling back to `summary`, then to a placeholder — the delegating agent's result body is never empty). The run is annotated, its slice of the transcript is closed and the sub-agent tab drops its `▶` for a `✓` (or, on any of the failure paths below, a `✗` and an honest note); `end_chat` returns the automation to the master window, the master's context is restored, its window is refocused, and the turn resumes at the call *after* `delegate`. The next delegation appends under its own divider in the same panel — the window's transcript is one scroll, and `render_log` slices it back apart per run.

**Waiting and stopping.** There is no wall-clock timeout — the transport is a human alt-tabbing between two browser windows and a bounded sub-task can honestly take twenty minutes. The composer therefore stays enabled for the whole sub-run (its border reads *"Sub-agent running · /abort ends it and tells the model"*) even though the master's flow is busy, because `/abort` is typed there. Two escape hatches, deliberately different:

- **`ctrl+x`** cancels the tool calls running *right now*, in whichever chat is live. The turn still finishes and reports (the killed call plus the skipped ones) into that chat. A delegation survives it.
- **`/abort`** ends the whole run. The master gets `status=error, body="the user aborted the sub-agent run…"`. Where it lands depends on where the run is parked, and all three cases converge on the same `finally`: waiting for a reply ⇒ the reply future raises; at an approval gate ⇒ the gate is rejected (which aborts that turn) and a latched flag ends the run at the next reply park; executing tool calls ⇒ `request_cancel()` on the sub-agent's engine unblocks the worker, that turn ends normally, and the latch ends the run when the loop comes back for a reply. A sub-agent's `ask_user` is **not** abortable this way: while the composer is in answer mode its text is the answer, verbatim (§3.3a's precedence rule), so `/abort` typed there is an answer like any other.

Every failure path — uncalibrated, unverified click, abort, budget, or an exception nobody predicted — comes back to the model as an `error` result on the `delegate` call, and the `finally` always restores the master, drops the live slot back to the master's window and refocuses the master's window.

### 3.4d Service appearance profiles

Everything §3.4a–c searches for is an **appearance**: a small picture of what one of a service's controls looks like, captured once and recognised wherever it happens to be. This section is the one place the whole model is written down.

**The seven kinds** (`agentclip.driver.screen.profile.TemplateKind`, in declaration order — the service editor's APPEARANCE column is generated from it, §1.4): `BUSY` (on screen only while the model generates — the stop button, not a spinner: an animation is a different picture every frame and can never be matched back), `IDLE` (its mirror: on screen only while the chat is idle, usually the send button), `CHATBOX_INITIAL` and `CHATBOX_ONGOING` (the input box in its fresh-chat and mid-conversation layouts, captured while empty), `COPY` (one response's copy icon), `NEW_CHAT` (the browser's new-chat control), and `SEND_READY` (the ready-to-send button, §3.4b's send gate — the mirror of the two chat-box captures in one respect that matters: it is captured with **something typed** in the composer, because the control only exists while there is something to send, and a capture made against an empty box is a capture of nothing). Each kind carries its own overlay `prompt` and its own match threshold (`max_diff`: 0.08 for the three crisp icons, 0.10 for the hover-tinted new-chat button and for the ready-to-send button, which services routinely tint or fade as the composer fills, 0.20 for the big mostly-flat chat boxes) — properties of the *appearance*, so they live on the enum, not in the TUI. `ServiceProfile` is the per-service bag of captured kinds; readiness questions (§1.6) and every search go through it.

**A kind is a thing on screen, not a picture of it — so it holds a *stack*.** One control is routinely drawn several ways: a send button greys out while a file uploads, an icon tints on hover, a composer grows an attachment chip. A profile that could hold only the picture it was last shown would not fix that, it would move the blind spot — so `ServiceProfile.templates` maps each kind to a **list** of `Template`s, `put` appends, `variants(kind)` is the only reader, and `drop(kind)` empties the whole stack (the editor's per-kind "Clear", §1.4). There is deliberately no single-template `get`: that is the shape in which a call site searches for the first image and never learns the others exist. Match time is a plain **OR-union** against the kind's own `max_diff` — no priorities, no per-variant meaning — so *found* means any image matched: presence questions stop at the first hit (`PresenceTracker`, the send-gate probe), "the newest one" takes the bottom-most across all of them (`driver.automation.flow.lowest_match`), and "all of them" unions the hits and folds near-duplicates away, so two images of one control read as one element (§3.4a). `captured` and `describe()` still count **kinds**, not images — *"is the copy button calibrated?"* is a yes/no question however many pictures of it there are — and it is the editor's per-kind status line that says how many (§1.4).

**Where inside an appearance the click lands is part of the appearance.** A match hands back a *rectangle*, and until now every click went to its centre (`ScreenRegion.center`) — fine for a 24px icon, wrong for a chat box that is clickable end to end and puts an attachment tray in the middle of it. So each kind carries a **click point**: two percentages of the matched image, `ServiceProfile.click_point(kind)` / `set_click_point`, defaulting to **50/50** — which is the centre *to the pixel*, for every size (`region.click_point_region` rounds half up, so `floor((size-1)/2 + 0.5) == size // 2`). 0/0 is the top-left pixel and 100/100 the bottom-right one: the percentages span the picture's *pixels*, not its edges, so an extreme is still inside the control. A percentage rather than an offset because the picture is recognised wherever it turns up and may be scaled by a zoom the user changed after capturing.

It is applied at the three places a click is aimed at an appearance, all of them reducing the match to a 1×1 region first (`click_point_region`): the chat-box focus click (`AutomationController.chatbox_target`), the copy click (before `COPY_CLICK_OFFSETS`, so the small retries walk around the point the user chose rather than around a centre they rejected), and `click_profile_element` — the new-chat button today. The **whole-window fallback keeps its centre**: with no chat box found, `chatbox_region` answers with the region the *user drew*, which is not the picture any click point describes, and aiming a tenth into it would land in the transcript. Busy, idle and send-ready are never clicked at all, and still carry a click point, because the editor shows all seven rows and a kind that is clicked one day is exactly the kind whose row has to have been there.

Stored in the **profile**, not the preset: it is a fact about the captured picture, so it belongs with the picture and dies with it — clearing a kind (or dropping its last variant) puts the point back to 50/50, since the next capture is a different rectangle of a possibly redesigned control. On disk it is one **optional** top-level manifest key, `"click_points": {"<kind>": [x, y]}`, which is why it needed no format bump: a manifest without it describes seven centre-clicked appearances, an entry that is not a pair of numbers reads as the same, and out-of-range numbers are clamped rather than dropped. `save_click_point` is legal for a kind with **nothing captured yet** — the user can know where in a control the click belongs before they have drawn the box around it. Both editors write it immediately, like a capture and unlike the preset form (§1.4, and the GUI's `set_click_point` / `svc_click_point`).

**The search** (`agentclip.driver.screen.template`): pure Python cannot afford a naive 2D scan (a 1920×1080 region is ~2M candidate offsets), so candidate generation is pushed into C-level `bytes` operations. At capture time, `Template.build` quantises the image's blue plane (`pixels[0::4].translate(>>5 table)`, 8 buckets — a bucket comfortably exceeds the tolerance-24 noise band) and picks 8 eight-byte **anchors** at the most varied windows on distinct rows. Per search, the scene's plane is built the same way once and each anchor's needle is swept **bottom-up** with `bytes.rfind` — when the per-anchor candidate cap (512, counting only deduped, in-bounds candidates) does bind on pathologically repetitive content, the survivors are the bottom-most ones, which is where the answers live (the newest response's copy button, the chat's action area). Each surviving candidate origin passes a 16-point grid probe before the full 1024-sample strided verification (per-channel tolerance 24 on B/G/R, the undefined X byte skipped, the stride bumped to be **coprime with the template width** — a stride sharing a factor with the width collapses the samples onto a few columns and can score a mostly-different image as a perfect match) produces the diff that `max_diff` judges; a global `MAX_VERIFICATIONS` cap bounds the worst case. Quantisation has a boundary hazard — a pixel drifting across a bucket edge breaks an exact `find` — and the first mitigation is 8 anchors preferring **distinct rows and distinct needles**: one surviving anchor is enough, and a genuinely static element keeps most of them. That is not enough on its own when the drifting shade is the **background**, which is on every row: a crop of a menu item on a flat panel is ~80% background, so every anchor carries it and row redundancy buys nothing (Gemini's `#1f1f1f` sidebar is blue 31, one unit under the edge at 32 — a single unit of hover tint took the new-chat button off the map while the comparison at its own origin still called it perfect). So anchors are chosen and searched against **two rulers**: the plain `v >> 5` and an offset `(v + 16) >> 5`, whose edges interleave 16 apart, so a shade shifting by up to 16 crosses at most one of them and the other reads exactly the byte it read at capture. Sixteen anchors, two failure modes that no longer coincide, and a residual band of 17–24 that the OpenCV backend exists to cover (§3.4g). The tiled worst case (a 2560×1440 scene covered in copies of the template) measures ~95 ms; the typical busy-path probe is ~10–30 ms — comfortable fractions of the 0.5 s poll tick on a worker thread. `find_all_in_region` returns every verified occurrence (ambiguity is the caller's question, §3.4a), `find_lowest_in_region` answers "the newest response's copy button" (max y), and `match_rect` converts a scene-local hit back to absolute screen coordinates for the click. The same coprime-stride rule guards `busy.diff_fraction`, which the staleness detector scores frames with — there the aliasing was not a nuisance but a harvest-mid-generation bug.

**Persistence** (`agentclip.driver.screen.profile_store` + `agentclip.driver.screen.png`): one folder per service key under `config.default_profile_dir()` (a `profiles/` sibling of config.toml), holding one PNG per captured **image** plus a `profile.json` manifest (`FORMAT_VERSION = 2`: `templates` maps a kind to a **list** of `{file, width, height, captured_at}`, in capture order, alongside the optional `click_points` table above). Files are `<kind>.png` for a kind's first image and `<kind>-2.png`, `<kind>-3.png`… for the rest — the first keeps the bare name so an old folder needs no renaming and a folder of one-image kinds still reads like the filenames somebody would have chosen by hand; the number is the lowest the manifest does not already list, so a PNG orphaned by a crash between the two writes is simply overwritten. **Format 1 is still read** (one entry per kind, normalised to a stack of one) so a profile captured before variants keeps working and migrates the first time it is written to; only format 2 is ever written, and a manifest announcing anything else is neither read nor rewritten. PNG — hand-rolled on stdlib `zlib`/`struct`, colour type 6, filter 0 — earns its ~70 lines over raw bytes because *"did I capture the right button?"* is the single most common calibration question and a PNG answers it with a double-click. Writes are atomic (`mkstemp` + `os.replace`, mirroring `config.save_services`) and ordered PNGs-first-manifest-last, so a crash mid-save leaves a consistent, possibly stale profile — never a manifest naming a missing file; `drop_template` is the mirror (unlist the whole stack, then unlink its files) and validates every filename it is about to delete exactly as loading does, because a manifest is a file anything can write. `load_profile` never raises: a missing directory is an empty profile, an unknown version is an empty profile, one corrupt PNG costs only that one image and the rest of its stack still loads — a damaged config dir must not stop the app booting. Service keys are validated against the editor's own `^[a-z0-9]+(-[a-z0-9]+)*$` before touching the filesystem, so a hand-written config key can never become a path. The store takes its root as a parameter and never imports `platformdirs` — the layering split (config owns the *where*, screen owns the *what*) is enforced by test_layering.

**A capture is a capability, not an instruction — but it is always worth LOOKING for.** Having `BUSY`/`IDLE` in the profile only means the poller *could* decide a response finished with them; whether it does is the service preset's `finish_signals` checklist (§1.3, §3.4b), and for the **finish decision** the two are ANDed — a ticked entry with nothing captured runs nothing, and an unticked appearance folds into no verdict.

**Searching is not ANDed, and used to be.** The picture alone decides whether a frame is looked at for that kind, busy and idle exactly like the other five: `build_detector` hands every captured kind over, and the only thing the checklist changes is whether a `PresenceTracker` — the debounced, verdict-producing half — is built for it (§3.4f). A captured-but-unticked appearance is therefore **display-only**: searched twice a second, sighted, remembered by `last_seen`, drawn in its ELEMENTS row (§1.7), and unable to end a response. The old ANDing left that row at `no match yet` for the life of a session, which is precisely backwards — *"the RHS should always show what button will be used in case it is going to be used, regardless of what is active"*: a user about to tick `busy` needs to see whether their stop-button capture still matches **before** they tick it, and a user who unticked it because it misfired needs to see what it is doing now. The sidebar's busy/idle *verdict* lines (§3.4e) are unaffected and stay silent for an unticked signal, because they report the finish decision and there is none. The same split governs the hover scan: the `COPY` capture says what the icon looks like, `ServicePreset.hover_scan` (default **off**) says whether the flow may go hunting for it with the user's real cursor. Both live in the config file rather than the profile because they are *policy about* a service, not a picture of it — and both are edited two columns away from the capture buttons in the same modal (§1.4), which is why the editor can warn inline when a tick and a capture disagree.

`SEND_READY` is the one kind with **no** policy half, and deliberately so: capturing it *is* turning the send gate on, and forgetting it is turning it off. The rule the pairs above encode is that a capture and a *decision* are different things; here there is no decision left to make once the user has pointed at their chat's send button, so a checkbox would only be a second way to say the same thing — and a third state ("captured but unticked") whose only effect is a feature silently not working.

**Tolerance is per service; `max_diff` is per kind.** The asymmetry is deliberate and worth stating, because the two are easy to confuse. `tolerance` (per-channel, `ServicePreset.tolerance`, default 24, edited on the MATCHING slider §1.4) is how different one *pixel* may be — a fact about a browser, a theme and its anti-aliasing, which is to say about a **service**. `max_diff` is how many of the sampled pixels may be that different — a fact about the **kind** of control being hunted (an icon sitting on whatever text is behind it needs more slack than a chat box), so it stays on `TemplateKind` and is not user-editable. One knob moved to the service; the other did not, and neither one belongs in the profile: both are policy *about* a service, not a picture of one.

**Invalidation is manual by design.** A profile is per service *and per theme*: switch the chat's light/dark theme or hit a site redesign, and the captures stop matching — the fix is that kind's "Clear" followed by a fresh capture in the editor (a capture alone only *adds*, which leaves a stale image being ORed in forever), or "Forget appearance" to start clean. Nothing expires automatically: a template that stops matching degrades to "not found" toasts, and the stale detector still finishes the turn wherever the checklist has it ticked (the shipped default) — annoying, visible, and safe. The failure mode automation must never have is clicking somewhere wrong quietly.

### 3.4e Who owns the sidebar's DETECTION lines

Five lines (`#side-tpl-send-ready`, `#side-tpl-busy`, `#side-tpl-idle`, `#side-stale`, `#side-tpl-copy`, §1.3) plus the whole `ElementsPanel` column beside them (§1.7) report what the finish detectors, and the send gate that holds them back, are seeing. They belong to the **live** window — the one the automation is driving — and everything above them in the column belongs to the **selected tab**. Those two pointers are the same almost always and are apart for exactly the length of a delegation, which is when the readout matters most, so the split has to be stated rather than inferred:

- **Only the detector machinery writes them.** `_start_detector_worker` repaints the whole block (`_paint_detection`) on *every* exit, including the two that start nothing, and the probe handlers overwrite it tick by tick. `Sidebar.show_slot` no longer touches the stale line and `Sidebar.show_profile` no longer resets the probe lines. Both used to: `show_slot` wrote a flat `watching the chat region` whenever the *selected* tab had a region, which silently overwrote `finish detection off` (§1.3) with a promise of an auto-copy that would never come, and froze on a stale claim as the detector set changed underneath it; `show_profile` reset the probe lines on every tab click, throwing away the live readout of the very sub-agent run the user had switched over to read.
- **A tab click that changes nothing does nothing.** `WindowTabs` re-posts `WindowSelected` for a click on the already-selected tab, so `_select_window` early-returns when the window is already selected. `_selected_window` and the displayed panel move together, so there is never a stale view to correct — only widgets to rebuild from state that did not change, which can only lose something.
- **The block names its window.** `Sidebar.show_detection_window(name)` titles it *DETECTION · MASTER* / *DETECTION · SUB-AGENT*, painted by the same repaint. Without the name, a mid-delegation readout of the sub-agent's window reads as the master tab's, which is a worse error than showing nothing.
- **The pictures obey the same rule as the lines.** `AutomationController.consume_elements` is the only per-tick writer of the ELEMENTS column, ghost-filtered on the `generation` stamp alone (like the send-button reading, it is in no `active_detectors` so `is_ghost`'s name check would reject every one); the crops then cross to `MainScreen.paint_elements` carrying a second, PAINT-side epoch, because `post_message` does not order two threads (`shell/tui/messages.py`). The copy row also takes a one-shot from `show_copy_crop` inside the auto-copy flow, which is detector machinery too. `_paint_detection` clears the whole column on every rebuild **and re-titles it** (`ElementsPanel.show_window`) in the same breath as the DETECTION heading: an old window's send button under a new window's name is a straightforward lie. It refills on the new run's first tick. Hiding the column with `F7` stops nothing — the crops keep arriving and keep being painted into a column nobody is looking at, which costs a few dozen cells a tick and means unhiding shows *now* rather than a poll interval ago.
- **The send line is the one `_paint_detection` re-derives rather than resets.** Every other line goes back to a resting state on a poller rebuild, because a rebuilt tracker has seen nothing; adopting a config or recapturing an appearance does not, however, un-paste the outbound the send gate is holding for, so that line is painted from `AutomationController.send_gate_line()` — HOLD/SEEN when the gate is up, and otherwise `gate armed` or `no gate - not captured` depending on whether the live service has the capture at all.
- **Its resting states explain their own silence.** `STALE_CALIBRATED` while stale runs, `STALE_UNTICKED` when the service unticked it but icons still run, `STALE_OFF` when nothing runs at all, `STALE_UNSET` with no region drawn; `PROBE_UNCAPTURED` on a busy/idle line whose signal is ticked with no appearance behind it (§1.3). A line resting forever at "no verdict yet" is indistinguishable from a detector that simply never finds anything.
- **Anything that draws on the screen suspends them.** A fullscreen overlay appearing and vanishing over the browser the detectors watch is exactly the sustained large delta that arms the trigger on staleness alone (§3.4b), so all three surfaces that can raise one bracket it with `MainScreen.suspend_detectors()` / `resume_detectors()`: `AgentClipApp._open_service_editor` around the editor visit (its capture buttons throw that overlay), `MainScreen._pick_chat_region` around the chat-region picker's own, and `MainScreen._identify_live_window` around `/identify`'s read-only one (§3.3a) — which brackets the *drawing* only, since its capture is deliberately taken before any overlay exists. Both resume in a `finally`, because the common exits are the empty ones — an editor closed with no changes propagates nothing, a cancelled pick adopts nothing — and neither would otherwise restart the poller. The picker's resume runs *after* the adoption, so the usual case (the live window is the one just drawn) has already rebuilt the poller and the resume is the no-op it is written to be; drawing the **sub-agent's** window is the case that genuinely restarts the master's poller rather than sparing it, which costs one poll interval and buys immunity to the overlay that was covering the master's window the whole time. F2 is refused outright while `MainScreen.picker_open`: two one-overlay-at-a-time guards on two screens can both be satisfied at once, and cancelling a worker cannot kill a child process.

### 3.4f The detector, and why it knows about none of the above

**A detector detects.** It says what is on screen and where, and nothing about *when* it looks may depend on what anybody is waiting for. `agentclip/driver/screen/detector.py` is that object — plain, Textual-free, unit-tested without a screen (`tests/driver/screen/test_detector.py`) — and everything in §3.4b is a **consumer** of it.

That was not how it shipped. The send button was searched for only while `_send_gate is not None` and the copy button only inside the auto-copy flow's click, so two of the four ELEMENTS rows (§1.7) sat at `no match yet` for the life of a session and a capture that had silently stopped matching was undiscoverable until an automation failed. Worse as a shape: the state machine was deciding what the eyes were allowed to look at, so every new consumer had to be threaded back into the poll loop.

The first fix left three kinds behind — the two chat boxes and the new-chat button, on the argument that nothing on the timer *consumes* them, since each is re-found by the click that is about to use it. That argument is the same mistake one level down: "what does the automation need?" is not the question this module answers. **`RUNTIME_KINDS` is now every `TemplateKind`**, the ELEMENTS column has a row for each (§1.7), and the on-demand searches are unchanged — they re-search a fresh capture at click time because a remembered corner is up to half a poll interval stale, which is a different job from telling the user what the tool can see.

- **The policy is calibration, and only calibration.** `build_detector(region, profile, signals=…, required_ticks=…, tolerance=…, matcher=…)` composes one `ScreenDetector` from a drawn region and one service's calibration. **What is searched is the profile alone**: every kind it holds a picture of is looked for on every frame, all seven, `BUSY` and `IDLE` included. **What can decide** is the checklist AND the profile: a `PresenceTracker` is built for busy or idle only where `signals` ticks it *and* the appearance exists, and a `StaleTracker` where the checklist ticks stillness. Everything else is a plain presence search — `SEND_READY`, `COPY`, both chat boxes, `NEW_CHAT` (none of them has a checklist entry — capturing one *is* the switch, §3.4d), **plus any busy/idle capture the checklist left unticked**, which lands in the same plain-search bucket and produces sightings without verdicts (§3.4d). A kind with a tracker is never also plain-searched: `ScreenDetector` drops it from the template map, because the tracker has already scanned that frame and `observe` reads its sighting back. There is no parameter through which a gate, a flow, a session or a loop phase could reach in.
- **Two questions, two answers, and no caller confuses them.** `searches(kind)` is *will a frame be looked at for this*, now true of anything captured; `active_detectors` is *what can close a tick and fold into a finish verdict*, still the three trackers and only them. `finish_tick_closed_by` and `is_ghost` read the second; `searched_kinds` (the ELEMENTS rows), the poll loop's `consume_send_ready` guard and `_copy_last_seen_note` read the first, and none of those three was ever asking about finishing. `DetectionSnapshot.busy`/`.idle` stay narrower than `sightings` on purpose: `None` unless the signal is ticked, even on a frame that carries a sighting for the kind. The two search settings (§3.4g) arrive here as plain values off the preset and are resolved **once**, at build time: `select_matcher(name)` turns the configured backend into a real candidate source and every tracker is handed the same `tolerance`, so a service cannot end up with its busy probe judging pixels differently from its copy button.
- **And the detector stays backend-agnostic.** `ScreenDetector` holds a resolved `Matcher` object, never a backend *name*; nothing on the poll path knows that `"opencv"` is a string, that it might not have been installed, or that a fallback happened. `observe` passes `self.tolerance` and `self.matcher.origins` into the same `find_in_region` it always called. Swapping the backend changes which origins get compared and nothing about how a comparison is decided — which is why `DetectionSnapshot`, `Sighting.diff` and every row of the ELEMENTS column mean exactly what they meant before, whichever backend produced them.
- **One frame, one snapshot.** `observe(scene)` folds the tick's single capture into a `DetectionSnapshot`: the three finish probes (`None` for a detector that was not built), plus `sightings` — one entry per **searched** kind, mapped to a `Sighting` (kind, winning `Template`, `RegionMatch`, and the frame's timestamp) or to `None` for searched-and-missing. A kind absent from the map was not searched, which now means exactly one thing **for all seven alike**: nobody captured it. `present(kind)` is the three-valued view the send gate reads (on screen / not on screen / no answer, the last being a failed capture). `scene=None` reaches every tracker as the same ERROR with its streak intact and searches nothing at all.
- **Two ways to ask.** The snapshot is *this frame*; `last_seen(kind)` / `seen_ago(kind)` / `locate(kind)` are the **memory** — the most recent frame each kind was actually on screen, with its timestamp, never cleared by a miss. That is what "tell me what you detected and where" means to a caller that is not standing at the poll loop. **A remembered location is not a click target**, and the one caller that clicks (the auto-copy flow) re-searches a fresh capture before it touches the mouse; the memory is read for diagnosis only (`_copy_last_seen_note`, §3.4b).
- **MainScreen keeps a bridge, not a policy.** `_start_detector_worker` builds the detector, records `detector.active_detectors` and the three trackers into the controller under their existing names (the paste, the flow and a slot move each reset the **debounce**, which is a per-tracker act — `AutomationController.reset_trackers`, which SWAPS a fresh tracker in rather than clearing one the poller may be inside), then hands it to `AutomationController.detector_loop`, which captures, calls `observe`, and feeds its own consumer in the same call stack: the finish probes in build order, `consume_send_ready` on every tick the button is calibrated, and one `consume_elements` with a crop per sighting. The 0.5 s cadence, the generation stamping and the ghost filter are all exactly as they were; the THREAD is the controller's since gui.md §1's slice 4, which is why what crosses back to this screen is a paint rather than a probe.
- **Cost.** Seven anchor-based searches a tick, where the gated version ran two. Measured on a 1200×900 region (24 px appearances for the four icons, 848×5 and 834×5 for the chat boxes, 100×30 for the new-chat button), and it is close to linear in the number of kinds because `_quantised_plane` over the *scene* dominates and is paid once per template: **~23 ms** for two, **~43–51 ms** for four, **~83–87 ms** for all seven — the same whether the appearances are present or absent and whether the scene is a flat page or noise. Under 18% of the 500 ms interval, in a worker thread. The cadence was not touched, and the answer to "is this affordable" is a measurement rather than an argument. If it ever stops being affordable the lever is obvious and untaken: the scene's quantised plane is recomputed per template and could be computed once per frame.

### 3.4g The two matcher backends, and the one thing they share

A search is two halves: **propose origins worth comparing**, then **compare them properly**. Only the first half is pluggable (`agentclip/driver/screen/matchers.py`, selected per service by `ServicePreset.matcher`). The second half — the 16-point grid probe, the 1024-sample strided comparison, the per-channel `tolerance`, the `max_diff` on the kind, the `MAX_VERIFICATIONS` budget, the `diff` on the returned `RegionMatch` — is **shared verbatim**. That split is the whole design, and everything else here follows from it: two backends that disagree about *where to look* still agree about *what a match is*, so one tolerance slider governs both honestly, the number in the ELEMENTS column means the same thing whichever is running, and a user can switch between them and compare the result instead of re-learning the readout.

| | `anchors` (default) | `opencv` |
|---|---|---|
| how | 16 quantised 8-byte needles located with `bytes.rfind` (§3.4d) | `cv2.matchTemplate` (`TM_CCOEFF_NORMED`) over every origin, then the peaks |
| character | a **fingerprint** search — finds what it recognises | an **exhaustive** sweep — nothing to recognise, so nothing to lose |
| dependency | none | the optional `agentclip[cv]` extra |
| cost | ~10–30 ms typical per template | ~50 ms per template on a 1411×740 frame |
| blind spot | a background shift of 17–24 crosses an edge on both rulers | none of that class |

**Why the second one exists.** The two-ruler fix (§3.4d) narrowed the anchors' quantisation blind spot; it could not remove it, because an exact byte search over a bucketed plane always has edges somewhere. `TM_CCOEFF_NORMED` subtracts each window's mean before correlating, which is *precisely* the invariance a uniform surface tint needs — so the shift band that leaves the anchors proposing nothing while the pixel comparison would still call the origin a perfect match is exactly the band the sweep walks straight through (pinned in `tests/driver/screen/test_matchers.py` against the real Gemini capture). It is opt-in per service rather than the default because it costs a compiled dependency and a full sweep per template per frame.

**Exhaustive candidate generation is not a looser threshold.** The sweep proposes more origins; it does not accept them. A shift big enough to fail `tolerance` fails under both backends, because both are judged by the same comparison — there is a test for that, since a backend that quietly matched more would make the slider mean two different things.

Three mechanics matter in how the sweep reduces a correlation surface to a shortlist, and each is about not losing the true match: **local maxima** (a dilation compared against the original) rather than a raw top-N, because a correlation surface is hills and the best 256 scores are routinely 256 origins on *one* hill; the best `MAX_PEAKS` (= `MAX_VERIFICATIONS`) of those hills, since anything below that cannot be verified anyway; and finally **sorted bottom-most first**, matching the anchor sweep's `rfind` order — ranking by score chose *which* origins, not the order the budget is spent in, and the rest of `driver.screen.template` (`find_lowest_in_region` above all) is written around bottom-most-first.

**Two things are load-bearing about the wiring.** `cv2`/`numpy` are imported **inside the function**: the screen layer is stdlib-only at module level (architecture.md §1, enforced by `tests/test_layering.py`), and a from-source install without the extra must stay fully functional rather than pay ~40 MB for a feature most users leave off. And a missing `cv2` **falls back to anchors, loudly** — `select_matcher` returns a `Matcher` carrying both what was asked for and what was granted, so the editor can say so inline (§1.4) while the search itself keeps working. A backend that silently searched for nothing would be indistinguishable from a chat window with no buttons in it, which is the one outcome this feature must never produce.

**The frozen exe bundles OpenCV** (architecture.md §6), so on the shipped build there is nothing to install and the fallback should never be reached. That was not the first answer: the exe originally shipped lean, and a user testing it was correctly told *"install it with `pip install agentclip[cv]`"* inside a binary with no environment to install into. The lesson is written into two places rather than remembered — the build carries the extra and verifies it by running the exe's own `--list-matchers`, and the editor's warning knows which kind of install it is running in (§1.4).

**Threaded end to end, not just into the poller.** `tolerance` and `matcher` reach `build_detector` (and through it every `PresenceTracker` and the `StaleTracker`), *and* every search this screen runs outside the poll loop: the auto-copy harvest and its hover scan, the manual harvest, `_find_all`, and `/identify`'s overlay — all of them through `MainScreen._live_search()`, read off the **live** window's preset. Half the call sites on the shipped default and half on the configured one would be two matchers disagreeing about the same frame, and `/identify` in particular is the user's answer to *"why is my button not being found"*: an overlay searching with different settings from the poller would be answering a question nobody asked.

### 3.4h The extra-instructions re-inject (`r`)

A service preset may carry `extra_instructions` — one short line the user wrote about *this host's* quirks (protocol.md §2). It rides the **bootstrap**, so a session starts with the model already knowing. `r` is the other delivery moment: **arm a one-shot reminder that rides the next payload**, for the hour-old session where the model has quietly drifted back to sending code the host mangles.

**Toggle, not a latch.** `r` armed presses `r` again to disarm. The only reason to make it a toggle is the only way to see it: the status bar's `✎ INSTR` segment (§3.3) is lit between the press and the payload that spends it, and a user who lit it by accident has to be able to put it out with the key they hit.

**One shot, and "next payload" means next payload.** `Engine.arm_extra_instructions` sets a flag with exactly `_mode_note`'s lifecycle (§2.6a): it survives until something is actually sent, and it is spent by whichever outbound comes first — a results payload *or* a typed follow-up (`Composer.task` takes the same `notes` sequence `results` does, protocol.md §4). A session steered by typed messages produces no results payload for many turns, and a reminder that waited for one would be armed for the whole of it. The bootstrap never spends it: it embeds the instructions already, and the flag cannot be armed before there is a session.

**Gated on two things, hidden rather than dimmed on one.** `check_action("reinstruct")` returns `False` — the key vanishes from the footer entirely — when the live session's preset carries no instructions, because unlike `u` or `i` this is not a key that becomes available in a moment: on this service it never does. With instructions present it is `None`/`True` on `session_active`, dimmed like its neighbours. The flag comes off `StatusSnapshot` (`has_extra_instructions`, `instructions_armed`), i.e. off the **engine**, not off `MainScreen._config`: a service edited mid-session has not reached the running engine, and `r` may only offer what that engine would actually send.

**Both refusals speak.** The engine answers `arm_extra_instructions()` with one of `armed` / `disarmed` / `no-session` / `no-instructions`, and `SessionController.reinstruct` turns the last two into different sentences — *"no session - the instructions ride the bootstrap when one starts"* and *"this service has no extra instructions - add them in the service editor (F2)"*. A single silent no-op would leave a user pressing a key at a bar that never changes.

Ungated on `busy`, like `shift+tab` and for its reason: the moment a user reaches for this is the moment they have just watched the model mangle something, which is as likely to be mid-turn as not.

### 3.4 Manual fallback and copy-again

- **`i`** — *ingest now*: one forced read of the clipboard, **bypassing** the watcher's unchanged-clipboard guard and the `===CLIP:` pre-filter result caching (still must parse). This is the hotkey fallback when polling is paused/broken or the watcher never saw the change.
- **`c`** — *copy again*: re-copies the current outbound payload (bootstrap, results, or — in chunk mode — the current part) to the clipboard and does nothing else. Status flashes `re-copied the last outbound (11,990 chars) — press c again to deliver it`. This is the recovery for "user copied something else and clobbered the clipboard" — and, **pressed twice inside 1.5 s**, for "the paste never made it into the chat": the second press re-runs the whole delivery through the ordinary send path (§3.4a) — the whole of it, so the re-delivery waits out the browser's activation before its Ctrl+V and obeys the same focus rule at the end (§3.4b: the foreground comes back here only if the payload was auto-sent, and stays on the browser whenever the banner is asking for a keystroke there).
- **`w`** — pause/resume the watcher (auto-paste-detection off; `i` still works).
- Provider death (both copykitten and pyperclip failing): **partially implemented.** Today the fallback is launch-time only — `select_provider` health-checks both and drops to `ManualOnlyProvider`, and the status segment reads `✗ manual paste`; `c` falls back to OSC-52 via `App.copy_to_clipboard()` (write-only, fine for outbound). The mid-session `ClipboardFault` message, a `✗ CLIP ERR` segment, and the selectable-payload modal described here are design intent, not yet built.

### 3.5 The ARMED switch (F5 / `/armed`)

One global switch over everything this app does **to** the machine. `ARMED` (the default) is every release before it existed. `DISARMED` is a promise with a hard edge: *no synthetic input reaches the OS, and the clipboard is not watched.*

**Terminology.** "Armed" is overloaded in this codebase and the collisions are deliberate to name here: `_copy_armed` is the auto-copy **trigger** (§3.4b), `.st-armed` is a status-bar **colour**, `SEND_READY_ARMED` is a **detector** line, and §2.6's YOLO badge is about **approvals**. This section's flag is none of those; in code it is `AutomationController.os_armed` — one armed switch below every shell rather than one per frontend (gui.md §1) — and it is the only one about whether the tool may touch the machine. `ChatView.set_os_armed` and `MainScreen.set_os_armed` only forward the intent.

**What DISARMED stops** — the five acting primitives in `driver/screen/focus.py`, i.e. every synthetic-input call in the app:

- mouse clicks (`click_region`) and scrolls (`scroll_region`);
- cursor moves (`move_cursor`, including the hover scan and the auto-copy flow's pre-snap park over the transcript);
- the synthetic Ctrl+V (`send_paste`), single-burst and chunk-streamed alike;
- focus stealing (`focus_window_verified`);
- clipboard **monitoring** (the watcher worker).

**What keeps running** — everything read-only, because the state a user reaches for this switch in is "what is it about to do, and why?", and blinding the instruments too would be the opposite of helpful: screen capture, all three finish detectors and their verdicts, the send gate, the DETECTION lines (§3.4e), the ELEMENTS crops (§1.7), the STATE rail, `/identify` and the region/appearance pickers (user-invoked foreground UI, not autonomous acting), clipboard **writes**, and `i` force-ingest (one read the user asked for, not a poll — and it is what keeps the manual path completable while the watcher is off).

**The four chokepoints.** The flag is enforced at exactly four places, not scattered through the callers, because each is the sole door to one group of primitives (`MainScreen.set_os_armed` documents the same list):

1. **`copy_outbound`** — the clipboard write still happens, then the focus click and the paste (burst or the streamed walk-in) are skipped. The loop lands in `MANUAL_INSERT` with the existing `>>> PRESS CTRL+V <<<` nag: the manual fallback *is* the disarmed UX, so there is no second implementation of it.
2. **`AutomationController.click_profile_element`** — the one find-then-click primitive returns a new `ElementClick.DISARMED` (`driver/automation/ops.py`) before it captures or searches anything. Covers `/new`'s new-chat click and a delegation's chat-open. The switch's promise is about the *machine*, so it stops at the machine's edge: the delegation is all-or-nothing (nothing clicked, nothing retargeted — a sub-run that cannot drive its window has no half worth having), while `/new` still starts its fresh session and says the switch is why the browser was left alone (§3.3a). A reset costs the user's screen nothing, and refusing it would make the switch quietly disable a command that has nothing to do with the OS.
3. **`AutomationController.evaluate_finish`** — the decision is still reached and still shown; where it would have launched the auto-copy flow it lands on `MANUAL_COPY` instead, leaving `copy_armed` and the streaks exactly as they were (same treatment as the no-captured-copy-button case). The toast says to copy by hand **and** to press `i`, since the watcher is off and no automatic ingest is coming.
4. **The watcher** — stopped via the existing `stop_input`/`start_watching` seam on the controller, `watch_paused` set true.

**In-flight rules.** Disarming mid-turn resets no bookkeeping: `awaiting_pasted_reply`, `send_gate`, `copy_armed` and the streaks are all fed by live detection, so clearing them would only make the sidebar lie about a turn that really is in flight. An auto-copy flow already running is allowed to finish (it holds `flow_running` and an exclusive worker group; interrupting between two clicks is worse than either end) — the guarantee is that no **new** one starts. A mid-turn `/new` is the one path that *does* clear that bookkeeping, and it earns it by ending the session rather than disarming it: the reset reaches `clear_transcript()`, which calls `reset_finish_trigger()` and `close_reply_gate()` — there is genuinely no outstanding reply once the chat it was due from has been replaced.

**The `w` rule.** Disarming forces the watcher off and remembers what it was; re-arming restores *that* — so a user who paused it with `w`, disarmed, then re-armed is not handed back a watcher they switched off themselves. While disarmed `w` is refused outright and `check_action` hides it, exactly as in manual-clipboard mode: there is no state in which a disarmed app may poll the clipboard. A session started while disarmed has its `start_input` remembered as an intention, so re-arming honours it.

**Where the flag lives.** On `MainScreen` — view-owned, unlike `/yolo`. Every primitive it governs is called from the view layer and the controller never touches the OS, so there is nothing here for the engine or a session to hold: YOLO is one session's policy (audited into that session's log, dead when it ends), while this is a property of the machine the user is sitting at and outlives every session on it. The controller's `_cmd_armed` therefore neither stores nor mirrors it; it forwards the intent through one port method, `ChatView.set_os_armed(target: bool | None)` (`None` = toggle).

**Indicators**, both painted synchronously on toggle (no status push is coming — disarming touches no session): the red `⛔ DISARMED` status badge in its own segment (§3.3), and `#side-armed-banner`, a standing, **non-blinking** sibling of the paste flash under the STATE rail. `/armed [on|off]` has no session gate, for `/identify`'s reason one step sharper (§3.3a).

## 4. Transcript design

One mounted widget per event in `TranscriptPanel(VerticalScroll)`; each new widget gets `.anchor()`. Rendering per event type:

| Event | Widget | Rendering |
|---|---|---|
| User task / follow-up / ask_user answer | `Markdown` `.ev-user` | left accent border, "you ▸" label line |
| LLM prose (text outside CLIP blocks) | `Markdown` `.ev-prose` | streamed not needed (arrives whole); plain `Markdown(prose)` |
| Tool call + result | `Vertical .ev-call`: summary `Static` + optional `Collapsible` | summary: `▶ run_command pytest -q · exit 1 · 74 lines` → glyph flips to `✓`/`✗` on completion. Body > 8 lines goes in `Collapsible(title="output (74 lines)", collapsed=True)` containing a `Static` with `rich.syntax.Syntax` (lexer by content: `diff`, file extension, or plain) |
| Approval / rejection | `Static .ev-approval` | `✓ approved edit_file src/utils.py` / `✗ rejected: "wrong function" · 2 calls skipped` |
| Outbound copy | `Static .ev-note` | `→ results copied (3,412 chars, 1 part)` |
| Backup notice | `Static .ev-note` | `▣ backup turn 5 (2 files)` |
| Parse/clipboard errors | `Static .ev-error` | red, full reason, remedy hint (`press c to re-copy`, `copy the full reply`) |

Expand interaction: `Collapsible` is focusable; `tab`/arrows reach it, `enter` toggles (native). Additionally `x` toggles the **most recent** collapsible in the transcript — covers the common "what did that command actually print" glance without focus navigation.

The `RichLog` single-widget transcript was rejected: no per-message collapse/expand, which this design leans on.

## 5. Diff presentation

All diffs render as `rich.syntax.Syntax(..., theme="ansi_dark", word_wrap=False)` inside a `Static` in `#action-body` (`VerticalScroll`, so long diffs scroll with arrows/PgUp/PgDn; `word_wrap=False` keeps hunks readable, horizontal overflow clips). No `textual[syntax]` extra — pygments via Rich, per the digest.

- **`edit_file` (find/replace)**: compute the post-edit file in memory, `difflib.unified_diff(old, new, n=3)` restricted to affected hunks, render with the `diff` lexer. Title line: `edit_file src/utils.py · 1 hunk · −1/+1`. If `find` matches zero or >1 locations, that is an executor *error result*, never a gate — nothing to approve.
- **`write_file`, file exists**: same unified-diff path, title `write_file (overwrite) src/config.py · −12/+40`.
- **`write_file`, new file**: full content as `Syntax(content, lexer_from_extension, line_numbers=True)` under a green banner `NEW FILE src/cli.py (84 lines)`. An all-`+` unified diff was rejected: `+` gutters add noise and lose language highlighting on brand-new code.
- **`run_command` gate**: body is the command line in a bordered `Static` plus the cwd and why it is being asked about — no rule allows it. The third button offers the rule an *always* answer would remember (`bash["git commit *"]`); writing one by hand is `/config` (§3.3a), since the ruleset has no form (F2 only edits services, §1.4).

## 6. Chunked-send UX (chunk-walk mode)

> **Status: designed, not implemented (lands in M3).** The controller currently
> short-circuits a multi-part outbound with a *"multi-part outbound - only part 1
> copied (chunk walk lands in M3)"* note (`shell/app/controller.py`), and `ActionPanel`
> has no wizard mode. Both UI shells target current behavior; the wizard lands
> core-first when M3 arrives. This section is the design it will follow.

When an outbound payload exceeds the preset budget, the protocol layer splits it; the TUI walks the user:

1. Part 1 is copied automatically. ActionPanel shows the wizard:
   ```
   CHUNKED SEND · part 1/3 on clipboard (11,990 chars)
   1. Alt-tab to the chat, paste, send.
   2. The model replies "ACK 1/3" — click its Copy button.
   3. Alt-tab back; the next part is copied automatically.
   [space] skip ACK & arm next part   [c] re-copy this part   [esc] abort send
   ```
   Status segment: `◍ PART 1/3`.
2. Watcher sees the ACK block (protocol marker w/ part number + length echo): on **match** → auto-copy part 2, bell, wizard advances. On **NACK / length mismatch** → re-copy the *same* part, red toast *"part 1 arrived truncated (got 9,400/11,990) — re-copied, paste again"*.
3. Final part sent → model's substantive reply comes back through the normal ingest path; wizard closes, state `ARMED`.

`space` exists because ACK round-trips cost a copy per chunk and some users will trust their service; it advances without verification. Inbound chunking (model output too big) is the protocol designer's problem; the TUI just renders however many ingests arrive against one turn.

**Calibration** (palette `calibrate paste budget`, or from the service editor): copies a numbered marker payload sized to the preset max; user pastes it; model reports the last marker seen; user copies that reply; TUI parses it and toasts a suggested budget with one-key accept (`y`).

## 7. Undo UX

- Before the first file mutation of each turn, the executor snapshots every to-be-touched file (and records created-file paths) under `.agentclip/backups/turn-NNN/` (storage layout = architecture lane). The transcript gets `▣ backup turn 5 (2 files)` so the user knows the safety net exists.
- **`u`** (dynamic: enabled when ≥1 undoable turn exists and state is `IDLE`/`ARMED`/`DONE`, never mid-`EXECUTING`) → `ConfirmScreen` listing exactly what restores: *"Restore 2 files modified in turn 5 (src/utils.py, tests/test_utils.py); delete 1 created file (src/new.py). Commands run in this turn are NOT undone."* Plus a `Checkbox` *"copy a revert notice for the LLM"*, default **ON** when a session is armed.
- On confirm: files restored, transcript line `↩ undid turn 5 (2 restored, 1 deleted)`, and — if the checkbox was on — a notice payload is composed and copied: a plain protocol note telling the model *"the user reverted all file changes from turn 5; file state is as before that turn"* (grammar = protocol contract). Without the notice the model's mental file state diverges and its next edit_file `find` anchors miss — so it defaults on; OFF exists for post-session cleanup.
- Repeated `u` walks back turn by turn (5, then 4, …). Whole-session undo lives on SummaryScreen (`u` there loops it).

The user is staring at the browser; the terminal must call them back:

## 8a. The RUN PANEL — watching a turn execute

Everything else on this screen is about a turn that has already happened or one
that has not started. This region is the only thing that says anything at all
*while* it runs — and a turn can run for minutes, because one of the calls in it
is `npm run build`.

Its predecessor said `Working - running 3 tool calls...` on one line, which was
enough for a turn of three reads (over before it is read) and useless for the
one that matters. Three questions went unanswered: **which** call is running,
**what is queued** behind it, and **what is the command printing**. The panel
answers all three, and disappears the moment the turn ends — the results land in
the transcript exactly as before, so nothing here is a second copy of anything.

```
⠹ Working - running 3 tool calls...  (ctrl+x to cancel)
✓ 1 read_file    src/utils.py
▶ 2 run_command  npm run build                      ctrl+o output
• 3 write_file   src/build.log
```

- **One row per planned call**, in id order, handed over whole when execution
  starts (`ChatView.start_working(label, calls)`) so the queue is visible before
  the first call runs. Pending rows are dim, the running row is bold, finished
  rows carry the `✓ / ✗ / −` alphabet the approval queue strip already uses.
  `detail` — the command line, the path, the pattern — is chosen and clipped by
  the controller; the view renders it and decides nothing.
- **Every row resolves.** The engine reports `done` for calls that never run
  too — denied by a rule, by plan mode or by the unattended toggle, skipped behind a rejection
  or a cancel, pre-resolved parse errors — because a row left pending forever is
  worse than no row.
- **`ctrl+o` opens the running command's output** (so does a click on the
  panel): the last 12 lines of what it has printed so far, growing live, capped
  and scrollable. Collapsed by default — most turns do not need it, and a panel
  that jumped to twelve rows high on every `ls` would be worse than the line it
  replaced. Only `run_command` rows can be expanded; the key is hidden outright
  when nothing is executing.
- **The buffer is MainScreen's, the pane is a view of it** — the harness log
  pane's division of labour (§3.3b), for the same reasons: the deque fills
  whether or not anyone is looking, nothing is painted while the pane is
  collapsed, and revealing it refills in one write. Bounded per call, dropped
  whole when the turn ends.

**How the characters get here.** `run_command` peeks at its `ExecHandle` once per
poll slice (5×/s, the same slices that check the deadline and the user's cancel)
and pushes the *delta* to `ToolContext.on_output`; the engine hands that, and the
per-call `running`/`done` progress, to the controller, which forwards both across
`ChatView`. All of it arrives **on the engine's worker thread**, so MainScreen's
three port methods do nothing but `post_message` (`CallStarted` / `CallFinished`
/ `CallOutput`) — the same bridge the clipboard watcher uses. A host whose
transport cannot expose partial output (`peek()` answering `""`) simply shows
nothing live; the turn is unaffected.

## 9. Edge cases

- **Partial copy** (`===CLIP:CALL` without `===CLIP:END===`, or chunk header without body): parser returns `ParseError(kind="truncated")` → red transcript line + toast *"partial protocol block — click the reply's Copy button and try again"* + bell. State stays `ARMED`; the bad content's hash is remembered so it doesn't re-toast every tick.
- **Prose-only reply** (user copied the right reply but the model emitted no blocks — pre-filter fails): nothing auto-ingests. `i` on such content ingests it as LLM prose into the transcript and toasts *"no tool calls found — reply shown in transcript"*; the user can then send a follow-up with `t`. This also covers "model forgot the protocol" — follow-up nudges it.
- **Two different replies copied quickly**: depth-1 queue per §3.2 (newest wins); the second runs when the turn completes — a mid-turn copy is a deliberate user action, and eligibility knows only the two preconditions (§3.2).
- **5 MB unrelated clipboard**: Windows pays nothing until seqnum changes; one read + substring scan + hash ≈ ms; no protocol marker → ignored. A hard cap (8 MB) skips parsing entirely with a one-time dim toast.
- **Terminal resize**: Textual reflows; ActionPanel `max-height: 60%; min-height: 8;` so the transcript never fully disappears; status segments have CSS `text-overflow: ellipsis` with the watcher segment first (highest priority). No "too small" overlay — degrade silently.
- **`ask_user`**: answering lives on the **persistent chat composer**, not the ActionPanel (the panel is approval-only — its own docstring says so; the original `TextArea#answer` question mode was removed). The question renders in the transcript, the composer switches to answer mode (verbatim — no slash parsing may eat an answer, the §3.3a invariant), plain `Enter` submits; the answer is recorded as the `ask_user` result and the turn continues (remaining calls run), then composes/copies as usual. `Esc` on the empty box **dismisses** the question instead of answering it — nothing is sent, the model stays parked, and the next ordinary message resolves it with the declined-prefix in front (§3.3e).
- **User quits mid-turn** (`ctrl+q` during `EXECUTING`/gate): ConfirmScreen warns the turn is incomplete and results were never sent; backups for the turn are kept.
- **LLM emits unknown tool / malformed call body**: that single call gets an `error: unknown tool 'foo'` result entry (LLM self-corrects next turn); the rest of the turn proceeds.

## 11. Contracts for other designers

**Protocol designer must provide:**
1. Per-call result status enum `{ok, error, rejected, skipped}` + optional `user_note` string (rejection reasons) in the results grammar.
2. A monotonically increasing **turn id** in outbound payloads, for ordering and the audit log only — the chat name, not the turn id, gates ingestion (protocol §1.3).
3. Chunk grammar: part header `k/n` with `len=` char count; ACK/NACK blocks that survive markdown-stripping copy (sentinel lines only, no backticks/asterisks — same rule as all markers); NACK carries observed length.
4. `ask_user` call shape (question text) and `task_done` with a summary field (rendered on SummaryScreen).
5. Bootstrap text must include: (a) "user's message may arrive as an attached pasted-text file — read it entirely"; (b) for Copilot/Gemini presets, "emit all CLIP blocks inside ONE fenced code block"; (c) ACK instructions for chunked input. A `CALIB` block grammar for the calibration flow.
6. Revert-notice block ("user reverted turn N's file changes") for the undo flow.
7. Parser must tolerate: fences wrapped/stripped, leading "Copilot said:", trailing Perplexity citations — and report `truncated` vs `malformed` distinctly (TUI gives different remedies).

**Architecture designer must provide:**
1. `ClipboardProvider` protocol: `read_text() -> str|None`, `write_text(str)`, `name`, `healthcheck()`; Windows variant exposes `changed() -> bool` (GetClipboardSequenceNumber shim) so the watcher can skip reads. Provider selection at startup; active provider name surfaced for the status bar.
2. Single clipboard thread owning reads and writes (write queue), with the self-written-hash registration happening inside that thread before the write.
3. Backup store: `snapshot_turn(turn, paths, created) -> BackupId`, `restore_turn(turn) -> RestoreReport(restored, deleted)`, retention pruning; synchronous and fast (TUI calls from executor worker).
4. Executor as an async service: `execute(call) -> CallResult`, cancellable (quit mid-turn), `run_command` via subprocess without blocking the event loop; the permission matcher returns the rule that decided (displayed in transcript).
5. Preset table struct with **two numbers per service** (`inline_safe`, `max`) + flags (`wrap_in_fence`, `attachment_ok`); user-editable, persisted via `platformdirs`.
6. Command output larger than budget: executor returns full output (TUI shows it all locally in the Collapsible); the payload composer truncates per budget with the protocol's truncation marker.
7. Testability: watcher injectable; tests post `ReplyCandidate` directly and drive with `pilot.press("y")` per `run_test` (`pytest-asyncio`, `pilot.pause()` after posts).
